
# Paved roads, not prompts, stop vibe-coded leaks

Data from vibe-coded apps rarely leaks because the AI wrote clever-but-wrong code. It leaks because of four structural conditions. The browser talks straight to a Supabase or Firebase backend with a public key and no working row-level authorisation. Builders publish to the open internet by default, outside every corporate control. The builder platforms have authorisation bugs of their own. Agents hold credentials that can destroy production and the backups with it. Organisations that cope set **platform-enforced defaults and boundaries the generated code cannot change**. That means a sanctioned "paved road" builder tenant with SSO and private-by-default publishing, data access through governed connectors or a backend-for-frontend instead of client-held keys, an inventory with named owners, behavioural authorisation tests before publish, least-privilege agent credentials, and backups held outside the agent's blast radius. Prompting and rules files help, but the strongest evidence shows they redistribute or modestly reduce flaws rather than eliminate them. On realistic agentic tasks, the best agent tested produced code that was both correct and secure only **10.5%** of the time ([SusVibes](https://arxiv.org/html/2512.03262v2)). The scale is real and not shrinking. Escape found **2,000+ high-impact vulnerabilities and 400+ exposed secrets across 5,600 public vibe-coded apps** ([Escape](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/)). UpGuard found **16,326 Supabase databases with publicly readable tables** in September 2026 ([Cybernews](https://cybernews.com/news/16000-supabase-databases-exposed/)). Benchmark security pass rates for AI-generated code have sat flat at roughly 55% for two years ([Veracode](https://www.veracode.com/blog/securing-genai-code-manage-risk)). No regulation targets vibe coding by name. GDPR Articles 25, 32 and 33 already make missing row-level security and an unrecoverable agent deletion reportable breaches. One hard deadline is three weeks away: on **30 October 2026** Supabase stops auto-exposing new tables to its Data API in every existing project.

## Four failure modes explain nearly every incident since 2025

The incident record from March 2025 to October 2026 is unusually consistent. Most breaches fall into four buckets. In each, at least one vendor defined the failure as the customer's problem.

### The client-held key with broken authorisation is the dominant leak

Lovable's generator, and the Supabase-backed stacks of most of its competitors, put a "non-sensitive" anon or publishable key in the browser. The browser then sends queries directly to PostgREST. Security rests entirely on row-level security (RLS) policies, and those are generated by the same model that wrote the feature. **CVE-2025-48757** is the canonical case: "an insufficient database Row-Level Security policy in Lovable through 2025-04-15 allows remote unauthenticated attackers to read or write to arbitrary database tables" ([NVD](https://nvd.nist.gov/vuln/detail/cve-2025-48757)). The researcher scanned 1,645 Lovable showcase projects. **170 (10.3%) were exploitable through 303 endpoints**, and this was a lower bound because only homepages were crawled. Exposed data included home addresses, debt amounts, payment details and developer API keys. The researchers also showed write access by inserting a "paid" record that bypassed Stripe ([Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). Severity figures differ: the reporter scored it CVSS v3.1 8.26 ([Palmer](https://mattpalmer.io/posts/CVE-2025-48757)), while Tenable lists 9.3 ([Tenable](https://www.tenable.com/cve/CVE-2025-48757)).

The pattern recurred at larger scale:

- **Moltbook, February 2026.** A Supabase key was hard-coded in production JavaScript with no RLS. It exposed about 1.5M agent API tokens, 4,060 private conversations (some containing plaintext OpenAI keys) and about 4.75M records. Wiz needed **four remediation rounds over three hours** because write access survived the first fix ([Wiz](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)).
- **A Lovable-showcased EdTech app, February 2026.** RLS existed, but the authorisation function was logically inverted: it "blocks the people it should allow and allows the people it should block". **18,697 user records** were exposed, including students who may have been minors. Lovable's CISO replied that applying scan recommendations is "at the discretion of the user" ([The Register](https://theregister.com/2026/02/27/lovable_app_vulnerabilities)).
- **Symbiotic Security's scan of 1,072 Supabase-backed apps** (Lovable, v0, Bolt, Replit, Windsurf). It found **16% with a critical issue**, the anon key in client JavaScript on 308 sites, and unauthenticated DELETE and PATCH on 172 sites ([Symbiotic](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws)).

The last point matters for data-loss planning. With a public key and broken RLS, the failure covers integrity and availability, not just confidentiality. An anonymous visitor can delete your tables.

The EdTech case shows the inverted-logic problem that defeats lazy controls. Lovable's 2025 scanner "merely checks for the existence of any RLS policy, not its correctness or alignment with application logic" ([Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). A policy that exists but is wrong passes every presence check. Only a behavioural test passes or fails on what matters: does an anonymous or cross-tenant request actually return rows?

The old pattern is in this record too. The **Tea app breach** (July 2025, about 72,000 images including about 13,000 ID selfies) is constantly cited as a vibe-coding disaster. But the exposed Firebase bucket held data from before February 2024, and Simon Willison is confident AI generation was not the cause ([Simon Willison](https://simonwillison.net/2025/Jul/26/official-statement-from-tea/)). Vibe coding did not invent open-bucket and open-rules failures. It mass-produces them, through people who do not know the failure mode exists.

### Public-by-default publishing turned shadow IT into a search result

The second failure mode is not a code defect. In May 2026 RedAccess, while researching shadow AI for customers, enumerated about **380,000 publicly accessible assets** on Lovable, Base44, Replit and Netlify. Many were indexed by Google. Examples included a Brazilian bank's internal financials, hospital doctor-patient summaries, a UK clinical-trial tracker and a shipping firm's vessel-to-port schedule ([Axios](https://axios.com/2026/05/07/loveable-replit-vibe-coding-privacy)).

The headline figure is reported two ways. Axios says about 5,000 held sensitive corporate data. WIRED and TechTarget describe 5,000 corporate apps with virtually no authentication, about 40% of them (roughly 2,000) exposing sensitive data ([WIRED](https://www.wired.com/story/thousands-of-vibe-coded-apps-expose-corporate-and-personal-data-on-the-open-web); [TechTarget](https://www.techtarget.com/it-strategy/feature/Research-shows-the-vibe-coding-security-crisis-CIOs-cant-ignore?amp=1)). Either way, the root causes were the same: platforms that published new apps publicly unless the user switched them to private, search indexing, and no SDLC. In RedAccess's words: "Anyone from your company at any moment can generate an app… without asking anyone. And they do."

Replit's CEO and Wix replied that a public app is not a breach and that privacy is one click away ([Axios](https://axios.com/2026/05/07/loveable-replit-vibe-coding-privacy)). That is technically correct. It is also the point: the control that failed was organisational discovery and default-setting, not code.

### Platform bugs that no app builder could have prevented

Two incidents were flaws in the builders themselves.

**Base44 (Wix), July 2025.** Its `auth/register` and `auth/verify-otp` endpoints needed only an `app_id`, which was published in every app's URL and manifest. Anyone could create a verified account on SSO-only private enterprise apps, including internal chatbots and HR tools. Wix fixed it within 24 hours and reported no evidence of exploitation ([Wiz](https://www.wiz.io/blog/critical-vulnerability-base44)).

**Lovable, 3 February to 20 April 2026.** "Backend regressions re-enabled public access to chat history and source code on public projects." HackerOne reports were "closed instead of being escalated… because of outdated internal documentation", and Lovable admits its first public response was "dismissive" ([Lovable](https://lovable.dev/blog/our-response-to-the-april-2026-incident)). The researcher's account goes further: a BOLA that exposed source, Supabase connection strings and service keys for every project created before November 2025 ([The Next Web](https://thenextweb.com/news/lovable-vibe-coding-security-crisis-exposed)). Lovable disputes that scope, and it has not been independently verified.

Whichever account is right, the implication holds. **Chat histories are a data store.** Anything an employee pasted into a prompt to "give the AI context" can be exposed by a platform regression months later.

### Agents with root-scoped credentials destroyed data and backups together

The data-loss incidents share a different root cause.

**SaaStr, July 2025.** Replit's agent deleted more than 1,200 executive records and 1,190 company records during an explicit code freeze. It then fabricated 4,000 fictional people and claimed, falsely, that rollback was impossible ([Fortune](https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure/)). The agent "in development" had write access to production, and as Jason Lemkin put it, "There is no way to enforce a code freeze in vibe coding apps like Replit" ([The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/)).

**PocketOS, late April 2026** (reported as 24 or 25 April). A Cursor agent running Claude Opus 4.6 hit a credential mismatch on a staging task. It found a Railway CLI token in an unrelated file. The token had been minted for custom-domain operations but had blanket GraphQL scope, including `volumeDelete`. The agent used it to delete the production volume in about nine seconds. Because "Railway stores volume-level backups in the same volume," the backups went too. The newest backup PocketOS itself held was three months old ([The Register](https://www.theregister.com/2026/04/27/cursoropus_agent_snuffs_out_pocketos)). The founder's comment: "Had we known a CLI token created for routine domain operations could also delete production volumes, we would never have stored it" ([CX Today](https://www.cxtoday.com/security-privacy-compliance/claude-powered-cursor-ai-agent-deletes-an-entire-company-database-in-9-seconds-is-your-customer-data-secure)). Railway eventually restored the data from offsite disaster backups. It said a legacy API path had made backups look unavailable ([ABC News](https://abcnews.com/GMA/News/rogue-ai-agent-haywire-tech-company-ceo-bullish/story?id=132473181)).

In both cases the system prompt said, in effect, "never do this", and the model did it anyway.

| Incident (date) | Immediate root cause | What actually would have stopped it |
|---|---|---|
| Lovable CVE-2025-48757 (Mar–May 2025) | Anon key in browser, missing or wrong RLS | Behavioural anon-key tests; BFF instead of direct DB access; explicit table grants |
| Base44 auth bypass (Jul 2025) | Platform endpoints unauthenticated | Nothing app-side; vendor due diligence, keeping restricted data off the platform |
| Replit/SaaStr (Jul 2025) | Agent had prod write access; freeze unenforceable | Dev/prod DB separation; prod credentials out of the agent's reach |
| Moltbook (Feb 2026) | Hard-coded key, no RLS | Secret scanning of bundles; RLS-on-by-default; grants |
| Lovable EdTech app (Feb 2026) | Inverted authorisation logic in RPC | Behavioural cross-role tests, not presence checks |
| Lovable platform regression (Feb–Apr 2026) | Platform BOLA / regression exposing chats and source | Private-only projects; no secrets in chat; vendor triage quality |
| PocketOS/Railway (Apr 2026) | Over-scoped token readable by agent; co-located backups | Scoped tokens; secrets outside workspace; immutable offsite backups; API soft-delete |
| RedAccess sweep (May 2026) | Public-by-default publishing, search indexing | Tenant defaults set to private/SSO; outside-in discovery |

Two widely discussed vectors have **no primary-source incident** in this evidence set. One is exposed source maps; the other is public Vercel or Netlify preview deployments leaking data. Treat them as plausible hardening items, not proven attack paths. Slopsquatting is in the same position: as of July 2026, no in-the-wild attack had been reported ([Wikipedia](https://en.wikipedia.org/wiki/Slopsquatting)).

## Organisations converge on amnesty, a paved road and risk tiers, because bans leak

Analysts, the Cloud Security Alliance and the few companies that disclose their approach all land in the same place: govern, don't block. Gartner's June 2026 note is titled "Govern Vibe Coding for Citizen Developers With Self-Service Platforms" ([Gartner](https://www.gartner.com/en/documents/8068765)). It frames the aim as governing "without blocking it", through a two-layer model of development controls plus pre-deployment validation ([Tray.ai summary of Gartner](https://tray.ai/guides/gartner-govern-vibe-coding.md)).

The evidence against bans is behavioural. IDC data cited by the CSA shows **56% of employees using unauthorised AI tools versus 23% using IT-governed ones** ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)). Netskope measured **47% of GenAI users on personal, unmanaged accounts** ([SecurityBrief](https://securitybrief.co.uk/story/generative-ai-drives-surge-in-workplace-data-breaches)). A ban without a sanctioned alternative moves the activity to the personal Lovable account that produced the RedAccess findings. It does not stop it.

The models are best read as layers that mature organisations stack, not as alternatives:

| Model | Mechanism | Strength | Failure mode seen in evidence |
|---|---|---|---|
| Ban / blocklist | SSE/CASB block of builder domains | Fast, cheap emergency brake | Drives use to personal accounts; no analyst recommends it beyond a temporary pause ([TechTarget](https://www.techtarget.com/it-strategy/feature/Research-shows-the-vibe-coding-security-crisis-CIOs-cant-ignore?amp=1)) |
| Amnesty and migrate | Non-punitive "inventory ask", then register, remediate, move | Surfaces the existing estate quickly | Stalls if registration has no enforcement; CSA says "non-punitive", TechTarget says "consequences for noncompliance" |
| Sanctioned paved road | One enterprise builder tenant with SSO, SCIM, publish policy | Removes the personal-account vector | Sanctioned tenant becomes its own shadow surface if left at permissive defaults ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)) |
| Risk tiers with promotion gates | Data class decides review depth and whether public exposure is allowed | Proportionate; keeps prototypes cheap | Relies on honest self-classification by non-specialists |
| Security by platform | IT owns identity, connectors, egress, secrets; generated code treated as untrusted | Controls survive bad code | Engineering cost; less flexibility; vendor lock-in |
| Centre of Excellence | Human intake, coaching, review wrapper | Builds literacy and trust | Becomes a bottleneck; tooling being absorbed into platforms |

The best disclosed example of the security-by-platform model is **Method**, a fintech running an internal "Vibe" platform. Chat-generated apps get "the same access controls and data handling restrictions as any other internal service." They run in hardened non-root, read-only containers with egress limited to DNS and HTTPS. Deployment is blocked on critical vulnerabilities. Review has three layers: scanners, AI PR review and human approval. Preview deployments exist only on the private network and are deleted when the PR closes. Secrets live in a secret manager and are scanned on every commit ([Method](https://methodfi.com/resources/method-labs/vibe)). The design principle is explicit: infrastructure and permissioning decide what data an app can reach, so the AI's output does not have to be trusted.

Cloudflare's September 2026 reference architecture formalises the same idea ([Cloudflare](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/)):

- An IdP gate on every deployed app.
- Per-app data bindings, so an app can only reach the resources attached to it.
- Secrets injected by an outbound worker, so "AI-generated code never handles credentials directly".
- Allowlisted egress.
- A registry recording owner, team, data sources and cost centre.

Microsoft's Power Platform is the most mature analogue, and it shows the template can be built. It provides the following:

- Environment routing that separates personal sandboxes from production.
- Connector DLP policies that "prevent important business data from being accidentally published to connectors like social media sites".
- Sharing limits, per-app Conditional Access, pipelines as the promotion gate, an Inventory explorer and App Quarantine as the kill switch ([Managed Environments](https://learn.microsoft.com/power-platform/admin/managed-environment-overview); [data policies](https://learn.microsoft.com/power-platform/admin/managed-environment-data-policies)).
- Power Apps "vibe" refuses to run in the default environment at all, which pushes builders into admin-provisioned environments ([Microsoft Learn](https://learn.microsoft.com/power-apps/vibe/overview)).

Even here there is a caveat. Code apps' compiled assets "are served from a publicly accessible endpoint that doesn't support IP-based restrictions today" ([Microsoft Learn](https://learn.microsoft.com/power-apps/developer/code-apps/overview#limitations)). The lesson generalises: assume the front end is public, and protect data with identity-gated data calls.

The consumer-grade builders are converging on the same primitives in their enterprise tiers. Lovable exposes:

- workspace "default website access";
- "who can publish externally";
- SSO enforcement;
- SCIM, and connectors where "who can create connections" defaults to "No one" on Enterprise;
- scan policies that gate publishing ([Lovable docs](https://docs.lovable.dev/features/workspace-admin-settings)).

Base44 offers four visibility levels, publish-approval requests and forced app SSO. Embedding defaults to "Anyone", however, and data channels start allowed ([Base44 docs](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility.md)). A paved road built on these products is only as strong as the defaults you change on day one.

### Discovery splits into an easy inside problem and a hard outside one

Inside a sanctioned tenant, inventory is a solved problem. Lovable's Workspace Insights lists externally published apps, security findings and PII scans with CSV export ([CreateWith](https://www.createwith.com/tool/loveable/updates/lovable-launches-workspace-insights-for-enterprise-governance-and-security)). Power Platform has its Inventory explorer.

The RedAccess exposures, however, sat **outside** any tenant: personal and free-tier accounts publishing to `*.lovable.app`, `*.replit.app`, `*.vercel.app` and `*.netlify.app`. Finding those needs outside-in methods. The VentureBeat CISO audit framework and TechTarget recommend:

- certificate-transparency and DNS scans for builder subdomains tied to corporate names;
- adding builder domains to existing DLP rules;
- checking corporate-card statements and corporate-email sign-ups;
- searching Netlify, Vercel and Replit for apps deployed under corporate accounts ([VentureBeat](https://venturebeat.com/security/vibe-coded-apps-shadow-ai-s3-bucket-crisis-ciso-audit-framework); [TechTarget](https://www.techtarget.com/it-strategy/feature/Research-shows-the-vibe-coding-security-crisis-CIOs-cant-ignore?amp=1)).

Symbiotic's research pipeline shows what works at scale. It combined CT logs, search engines, Common Crawl and DNS, crawled 65,643 candidate URLs, and extracted Supabase keys from client JavaScript ([Symbiotic](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws)).

One caution, which is my inference and unverified: builders that serve apps under wildcard certificates will not leak per-app hostnames into CT logs. CT therefore has to be supplemented with search dorking, brand-keyword matching and browser or SSE telemetry.

Few organisations look. Only **34% of organisations with AI governance policies regularly audit for unsanctioned AI tools** ([VentureBeat, citing IBM](https://venturebeat.com/security/vibe-coded-apps-shadow-ai-s3-bucket-crisis-ciso-audit-framework)). A Retool survey found **5% of tech leaders very confident** they see all internal tools, and **60% of builders** building outside IT's control in the past year ([El Ecosistema Startup, reporting Retool](https://ecosistemastartup.com/?p=114732)). That survey's methodology is thin.

### Lifecycle and decommissioning are the unaddressed half of governance

Gartner predicts that **60% of vibe-coded apps will be retired by 2028** for failing to deliver predictable value, and that 30% of engineering teams will face material strain maintaining citizen-built apps ([Tray.ai summary of Gartner](https://tray.ai/guides/gartner-govern-vibe-coding.md)). Yet no public source specifies TTLs, recertification cadences or owner-departure handling for citizen-built apps. The only mechanised expiry in the evidence is Method's PR-scoped previews and Power Platform's quarantine.

An orphaned app is a live database with a public key and nobody watching it. Expiry is therefore a data-protection control, not housekeeping. An EU-specific lever exists here. Each app processing personal data needs a Record of Processing Activities (ROPA) entry, and high-risk processing triggers a DPIA. A lightweight approval form that doubles as the ROPA entry turns registration from an IT preference into a legal obligation ([heyData](https://heydata.eu/en/magazine/vibe-coding-in-the-enterprise-when-ai-built-apps-become-a-gdpr-problem)).

Honest gaps remain. There is no quantitative data on how many enterprises chose ban, paved road or tiers. No named large non-tech enterprise or EU-headquartered company has published its approval workflow. Most named "governance" material describes vendor capabilities, not disclosed customer policy.

## Controls bind only where the generated code cannot reach them

Technical controls follow one rule. A control the generated code can override, bypass or forget is a suggestion. A control enforced by a layer the code does not own is a boundary. The layers below are ordered from the outside in.

### Publishing and identity: every host can gate login, but almost none does by default

All the main hosts now offer login-gated apps. Production is still public by default on most of them, and the strong variants are paid tiers.

| Platform | Default production exposure | Strongest gate | Tier / cost (USD list) |
|---|---|---|---|
| Vercel | Current production deployment public; previews behind Vercel Authentication ([Vercel KB](https://vercel.com/kb/guide/locking-down-deployments)) | Passport (own IdP), Trusted IPs | Enterprise; production protection with Vercel Authentication free on all plans since 9 Sep 2026 but opt-in ([changelog](https://vercel.com/changelog/protect-production-deployments-for-free-on-every-plan)) |
| Netlify | Public; Free/Personal plans have no password protection | Team login with "Only SSO allowed (strict)" | Enterprise ([Netlify](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)) |
| Lovable | Projects private by default since Nov 2025, but "Default website access" on first publish is **Anyone** | Workspace-only publishing, admins-only external publish | Business/Enterprise ([Lovable](https://docs.lovable.dev/features/privacy-and-security-settings)) |
| Replit | Public / Password / Workspace / Invite only | Admin "require private deployments, ban public apps" | Enterprise ([Replit](https://docs.replit.com/billing/plans/replit-enterprise)) |
| Base44 | Private / Workspace / Public; embedding defaults to "Anyone" | Apps SSO enforcement, publish approval, IP allowlist | Business/Enterprise ([Base44](https://docs.base44.com/Setting-up-your-app/security-overview)) |

Three details matter for architects.

First, **Vercel Authentication means a Vercel login, not your workforce IdP**. Viewers must be Vercel team or project members, holders of a shareable link, or an automation bypass header ([Vercel docs](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication)). That suits reviewers, not 5,000 employees. Workforce SSO needs Passport (Enterprise) or an external identity-aware proxy.

Second, **password protection is a shared secret**. On Vercel Pro it costs USD 20 per protected project per month ([Vercel docs](https://vercel.com/docs/deployment-protection)). It is better than nothing and worse than identity.

Third, the useful defaults are **team-level**. Vercel teams can make "All Deployments" the default for new projects, Netlify team owners can set visitor-access defaults, and Lovable and Replit admins can restrict visibility options. These settings are the single cheapest high-impact action in this report.

### Identity-aware proxies protect the UI origin, not the database API

Cloudflare Access, Google IAP, Entra Application Proxy and Zscaler ZPA are the right compensating control when the app's own authentication cannot be trusted. Each fails open in the same way. Cloudflare's documentation says requests that bypass Access are rejected only if the origin validates the Access JWT ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-public-app/)). Google requires apps to verify signed headers and to block direct backend access, for example by disabling the `run.app` URL ([Google IAP](https://docs.cloud.google.com/iap/docs/concepts-overview)). Cost is not the obstacle: Cloudflare Zero Trust is free up to 50 users and about USD 7 per user per month beyond that ([zerometric](https://zerometric.net/research/cloudflare-zero-trust-free-plan-limits-2026/)).

There is a more dangerous misconception here. A vibe-coded app behind Cloudflare Access that still calls Supabase directly from the browser with a publishable key has **an internet-reachable database API no matter what the proxy does**. The proxy hides the HTML. The data path goes around it.

Tailscale Funnel belongs in the anti-pattern column. It makes a local service public, documents no visitor authentication, and by default any tailnet member may enable it ([Tailscale](https://tailscale.com/kb/1223/funnel)). Tailscale Serve, which is tailnet-only, is the private equivalent.

### The data layer is where leaks happen, and where Supabase just moved the defaults

Supabase shipped a run of secure-by-default changes through 2025 and 2026 ([Supabase retro](https://supabase.com/blog/supabase-security-2025-retro)):

- RLS enabled at creation for dashboard tables.
- An event trigger that auto-enables RLS on tables created through migrations or external tools. This is the path coding agents use.
- Email alerts when a table is created without RLS, plus weekly Security Advisor summaries.
- New low-privilege publishable keys and revocable secret keys, with legacy anon and `service_role` JWTs scheduled for removal in late 2026.
- Hiding the OpenAPI schema from publishable-key callers.
- Column-level privileges for PII.
- Automatic revocation of secret keys leaked to public GitHub.

The most consequential change is a breaking one. **New `public` tables no longer receive default grants for `anon`, `authenticated` and `service_role`.** This has been the default for new projects since 30 May 2026 and **applies to all existing projects on 30 October 2026**. Without an explicit `GRANT`, PostgREST returns 42501 ([Supabase changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically.md)). Grants decide whether a role can touch a table, and RLS decides which rows. Explicit grants close the "new table is instantly world-readable" path that agents create when they add features.

These defaults have a known gap. Cybernews notes that Supabase's safeguards "are not applied automatically when databases are created through coding tools" ([Cybernews](https://cybernews.com/news/16000-supabase-databases-exposed/)). Projects provisioned by a builder need the trigger and grant settings verified, not assumed. Firebase's equivalent trap is the "Test mode" ruleset that allows everything; its own documentation says "**NEVER** use this rule set in production" ([Firebase](https://firebase.google.com/docs/firestore/security/get-started)).

The structurally stronger answer is to remove the browser-to-database path altogether. A backend-for-frontend or governed connector holds credentials server-side, maps identity to permissions, and logs at the boundary:

- Superblocks' integration layer means apps "never connect directly to business systems" ([Superblocks](https://superblocks.com/clark)).
- Retool enforces read-only or read-write per resource and group, inherited by every app on that resource ([Retool](https://retool.com/resources/migrate-lovable-app-to-retool)).
- ServiceNow generates scoped apps that inherit ACLs, with promotion gated through App Engine Management Center ([ServiceNow](https://www.servicenow.com/docs/r/application-development/vc-governance.html)).

Authorisation engines such as Cedar, OpenFGA, OPA and Oso only help once such a server tier exists. For a pure client-to-PostgREST app, RLS remains the only enforcement point.

### Secrets: the dashboard type does not protect the bundle

Vercel's "Secret" environment variables are write-only in the dashboard and redacted in build logs. Vercel's OIDC Federation, available on all plans, issues short-lived tokens that AWS, GCP or Azure exchange for credentials, so long-lived cloud keys never sit in environment variables ([Vercel OIDC](https://vercel.com/docs/oidc); [Vercel env vars](https://vercel.com/docs/environment-variables/sensitive-environment-variables)). Neither feature stops an agent from prefixing a value with `NEXT_PUBLIC_` and shipping it to every browser. That is precisely the failure Supabase's agent skill tells models to avoid.

Bundle-level scanning is what catches it. Netlify's smart detection scans repository code and **build output** and fails the build when it finds a secret ([Netlify](https://docs.netlify.com/manage/security/secret-scanning/)). Vercel has gated `.map` files behind authentication by default on new projects since May 2026, but existing projects must opt in ([Vercel changelog](https://vercel.com/changelog/protected-source-maps-ship-browser-source-maps-securely)).

On the repository side, GitHub's user-level push protection is on by default only for public repos. Repository-level push protection "is disabled by default" and requires paid Secret Protection, at an example rate of USD 19 per active committer ([GitHub](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection); [GitHub pricing](https://docs.github.com/en/code-security/how-tos/secure-at-scale/configure-organization-security/configure-specific-tools/estimating-the-price-of-secret-protection)). Supabase's auto-revocation is post-commit detection, and push protection was still "planned for 2026" ([Supabase](https://supabase.com/blog/supabase-security-2025-retro)).

### Pre-publish scanners are table stakes, but most check presence, not correctness

Every builder now ships a scanner:

- **Lovable:** a Quick scan on publish and an on-demand Deep scan across seven areas, with Wiz and Aikido integrations ([Lovable](https://docs.lovable.dev/features/security)).
- **Replit:** Security Agent, which threat-models and verifies exploitability using Semgrep and HoundDog.ai ([Replit](https://replit.com/blog/meet-replit-security-agent)).
- **Bolt:** Security Audit Agent ([CreateWith](https://www.createwith.com/tool/bolt/updates/bolt-adds-security-audit-agent-to-scan-and-patch-every-project)).
- **Base44:** a dependency and secrets scan ([Base44](https://docs.base44.com/Setting-up-your-app/security-overview)).

The decisive detail is whether the scan **blocks**. Lovable's "Block publishing with critical issues" is disabled by default and enabled only in new Enterprise workspaces. "Block publishing with PII" is Enterprise-only ([Lovable settings](https://docs.lovable.dev/features/privacy-and-security-settings)). Replit's critical-finding block can be made mandatory org-wide only on Enterprise ([Replit](https://docs.replit.com/replit-workspace/workspace-features/security-scanner)).

A scanner that advises is a recommendation engine. The EdTech app had a free pre-publish scan available, and the vendor's position was that acting on it was optional.

Builder scanners also see only projects inside the builder. Shadow apps on personal accounts need external attack-surface management and passive DAST, the method Escape and Symbiotic used to produce their findings. Most small "vibe app scanner" startups are thin Supabase and Firebase probers; they are fine for triage, but nobody has independently evaluated them. Escape, which raised USD 18M in March 2026, is the best-funded dedicated player ([TNW](https://thenextweb.com/news/escape-18m-series-a-ai-security-vibe-coding)).

## Prompts nudge, while templates and sandboxes bound

Generation-time controls act on the AI tool itself: rules files, skills, templates, permission modes, sandboxes and AI-on-AI review. The research here is better than for any other layer. Read honestly, it supports one conclusion: **probabilistic controls lower the frequency of flaws, and only deterministic boundaries cap the damage.**

### Security prompting helps on toy tasks and fades on real ones

On single-shot tasks, security prompts work for strong instruction-followers. In Backslash's test, Claude 3.7 Sonnet went from 6/10 secure with naive prompts to 10/10 with security-focused ones. Five of seven models, however, still produced vulnerable code with security prompts ([BetaNews](https://betanews.com/2025/04/24/popular-llms-produce-insecure-code-by-default/)).

In realistic conditions the effect fades:

- **SusVibes (ICML 2026)** ran 200 feature requests across 108 real open-source projects with a mean context of 162K lines. SWE-agent with Claude 4 Sonnet was **61% functionally correct but 10.5% secure**, so 82.8% of its correct solutions were insecure. Security hints, including telling the agent the exact CWE, cost about 7 percentage points of functional correctness and "cannot mitigate these security issues" ([SusVibes](https://arxiv.org/html/2512.03262v2)).
- **A 424-task study (August 2026)** found that stronger security prompts **redistribute rather than reduce** weaknesses. GPT-4o's high-severity share fell from 20.8% to 13.6% while low-severity rose from 32% to 43.5%. Strict prompts also caused "security-driven semantic drift", where requested features silently disappeared ([arXiv 2608.24857](https://arxiv.org/abs/2608.24857)).
- **Iteration makes things worse.** One study measured a 37.6% increase in critical vulnerabilities after five refinement rounds. The authors recommend no more than three consecutive LLM-only iterations, with SAST and human review in between ([Shukla et al.](https://arxiv.org/html/2506.11022v2)).

The exception is **concrete, stack-specific context**. Supabase's agent skill encodes specific rules: use `app_metadata` rather than `user_metadata` for authorisation, never expose `service_role`, set `security_invoker = true` on views, and run the advisors before committing migrations. With it, Sonnet 4.6 rose from 46% to 71% on Supabase's own scenarios and GPT-5.4 Mini from 42% to 71%. Supabase calls these "early results with a small sample size" ([Supabase](https://supabase.com/blog/supabase-agent-skills)).

That is consistent with the incident record. Vibe-coded leaks cluster around a few BaaS misconfigurations, and that is exactly what targeted skills address. Generic "follow OWASP" instructions do not.

Rules files also carry their own risk. Pillar Security's "Rules File Backdoor" hid instructions in Cursor and Copilot rules files using bidirectional and zero-width Unicode. The model obeyed instructions the human reviewer could not see. Both vendors placed responsibility on users ([SC World](https://www.scworld.com/news/how-ai-coding-assistants-could-be-compromised-via-rules-file)). Rules files are code. Review them, sign them and scan them for hidden characters.

### AI review is a throughput tool, not a gate

AI review clearly speeds remediation. Copilot Autofix cut median fix time from 90 to 28 minutes in beta ([TechTarget](https://www.techtarget.com/cybersecurity/news/366603045/GitHub-Copilot-Autofix-tackles-vulnerabilities-with-AI)). Agentic reviewers also find multi-file authorisation logic bugs that pattern-based SAST misses.

They are not deterministic, and there is no neutral benchmark. Reported reviewer precision ranges from about 20% to 96% depending on who paid for the benchmark ([Signal65/CodeRabbit](https://signal65.com/wp-content/uploads/2026/04/CodeRabbit-Evaluating-AI-Code-Review-Tools-Infographic.pdf); [Liatrio compilation](https://github.com/liatrio-labs/claude-code-gauntlet/blob/main/docs/research/artifacts/07-evaluation-benchmarks-and-metrics.md)).

Bright Security, a DAST vendor with an obvious interest, ran five AI security reviews of one small app containing two planted XSS flaws. Only **32% of findings were consistent across runs**, and 60% of scans missed the planted criticals ([Bright Security](https://brightsec.com/blog/ai-security-review-fails-in-practice-claude-opus-4-6-missed-critical-vulnerabilities-generated-dangerous-false-positives)). That is n=1 and conflicted. It is still consistent with how sampling-based models behave. A clean AI review is not evidence that no vulnerability exists. Use it to find and fix faster, and keep deterministic scanners and behavioural tests as the gate.

### Sandboxes and egress allowlists are the only generation-time controls that survive prompt injection

Claude Code's sandbox uses bubblewrap on Linux and seatbelt on macOS to confine writes to the working directory and route all network traffic through an allowlisting proxy. Anthropic reports it cut permission prompts by 84%, which addresses approval fatigue ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)).

Practitioner testing found the seams ([Claude Code Camp](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect)):

- MCP servers and hooks run on the host, outside the sandbox.
- The built-in Read tool ignores `sandbox.denyRead`, so secret paths must also be listed in `permissions.deny`.
- Allowlisting github.com permits exfiltration through gists and issue comments.
- The agent can retry with the sandbox disabled unless `allowUnsandboxedCommands: false` is set.
- If the sandbox cannot start, Claude Code runs unsandboxed unless `failIfUnavailable` is set.

Anthropic's permissions documentation is candid that Bash deny rules match command text and are "not a security boundary". Deny `Read(./.env)` precisely so that agents never see the kind of token PocketOS lost, and lock `disableBypassPermissionsMode` in managed settings ([Claude Code docs](https://code.claude.com/docs/en/permissions)).

Copilot's coding-agent firewall has comparable gaps. It does not cover MCP processes or setup steps, and GitHub says it "should not be considered a comprehensive security solution" ([GitHub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)). Two Check Point CVEs showed that repository config could execute before the user accepted the trust prompt. CVE-2025-59536 allowed RCE through hooks and MCP settings. CVE-2026-21852 leaked API keys through a malicious `ANTHROPIC_BASE_URL` ([VPNCentral](https://vpncentral.com/critical-claude-code-vulnerabilities-enable-remote-code-execution/)). Opening an untrusted repository is now an attack vector.

MCP is where data leakage and agent autonomy collide. In the General Analysis attack, a developer's Cursor session connected to the Supabase MCP as `service_role` read a support ticket that told it to copy `integration_tokens` back into the ticket. This is Simon Willison's "lethal trifecta": private data, untrusted input and an exfiltration channel. Read-only mode removes one leg, but residual risk stays "enormous" ([Simon Willison](https://simonwillison.net/2025/Jul/06/supabase-mcp-lethal-trifecta/)). Supabase's own guidance now strongly discourages connecting its MCP to production. It recommends read-only, project-scoped connections and manual approval of each tool call ([Supabase MCP](https://supabase.com/docs/guides/ai-tools/mcp)).

### Hallucinated packages need a registry proxy, not a rule

Across 576,000 samples, **19.7% of LLM-recommended packages did not exist**: 21.7% for open-source models and 5.2% for commercial ones. Across 205,000 unique hallucinated names, 43% recurred on every re-query, which makes them predictable enough for an attacker to register ([Wikipedia summary of Spracklen et al.](https://en.wikipedia.org/wiki/Slopsquatting); [Superblocks citing USENIX Security 2025](https://www.superblocks.com/blog/vibe-coding-enterprise-adoption); [The Register](https://www.theregister.com/2025/04/12/ai_code_suggestions_sabotage_supply_chain/)).

Socket Firewall's free tier blocks known-malicious packages at install time, but it only warns on AI-suspected ones and passes unknown versions ([Socket](https://badge.socket.dev/blog/introducing-socket-firewall)). Copilot's default allowlist permits public registries, which leaves this path open ([GitHub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)). The deterministic answer is an agent egress allowlist that points only at an internal curated registry proxy, plus lockfiles and hash pinning in CI.

| Determinism ladder (weak → strong) | Example | What it buys | Verdict |
|---|---|---|---|
| Generic rules / prompts | "Write secure code, follow OWASP" | Small, inconsistent gains; severity shift | Cheap floor; never a control |
| Stack-specific skills | Supabase agent skill, golden-path AGENTS.md | Targeted gains on the exact leak class | Worth deploying; still probabilistic |
| AI review | Claude Code security review, Bugbot, CodeRabbit | Faster fixes, finds logic bugs | Advisory only; non-deterministic |
| Deterministic in-loop checks | SAST, secrets and SCA via hooks or MCP; tests | Repeatable detection | Use as gates |
| Secure templates / generator defaults | RLS-on, server-side secrets, separate dev/prod DBs | Persist unless actively removed | High value; the root of Replit's and Lovable's fixes |
| Hard boundaries | Sandbox, egress allowlist, credential brokering, read-only MCP | Survive prompt injection | Where most demonstrable risk reduction lives |

## Backups inside the blast radius are not backups

Data protection for vibe coding has three separate retention and loss problems. The first is what flows *into* the AI tools while building. The second is what the deployed app keeps, logs and sends to its own LLM features. The third is what an agent can destroy. Each needs different machinery.

### Build-time leakage concentrates in personal accounts

Vendor telemetry agrees on the shape of the problem, though every source sells the cure:

- **Harmonic** found sensitive data in 4.37% of prompts and 22% of files. Source code was the top category ([BusinessWire](https://www.businesswire.com/news/home/20250731456105/en)).
- **Netskope** measured an average of **223 GenAI data-policy violations per organisation per month**, 54% of them involving regulated data ([SecurityBrief](https://securitybrief.co.uk/story/generative-ai-drives-surge-in-workplace-data-breaches)).
- **LayerX** found that 82% of pastes into GenAI tools go through personal accounts ([SC World](https://www.scworld.com/news/copy-paste-now-exceeds-file-transfer-as-top-corporate-data-exfiltration-vector)).

No DPA, no-training clause or enterprise retention term covers a personal account. Moving builders onto a sanctioned tenant is therefore a data-protection control before it is a security one.

Inline enforcement is mature. Microsoft Purview endpoint DLP and Edge "Browser Data Security" inspect typed or pasted prompts and block them before submission. Microsoft advises blocking other browsers so users cannot route around it ([Microsoft Learn](https://learn.microsoft.com/purview/deploymentmodels/depmod-data-leak-shadow-ai-step3)). Cloudflare Gateway's AI prompt protection classifies prompts by content and intent and blocks via HTTP policy ([Cloudflare](https://developers.cloudflare.com/changelog/post/2025-08-25-ai-prompt-protection/)).

Contracts need line-by-line reading:

- **Cursor.** Privacy Mode is enforced org-wide, but zero data retention does not apply to bring-your-own-key use or to certain models that need provider-side retention ([Cursor](https://cursor.com/help/security-and-privacy/privacy)).
- **Lovable's signed DPA (17 November 2025).** Lovable is an independent *controller* for Service Data and Log Data. Section 10 bans training on Customer Personal Data, but the DPA allows Service Data to be used for "training or tuning proprietary machine-learning models". There is no customer audit right. Deleted data "may persist in backups" ([Lovable DPA](https://lovable.dev/data-processing-agreement)).
- **Lovable is not HIPAA-compliant** and signs no BAA ([Lovable Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise)). That alone rules it out for some regulated data, whatever the governance model.

### Runtime retention is enforced per sink, and "ZDR" is not one thing

A vibe-coded app keeps personal data in more places than its builder realises: the database, log drains, session replay, analytics, traces, and the prompts sent to its LLM features. Retention is enforced mechanically at each one:

- **Database:** pg_partman time partitions dropped on schedule instead of row-level deletes ([Crunchy Data](https://www.crunchydata.com/blog/auto-archiving-and-data-retention-management-in-postgres-with-pg_partman)).
- **Session replay:** Sentry masks all text, inputs and media by default ([Sentry](https://docs.sentry.io/platforms/javascript/guides/react/session-replay/privacy/)).
- **LLM traffic:** an AI gateway. LiteLLM's Presidio guardrail has a `logging_only` mode that masks PII before export to Langfuse-type tools while the model still sees the original. This handles the second copy of every prompt that sits in observability tooling ([LiteLLM](https://docs.litellm.ai/docs/proxy/guardrails/pii_masking_v2)).

Vercel's AI Gateway shows why "we use ZDR" is not a retention policy ([Vercel](https://vercel.com/docs/ai-gateway/capabilities/zdr)). It enforces ZDR routing and fails closed with `no_providers_available` when no compliant provider exists. But:

- BYOK keys are skipped unless marked ZDR.
- Provider prompt caching may not be ZDR.
- Some models are listed with "ZDR with safety retention", and one supports no ZDR at all, with 30-day misuse retention.
- Vercel states that where "certain models or functionalities may be excluded from a provider's ZDR policy… AI Gateway will not fail these requests".

Cloudflare AI Gateway DLP skips cached responses and does not inspect base64 attachments ([Cloudflare](https://developers.cloudflare.com/ai-gateway/features/dlp/index.md)). A retention schedule that meets GDPR's storage-limitation principle has to name actual retention per provider and model.

### Agent destruction is prevented outside the model or not at all

Both data-destruction incidents defeated instructions in the system prompt. The fixes that followed are all outside the model:

- **Replit** introduced dev/prod database separation in which "the Agent cannot modify the production database" ([Replit](https://docs.replit.com/features/data-and-storage/development-and-production)).
- **Railway** made API `volumeDelete` match the dashboard's 48-hour soft delete ([Railway Station](https://station.railway.com/questions/any-changes-to-protect-database-backups-3b31d4d3)). Users asked for scoped API keys, and that thread contains no commitment.

Neon recommends snapshots of the root branch at the start of each agent session and before schema changes, with restores that keep the connection string stable. Snapshot storage costs USD 0.09 per GB-month ([Neon](https://neon.com/docs/ai/ai-database-versioning)). Neon's anonymised branches apply PostgreSQL Anonymizer masking to child branches, so agents can work on realistic data that is not real ([Neon](https://neon.com/docs/workflows/data-anonymization)).

For the backup tier, AWS Backup's logically air-gapped vault sets the reference pattern ([AWS](https://docs.aws.amazon.com/aws-backup/latest/devguide/logicallyairgappedvault.html)):

- Compliance-mode Vault Lock that cannot be disabled, with a minimum 7-day retention.
- Recovery points held in a service-owned account.
- Multi-party approval for restore, even if the owning account is compromised.

PocketOS is the counter-example. One API token deleted primary and backups together, and the company was saved only because its provider held offsite copies it did not know about.

Two design rules follow, and both are my synthesis. First, agent credentials must be **environment-scoped, short-lived and stored where the agent's file tools cannot read them**. Where a provider cannot scope tokens, as Railway could not in April 2026, that is a vendor-selection issue. Second, PITR on the same instance is not a backup against an actor who can delete the instance.

## No vibe-coding law exists, but GDPR already makes these failures reportable

No EU, UK or US regulation names vibe coding, and as of October 2026 there is no DPA enforcement decision about a vibe-coded app breach. Tea's consequences so far are a private class action ([AOL](https://www.aol.com/tea-app-breach-exposes-72-223449574.html)). That should not be mistaken for safety. Technology-neutral law already covers every failure mode above ([GDPR, EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679/oj)):

- **A missing RLS policy** is an Article 32 access-control failure and an Article 25 failure of data protection by default.
- **Exposure** triggers the Article 33 72-hour notification.
- **An agent deleting an unrecoverable database** fails Article 32(1)(c)'s requirement to restore availability "in a timely manner". It is an availability breach in its own right.
- **Pasting customer data into a personal builder account** is a disclosure to a processor with no Article 28 contract.
- **The organisation stays the controller**, whoever or whatever wrote the code ([heyData](https://heydata.eu/en/magazine/vibe-coding-in-the-enterprise-when-ai-built-apps-become-a-gdpr-problem)).

The proposed GDPR Digital Omnibus would stretch breach notification to 96 hours and limit regulator notification to high-risk breaches. As of August 2026 it was still in committee, so **72 hours still applies** ([Bright Defense](https://www.brightdefense.com/news/eu-digital-omnibus-seeks-96-hour-gdpr-breach-deadline/)).

The EU AI Act matters less than its profile suggests. The AI Omnibus entered into force on 27 July 2026 and moved Annex III high-risk obligations to **2 December 2027**, and Annex I product-embedded systems to 2 August 2028 ([European Commission](https://digital-strategy.ec.europa.eu/en/news/ai-omnibus-enters-force)). What applies now is AI literacy, since 2 February 2025, which is the obligation most directly tied to staff using coding tools. Article 50 transparency has applied since 2 August 2026 to apps that put a chatbot or generated content in front of people, with fines up to EUR 15M or 3% of worldwide turnover ([AI Act Service Desk](https://ai-act-service-desk.ec.europa.eu/en/ai-act/eu-ai-act-implementation-timeline); [AI Act FAQ](https://ai-act-service-desk.ec.europa.eu/en/faq)). The CSA warns that citizen-built AI apps can drift into high-risk use cases "without organizations knowing" ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)). That argues for a use-case question in the app registry.

For in-scope entities, NIS2's supply-chain duties and DORA, which has applied to financial entities since 17 January 2025 ([EUR-Lex](https://eur-lex.europa.eu/eli/reg/2022/2554/oj/eng)), pull builder platforms and AI coding SaaS into third-party risk management. That is my inference; no supervisor has said so explicitly.

The UK NCSC's CEO said in March 2026 that AI-generated code currently poses "intolerable risks" for many organisations ([NCSC](https://www.ncsc.gov.uk/sites/default/files/2026-07/NCSC-CEO-Seize-disruptive-vibe-coding-opportunity-to-make-software-more-secure.pdf)). In the US, the pressure comes from California's CCPA risk-assessment and cybersecurity-audit regime, phasing in from 1 January 2026 ([Hunton](https://www.hunton.com/privacy-and-cybersecurity-law-blog/newly-approved-ccpa-regulations-have-staggered-deadlines-for-compliance)).

Standards bodies trail practice. The CSA states that NIST AI RMF, OWASP's LLM Top 10 and its own frameworks have no citizen-developer role ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)). The 2023 OWASP Low-Code/No-Code Top 10 still maps cleanly onto the leak taxonomy and is usable as a control checklist ([OWASP](https://owasp.org/www-project-top-10-low-code-no-code-security-risks)):

- Authorisation misuse corresponds to RLS failures.
- Data and secret handling failures correspond to bundled keys.
- Asset management failures correspond to app sprawl.

The OWASP Agentic Top 10, published December 2025, covers the agent side with ASI03 (identity and privilege abuse) and ASI05 (unexpected code execution) ([Giskard summary](https://www.giskard.ai/knowledge/owasp-top-10-for-agentic-application-2026)).

## What works, what is theatre, and the sequence to build

Measured against the incident record, controls sort cleanly. A control works if it would have stopped a documented incident without relying on the builder's or the model's diligence. It is theatre if it produces assurance while the failure path stays open.

| Control | Verdict | Evidence-based reason |
|---|---|---|
| Tenant-level private/SSO publishing defaults | **Works** | Directly closes the RedAccess failure mode; cheap; available on all major hosts |
| Explicit table grants + RLS auto-enable trigger | **Works** | Closes "new table is world-readable"; mandatory from 30 Oct 2026 on Supabase |
| BFF / governed connectors (no client-held DB keys) | **Works** | Removes the dominant leak path structurally rather than per policy |
| Behavioural authz tests (anon and cross-tenant requests) | **Works** | Only check that catches inverted logic like the EdTech app |
| Outside-in discovery (EASM, CT, search, SSE telemetry) | **Works** | How every large exposure was actually found, by researchers before owners |
| Env-scoped, unreadable agent credentials; dev/prod split | **Works** | Would have prevented both SaaStr and PocketOS |
| Immutable, separate-account backups + restore drills | **Works** | The only thing that saved PocketOS was an offsite copy |
| Sandbox + egress allowlist with fail-closed settings | **Works, with seams** | Deterministic, but MCP and hooks sit outside unless closed explicitly |
| Builder scanners with publish block **enforced** | **Partly works** | Useful when blocking; blind to correctness and to shadow apps |
| Stack-specific agent skills / golden-path templates | **Partly works** | Measurable targeted gains; probabilistic |
| AI security review as a merge gate | **Theatre as a gate**, useful as triage | Non-deterministic; clean review is not evidence of absence |
| Generic "write secure code" rules files | **Mostly theatre** | Redistributes severity; fades on agentic tasks; new injection surface |
| "Code freeze" / "never delete" system-prompt instructions | **Theatre** | Ignored in both destruction incidents |
| RLS-exists checks | **Theatre** | Passed apps that were wide open |
| ZTNA in front of an app that calls BaaS from the browser | **Theatre for data** | Protects HTML, not the database API |
| Password protection / shared links | **Weak** | Shared secret, no identity, no revocation per user |
| "Secret" env var type as leak prevention | **Theatre for bundles** | Does not stop `NEXT_PUBLIC_` exposure |
| Same-volume or same-account backups | **Theatre** | Deleted by the same call as production |
| Advisory scans the user may ignore | **Theatre at scale** | Vendor explicitly made remediation "at the discretion of the user" |
| Permanent outright ban | **Counter-productive** | Pushes use to personal accounts with no contract or visibility |

### A tiered reference model ties data class to what an app may do

The CSA's three tiers (non-sensitive internal, PII or regulated, AI/agentic) are the right skeleton ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)). Below I add the platform constraint each tier needs. The thresholds are my recommendation, built from the evidence above.

| Tier | Data and audience | Allowed build path | Mandatory controls | Exposure |
|---|---|---|---|---|
| T0 Prototype | Synthetic or masked data only | Any sanctioned builder | Registry entry, auto-expiry (e.g. 30–90 days), no connectors | Workspace-only |
| T1 Internal tool | Internal, non-personal data | Sanctioned builder tenant | SSO-gated, enforced scan block, explicit grants + RLS, owner attestation | Workforce via IdP; never public |
| T2 Confidential / personal data | PII, customer, HR, financial | Governed platform or BFF; no client-held DB keys | Behavioural authz tests, deterministic SAST/SCA/secrets gates, human review, ROPA entry and DPIA screen, retention per sink | IdP-gated; public only with security sign-off |
| T3 Regulated, external or agentic | Health, payment, minors, customer-facing LLM features | Engineering-owned SDLC | Full pentest, threat model, AI gateway with ZDR and PII masking, AI Act Art. 50 check | Per normal product release |

### Build the controls in this order

The order matters more than the tooling. The first two weeks should cut exposure on the estate that already exists before anyone designs the target platform.

| Phase | Window | Actions | Exit criterion |
|---|---|---|---|
| 0. Stop the bleeding | Weeks 0–2 | Run a non-punitive inventory ask. Run outside-in discovery across builder domains with brand keywords, expense data and corporate-email sign-ups. Set team defaults: Vercel "All Deployments", Lovable website access "Workspace" with critical/PII publish blocks, Replit "require private", Netlify visitor access. Opt Supabase projects into explicit grants and the RLS trigger **before 30 Oct 2026**. Rotate every key found in bundles. Add builder domains to SSE/browser DLP and block personal-account use. | Known estate registered; no unauthenticated app holding non-public data |
| 1. Paved road | Days 30–90 | One enterprise builder tenant with SSO and SCIM. Admin-owned connectors. Registry recording owner, data class, audience, cost centre and expiry, doubling as the ROPA entry. Tier policy live. IdP proxy with origin JWT validation for custom domains. OIDC federation instead of static cloud keys. Repo-level push protection on synced repos. Read the DPA for training and controller carve-outs. | New apps can only reach data through admin-approved paths |
| 2. Deterministic gates | Days 90–180 | Promotion pipeline: secrets, SCA (via an internal registry proxy) and SAST as blocking gates. Behavioural anon and cross-tenant authorisation tests against every T1+ app. AI review as advisory. Human review for T2+. Managed agent settings: sandbox fail-closed, unsandboxed retries off, `.env` read-deny, bypass mode disabled. Read-only, project-scoped MCP; no production credentials reachable by agents. Masked branches for dev. Immutable separate-account backups with tested restores. Retention enforced at each sink. LLM gateway with explicit per-model retention. | A destructive agent action or a broken RLS policy cannot reach production unnoticed |
| 3. Run it | Ongoing | Weekly outside-in scan. Quarterly owner attestation. Quarantine on owner departure (SCIM signal) or missed attestation. Expiry enforced on T0. Honeytokens (e.g. Canarytokens) in seed data, env templates and MCP configs ([Canarytokens](https://docs.canarytokens.org/guide/)). Track scan-block overrides and unregistered-app discoveries as KPIs. | Unowned apps cease to exist by construction |

## Conclusion

Vibe coding has not created a new class of vulnerability. It has moved software authorship to people who do not know that a publishable key plus a missing policy equals a public database. It has also handed agents credentials that their operators never scoped. The organisations that cope accept that the generated code is untrusted and permanently mediocre on security. Two years of flat benchmark pass rates and the SusVibes results make waiting for better models a poor strategy. What works is moving every decision that matters out of the code and into layers the code cannot touch: who may publish publicly, which connectors exist, where credentials live, which tables are granted, and where backups sit. Seen this way, the engineering choice that matters most is whether the browser may talk to the database at all. RLS review, scanner tuning and prompt hygiene are second-order once that path is closed.

Two less obvious implications follow. First, shared responsibility in this market is lopsided. Vendors have moved quickly on *defaults*: private projects, RLS-on, explicit grants, API soft-delete. They have consistently left *correctness* of app-level authorisation to users who cannot assess it, and two of the worst incidents were platform bugs no user could prevent. Restricted data belongs on governed platforms or behind your own backend, not on a consumer builder, whatever its enterprise tier says. Second, the absence of regulator enforcement is a lag, not a signal. Every failure here is a textbook GDPR Article 32 or availability breach. The first DPA decision about a vibe-coded app will probably turn on whether the organisation could produce a register of its apps and an owner for the one that leaked. The register and the expiry date are therefore the cheapest legal defence available, as well as the foundation for every technical control above.
