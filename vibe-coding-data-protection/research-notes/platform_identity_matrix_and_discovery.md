## Key Question 1: For each platform, what is the default exposure of a newly published production app on an enterprise tenant today, and can an admin force private/SSO for all new apps? (the buyer-validation matrix)

### Takeaway
Only three products ship an admin-enforced, inherited "no public apps" policy that applies to all new apps: Replit ("Private deployments: Require"), Base44 ("Apps SSO" toggle plus role-based publish blocking), and Microsoft Power Platform (Entra-only by construction). Vercel and Netlify offer team-level defaults that make new projects private but are overridable per project. Lovable's workspace default for first publish is still "Anyone", and its publish-blocking scanners are enabled by default only in new Enterprise workspaces. In every case the strong variant is a Business/Enterprise SKU.

### Cited Findings — per-vendor detail across the eight audit columns

#### Lovable (docs fetched 8 Oct 2026; pages carry no last-updated stamp)
- **Scope:** Settings are workspace-level; "Default website access" governs the published website; "Default project access" ("Workspace" default; "Restricted" needs Business/Enterprise) governs the project/editor; "Preview link sharing" ("Enabled" default; disabling needs Enterprise) governs preview URLs; "Build secrets" (Enterprise, admin/owner-only) governs build-time env — [Lovable privacy & security settings](https://docs.lovable.dev/features/privacy-and-security-settings); [Lovable workspace admin settings](https://docs.lovable.dev/features/workspace-admin-settings).
- **Default for new enterprise tenants:** "Default website access" default "Anyone" (Business/Enterprise). "Block publishing with critical issues": "Disabled", except new Enterprise workspaces created by Lovable start "enabled". "Block publishing with PII": Enterprise only, "Disabled" except new Enterprise workspaces start "enabled". "Who can publish externally": default "Editors and above" (Enterprise). "External project collaborators": default "Allow all". "Third-party MCP clients": enabled on Business, disabled on Enterprise. "Sensitive data scanning": Enterprise, "Disabled" by default. "Chat send protection": default "Log only" — [Lovable privacy & security settings](https://docs.lovable.dev/features/privacy-and-security-settings).
- **Policy enforcement:** Workspace admin sets defaults; "Individual projects can override the workspace default [website access] in the publish flow"; "Who can publish externally" set to "Owners only" cannot be lowered by admins — [same page](https://docs.lovable.dev/features/privacy-and-security-settings). Connector creation: "Who can create connections and clients" defaults to "No one" on Enterprise — [Lovable workspace admin settings](https://docs.lovable.dev/features/workspace-admin-settings).
- **Identity:** Website access "Workspace" = Lovable workspace membership (builder-console identity). Separately, "App login methods" (Business/Enterprise, default "All methods allowed") lets admins restrict the app's own end-user auth to Email/Phone/Google/Apple/Microsoft/**SAML SSO**/Lovable workspace identity — [Lovable privacy & security settings](https://docs.lovable.dev/features/privacy-and-security-settings). Builder console SSO (OIDC/SAML, Okta/Auth0/Entra) is Business+; SCIM is Enterprise — [Lovable for Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise).
- **Data path:** Lovable Cloud = built-in Supabase-backed backend (database, auth, storage, edge functions) — [Lovable Cloud](https://docs.lovable.dev/features/cloud). Admin connectors and MCP registries are workspace-controlled — [Lovable workspace admin settings](https://docs.lovable.dev/features/workspace-admin-settings).
- **Known bypasses:** Per-project override of website access; preview links enabled by default; "Code downloads" enabled by default (Enterprise can disable); "Cross-project sharing" enabled by default — [Lovable privacy & security settings](https://docs.lovable.dev/features/privacy-and-security-settings). Branded app URLs publish under a workspace subdomain of a verified corporate domain (Business/Enterprise) — [Lovable workspace admin settings](https://docs.lovable.dev/features/workspace-admin-settings).
- **Observability:** Audit logs (Enterprise), searchable by member/action/resource/time, retained about 13 weeks; longer retention and SIEM forwarding via account team — [Lovable for Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise). Security insights (Business/Enterprise) and Workspace Insights CSV exports — see Key Question 2.
- **Contract:** DPA last updated 6 Nov 2025; Lovable is processor for Customer Personal Data but an **independent controller for Service Data**, which §9.1(c) permits using for "training or tuning proprietary machine-learning models"; §10.1 bars training on Customer Personal Data; deleted data "may persist in backups" for an unspecified "limited time"; no direct customer audit right (SOC 2/ISO reports on request); breach notice "without undue delay", no fixed hours; SCCs Module 2/3 and UK Addendum — [Lovable DPA](https://lovable.dev/data-processing-agreement). "Lovable is not HIPAA-compliant and does not sign Business Associate Agreements" — [Lovable for Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise). Enterprise uses zero-data-retention models by default with an opt-in to 30-day-retention models; EU inference is an Enterprise toggle that fails rather than routes outside the EU — [same page](https://docs.lovable.dev/introduction/lovable-for-enterprise).
- **Price (third-party, as of July 2026, checked 5 Oct 2026):** Pro USD 25/month, Business USD 50/month, Enterprise custom with "$500+/month minimums" — [Layer3 Labs guide](https://www.layer3labs.io/guides/lovable-pricing). Lovable's own pricing page did not render in my fetch; the docs state only credit top-up prices (Business USD 30 per 50 credits) — [Lovable plans and credits](https://docs.lovable.dev/introduction/plans-and-credits).

#### Replit (docs undated; fetched 8 Oct 2026)

- **Default:** "apps in your personal workspace default to Public, and apps in an organization workspace default to a private option" — [Replit: Who can access your app](https://docs.replit.com/features/publishing/private-deployments). Admin policy defaults are not stated on the settings page — [Replit privacy and deployment settings](https://docs.replit.com/teams/privacy-and-deployment-settings).
- **Policy enforcement:** "Private deployments": Off / Require / Require for non-admins; "This policy applies to newly published apps. It does not change the visibility of apps that are already published." "Password-protected deployments": Enabled / Disabled / Disabled for non-admins — [same page](https://docs.replit.com/teams/privacy-and-deployment-settings). "Block publishing of critical vulnerabilities" can be required for every app by Enterprise organizations; Auto-Protect is off by default — [Replit Security Scanner](https://docs.replit.com/replit-workspace/workspace-features/security-scanner).
- **Identity:** Private options gate on a **Replit login**; "Only logged in members of your Organization that have access can use the site"; Viewer seats exist for non-builders — [Replit Private Deployments](https://docs.replit.com/cloud-services/deployments/private-deployments); [Replit Pro and Enterprise](http://docs.replit.com/category/teams). Org SSO/SAML + SCIM apply to Replit login — [Replit Enterprise](https://docs.replit.com/billing/plans/replit-enterprise). Password protection is "different from private access tied to an authenticated identity" — [Replit privacy and deployment settings](https://docs.replit.com/teams/privacy-and-deployment-settings).
- **Data path:** Not documented on these pages (apps are arbitrary code; dev/prod DB separation is covered in the original report).
- **Known bypasses:** Changing access requires unpublish/republish; External access tokens let integrations reach private deployments (added 8 May 2026) — [Replit changelog 8 May 2026](https://docs.replit.com/updates/2026/05/08/changelog). - **Observability:** Audit logs streamable to SIEM; Enterprise Security Center with CVE drill-down and SBOM download — [Replit Enterprise](https://docs.replit.com/billing/plans/replit-enterprise). Deployments list per team workspace — [Replit Private Deployments](https://docs.replit.com/cloud-services/deployments/private-deployments).
- **Contract:** Hosting in the US on GCP; EU hosting on request for Enterprise — [Replit About deployments](https://docs.replit.com/cloud-services/deployments/about-deployments). Privacy policy dated 3 Aug 2026 — [Replit privacy policy](https://replit.com/privacy-policy). DPA/HIPAA: not found (Gap).
- **Price:** Core USD 20/month (USD 18 annual), Pro USD 100/month (USD 90 annual), Enterprise custom — [Replit pricing](https://replit.com/pricing). Enterprise: "unlimited seats", annual credit commitment slider USD 10,000–200,000 — [Replit Enterprise](https://docs.replit.com/billing/plans/replit-enterprise). Private and password-protected publishing extended to Core and Starter on 8 May 2026 — [Replit changelog](https://docs.replit.com/updates/2026/05/08/changelog).

#### Base44 / Wix (docs undated; fetched 8 Oct 2026)
- **Scope:** Per-app visibility; workspace-wide embedding policy; workspace-wide data in/out channel policy; Apps SSO toggle — [Base44 Enterprise SSO and app visibility](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility).
- **Default:** Embedding policy "Workspaces start at Anyone"; each role/group publishing rule has its own "Default visibility"; auto-admit SSO users is a workspace default that apps can override — [same page](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility).
- **Policy enforcement:** "Apps SSO" — "When enabled, all apps use workspace SSO, app-level SSO settings are locked, and public apps now require sign-in"; builders cannot override. Embedding and data-channel policies "apply to all current and future apps, and builders can't override" (exceptions only while policy is on). Publish blocking by role with "Request to publish" reviewed by owners/admins — [same page](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility).
- **Identity:** Apps SSO = workspace IdP gating the **deployed app's end users** (genuine end-user federation); separate workspace SSO for builders — [same page](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility). Auth tokens stored in browser localStorage; HttpOnly cookies "aren't currently available" — [Base44 security overview](https://docs.base44.com/Setting-up-your-app/security-overview).
- **Data path:** First-party backend: "Data access rules" per entity type, backend functions expected to verify the user, secrets backend-only; all public endpoints rate-limited by default — [Base44 security overview](https://docs.base44.com/Setting-up-your-app/security-overview).
- **Known bypasses:** Embedding default "Anyone"; per-app override of auto-admit; policy exceptions — [Base44 Enterprise SSO and app visibility](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility). Platform-level auth bug (July 2025) is in the original report.
- **Observability:** Audit logs Enterprise only, with API reference — [Base44 security overview](https://docs.base44.com/Setting-up-your-app/security-overview). Exportable inventory: not documented (Gap).
- **Contract:** SOC 2 Type II, ISO 27001, GDPR with DPA "available on request", PCI DSS payment processing, AWS KMS with dedicated key for Enterprise; HIPAA not mentioned — [Base44 security overview](https://docs.base44.com/Setting-up-your-app/security-overview).
- **Price (annual billing):** Starter USD 16, Builder USD 40, Pro USD 80, Elite USD 160 per month; Enterprise custom with SSO — [Base44 pricing](https://base44.com/pricing). Docs refer to a "Business" tier for governance features and note Elite works for workspaces created before 1 Oct 2026 — [Base44 Enterprise SSO and app visibility](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility); a third-party guide puts Business at roughly USD 149–299/month as of mid-2025 — [Lowcode Agency](https://www.lowcode.agency/blog/base44-pro-vs-business-plan) (dated figure; treat as unverified).

#### Vercel (docs last_updated 2026-09-15 and 2026-09-16)
- **Scope:** Standard Protection = all deployments except production domains; All Deployments = production + previews + generated URLs; Trusted IPs can protect production only (Enterprise); Protected Source Maps gate `.map` files — [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection).
- **Default:** Vercel Authentication "is on by default for all deployments except the latest production deployment" — [Vercel KB](https://vercel.com/kb/guide/locking-down-deployments). Each project must select 'All Deployments'" — [Vercel changelog 9 Sep 2026](https://vercel.com/changelog/protect-production-deployments-for-free-on-every-plan).
- **Policy enforcement:** Team default for new projects (level + method), overridable per project — [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection). Passport team default "applies to projects created after you save it. Existing projects keep their current settings" — [Vercel KB: Passport](https://vercel.com/kb/guide/vercel-passport).
- **Identity:** Vercel Authentication admits team members (viewer role or higher), project members, access-group members, users granted access via request, Shareable Link holders and automation-bypass header users — all **Vercel accounts** — [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication). Passport gates visitors through "your own identity provider" (Okta, Auth0, any OAuth 2.0/OIDC "Generic OAuth"; SAML and Entra not named), Enterprise only, pricing via account team — [Vercel KB: Passport](https://vercel.com/kb/guide/vercel-passport).
- **Data path:** Not applicable at this layer (platform hosts arbitrary code).
- **Known bypasses:** Shareable Links, Protection Bypass for Automation header, OPTIONS allowlist, Deployment Protection Exceptions (make a preview domain public), disabling Vercel Authentication unprotects all existing deployments and re-enabling keeps old cookies valid — [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication); `*.vercel.app` URLs are public and indexable unless locked down — [Vercel KB](https://vercel.com/kb/guide/locking-down-deployments).
- **Observability:** Not covered on these pages (Gap for immutable admin audit/export).
- **Contract:** Not verified in this pass (Gap).
- **Price:** Password Protection USD 20/month per protected project on Pro; included on Enterprise; legacy Advanced Deployment Protection USD 150/month per team; Vercel Authentication for All Deployments and Exceptions free on all plans — [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection).

## Key Question 4: What does Cloudflare's September 2026 reference architecture prescribe?

### Takeaway
The architecture (last updated 28 Sep 2026) prescribes an Access/IdP gate on the platform entrypoint, a dispatch worker that enforces per-app RBAC and per-invocation limits, per-app D1/KV/R2 bindings, an outbound worker that both allowlists egress and injects secrets so "AI-generated code never handles real secrets", and a registry recording owner, team, description, connected data sources and usage. It is a build-it-yourself blueprint on Workers for Platforms, not a managed product.

### Cited Findings
- Cloudflare Access protects the platform entrypoint and integrates with Okta, Azure AD and Google Workspace via SAML/OIDC; Access "verifies employee or third-party access across the custom domain" — [Cloudflare reference architecture](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Hosting on Workers for Platforms; a dispatch worker routes to user workers, applies access checks that "can match role-based access control and assigned permissions", and sets per-invocation processing-time and subrequest limits — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Per-app bindings: a unique D1 database, KV namespace or R2 bucket per app; "Each user worker can access only its attached bindings" — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Secrets: live in Secrets Store; injected at the platform layer by the outbound handler (containers, in development) or outbound worker (Workers for Platforms, in production); "User workers never handle credentials directly" — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Egress: outbound worker governs all production egress; administrators allow/deny destinations, reroute traffic and apply custom policies; downstream access via bindings, Hyperdrive, or Workers VPC with Cloudflare Tunnel — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Development: AI-generated code runs in Containers/Sandbox (full environments with preview URLs) or Dynamic Workers (lightweight evaluation) with an outbound handler intercepting HTTP — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Registry: production registry surfaces each app's owner, team, description, connected data sources and usage metrics; resource tags link each user worker to owner and cost attribution; development metadata store holds user profiles, sessions, cost tags and department/team permissions — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- AI Gateway provides provider routing, cost controls, prompt logging and DLP inspection; Logpush, Tail Workers and Workers Analytics Engine supply observability — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).
- Customer responsibilities are not enumerated on the page; the guidance implies the customer configures IdP/Access policies, RBAC roles, usage limits, egress allowlists, locked package versions and governed container images, security checks and human review in the pipeline, registry metadata and resource tags, DLP rules and audit review — [same page](https://developers.cloudflare.com/reference-architecture/diagrams/ai/enterprise-ai-vibe-coding-platform/).

### Inferences
- The design matches the original report's "security by platform" model (Method, Power Platform) and the audit's invariant list: identity at ingress, scoped data bindings, brokered secrets, egress control and a registry. Its cost is engineering time: none of the components is pre-assembled as a product.

### Gaps
- The page does not describe how a Supabase-style direct-to-BaaS data path would be prevented if a generated app embedded an external BaaS key; the egress allowlist is the only control implied.
- No pricing for Workers for Platforms is given on the page.

## Key Question 6: Identity-aware proxies, origin validation, and Tailscale Funnel vs Serve

### Takeaway
All four IAPs (Cloudflare Access, Google IAP, Entra Application Proxy/Private Access, Zscaler ZPA) depend on the origin being unreachable except through the proxy, or on the origin validating a signed assertion; Cloudflare and Google say so explicitly. Tailscale Funnel exposes a local service to the public internet with no visitor authentication and, once enabled via CLI, defaults to allowing all tailnet members to use it; Serve is tailnet-only.

### Cited Findings
- Cloudflare Access: "To secure your origin, you must validate the application token issued by Cloudflare Access"; validation ensures requests that bypass Access (for example via "a network misconfiguration") are rejected; options are Tunnel "Protect with Access" or manual JWT validation; publicly routable origins must protect the origin IP — [Cloudflare self-hosted app](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-public-app/).
- Google IAP: apps must "Update your app to use signed headers"; on Compute Engine/GKE anyone who can reach the serving port bypasses IAP; on Cloud Run behind a load balancer the auto-assigned run.app URL "might be directly accessible" unless disabled or ingress restricted; enabling IAP directly on the Cloud Run service protects all ingress paths; last updated 2026-10-07 — [Google IAP concepts](https://docs.cloud.google.com/iap/docs/concepts-overview).
- Entra Application Proxy: "Conditional Access Policies are only enforced for successfully authenticated users in Microsoft Entra ID. Passthrough preauthentication doesn't trigger Microsoft Entra authentication, so Conditional Access Policies can't be enforced"; P1/P2 licence; connector needs no inbound ports — [Entra app proxy FAQ](https://learn.microsoft.com/entra/identity/app-proxy/application-proxy-faq); [Entra app proxy overview](https://learn.microsoft.com/entra/identity/app-proxy/overview-what-is-app-proxy). Private Access brokers via the private network connector and the Global Secure Access client; access by user/group assignment and Conditional Access — [Entra Private Access](https://learn.microsoft.com/entra/global-secure-access/concept-private-access).
- Zscaler ZPA: App Connectors "connect to Public Service Edges or Private Service Edges only ... and do not accept inbound connections"; users authenticate with SAML 2.0 SSO via Client Connector — [Zscaler: What is ZPA](https://help.zscaler.com/zpa/what-zscaler-private-access).
- Tailscale Funnel: exposes a local service to the public internet through a Funnel URL; "Anyone with the Funnel URL can reach the shared resource" and no visitor sign-in is described; disabled by default but "Enabling Funnel through the CLI adds a default that lets all autogroup:member users use it"; ports 443/8443/10000 only; `ts.net` names only; beta; last validated 20 Jan 2026. Serve "shares services only with devices in your tailnet" — [Tailscale Funnel](https://tailscale.com/kb/1223/funnel).

### Inferences
- For vibe-coded apps on Vercel/Netlify/Lovable platform subdomains, an IAP in front of a custom domain protects only that hostname; the platform subdomain and any direct BaaS endpoint remain reachable unless separately locked (Vercel's own docs say `*.vercel.app` URLs stay public unless Deployment Protection covers "All Deployments"). This is the trust-path analysis the audit asked for rather than a blanket "theatre" verdict.

### Gaps
- Zscaler ZPA Browser Access (clientless) documentation was JavaScript-gated and not readable; per-app certificate and SAML details for Browser Access were not verified.
- Entra Private Access and Global Secure Access licensing (Entra Suite SKU) was not verified.

## Key Question 7: Shadow-app discovery — do platforms issue per-app certificates, and what does each discovery channel actually yield?

### Takeaway
Direct TLS probes on 9 October 2026 show that all five platform subdomains (`*.lovable.app`, `*.replit.app`, `*.vercel.app`, `*.netlify.app`, `*.base44.app`) are served under a single wildcard certificate, including live apps, so per-app hostnames on platform subdomains never appear in Certificate Transparency logs; custom domains attached to these platforms do get per-domain certificates and are CT-visible. Symbiotic's own pipeline corroborates this: crt.sh produced only 4.8% of its confirmed vibe-coded sites, versus 58% from search dorking, 23% from Common Crawl and 14% from DNS brute-forcing.

### Inferences
- The original report's "unverified inference" about wildcard certificates is now verified for all five named platforms. CT monitoring remains useful for (a) custom domains the company or its staff attach to these platforms, (b) Lovable branded URLs under the corporate domain, and (c) wildcard customer domains on Vercel; it is blind to the `name.lovable.app`-style hostnames that made up the RedAccess findings.
- Because platform subdomains share one certificate and one IP pool, EASM products that attribute by certificate names or netblocks cannot attribute these apps to a customer; attribution has to come from content (brand keywords, logos, corporate email domains, favicon hashes), HTML/JS fingerprints (Escape used Shodan this way), search indexes and Common Crawl, or from inside signals (IdP, email, expense, browser).
- Two independent research pipelines converged on the same triage checks (Supabase URL and anon key in bundle, PostgREST schema enumeration, anonymous read probe), which is therefore the minimum viable check set for a company's own triage; write/delete probes should not be run against assets the company does not own.

### Gaps
- No vendor documentation located confirming that Lovable, Replit or Base44 published-app domains are specifically catalogued in Netskope CCI, Zscaler, Cloudflare Gateway or Defender for Cloud Apps; only generic "Generative AI"/"Artificial Intelligence" categories are documented.
- RedAccess's enumeration method for 380,000 assets remains undisclosed in the sources reached.
- Zylo and Productiv AI-discovery features were not verified (search rate-limited); Torii's comparison is a vendor source.
- Shodan and Censys pricing for a mid-size buyer was not verified in this pass.

## Key Question 8: What practical discovery pipeline (steps, tools, cost) would a mid-size EU company run to find its shadow vibe apps?

### Takeaway
A workable pipeline combines three inside signals (IdP/OAuth and email metadata, expense/SaaS-management feeds, SSE/browser telemetry) with two outside-in channels (search/Common Crawl/DNS brute-force with brand tokens, plus CT only for custom domains), then a passive triage probe and registration into the sanctioned inventory. The tooling can be assembled from free sources (crt.sh, Common Crawl, search operators, DNS wordlists) plus existing SSE/IdP licences; the paid add-ons are a SaaS-management or email-metadata product and an optional external scanner.

### Cited Findings (each step tied to the evidence above)
1. **Inside the sanctioned tenants (day 1, zero cost):** export Lovable Security insights CSV filtered to "Externally published" and "no owner" — [Lovable Security insights](https://docs.lovable.dev/features/security-insights.md); Power Platform Inventory CSV/API — [Power Platform inventory](https://learn.microsoft.com/power-platform/admin/power-platform-inventory); Replit team Deployments list — [Replit Private Deployments](https://docs.replit.com/cloud-services/deployments/private-deployments); Vercel/Netlify project lists with protection settings (team defaults do not retro-apply) — [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection); [Netlify site protection](https://docs.netlify.com/manage/security/secure-access-to-sites/site-protection/).
2. **Identity and email signals (days 1–7):** IdP sign-in and OAuth consent logs for builder domains; email-metadata scan of vendor welcome/billing mails recovers historical sign-ups (Nudge, 25 Aug 2026) — [Nudge Security](https://www.nudgesecurity.com/post/how-to-discover-shadow-ai-with-nudge-security); unfederated-access detection from IdP traffic (Grip) and multi-source SaaS inventory including expense feeds (Torii) — [Torii](https://www.toriihq.com/articles/five-shadow-ai-discovery-tools); corporate-card review and corporate-email registration checks recommended by TechTarget — [TechTarget](https://www.techtarget.com/it-strategy/feature/Research-shows-the-vibe-coding-security-crisis-CIOs-cant-ignore).
3. **SSE/CASB/browser telemetry (days 1–14):** query SWG/CASB logs for builder consoles and for destinations under `*.lovable.app`, `*.replit.app`, `*.vercel.app`, `*.netlify.app`, `*.base44.app` using the GenAI/AI app-type categories — [Cloudflare Gateway app types](https://developers.cloudflare.com/cloudflare-one/traffic-policies/application-app-types); [Purview AI apps](https://learn.microsoft.com/en-us/purview/ai-microsoft-purview); request catalogue additions where missing — [Netskope CCI](https://docs.netskope.com/en/cloud-confidence-index/). VentureBeat's caveat: access logs show platform use, not what was deployed — [VentureBeat](https://venturebeat.com/security/vibe-coded-apps-shadow-ai-s3-bucket-crisis-ciso-audit-framework).
4. **Outside-in enumeration (weeks 1–3):** search dorking with brand/product tokens restricted to the five platform zones (58% of Symbiotic's hits), Common Crawl index queries (23%), DNS brute-force of brand tokens under platform zones (14%), GitHub code search, urlscan.io, Wayback — [Symbiotic](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws); Shodan/Censys HTML/JS fingerprint searches as Escape did — [Escape methodology](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/); CT monitoring (crt.sh/Censys) only for the corporate domain and known custom domains, since platform subdomains are wildcard-certified (own probes, 9 Oct 2026; [Vercel: Working with SSL](https://vercel.com/docs/domains/working-with-ssl)).
5. **Passive triage (continuous):** for each candidate, fetch the bundle and look for `*.supabase.co` URLs and anon/service keys, enumerate the PostgREST OpenAPI schema, and attempt an anonymous read only — the common checks in [Symbiotic](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws) and [Escape](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/); external read-only scanners exist but none claims independent validation — [Vibe App Scanner](https://vibeappscanner.com/products/scanner); [VibeScan](https://replit.discourse.group/t/i-built-an-open-source-tool-to-check-if-your-vibe-coded-apps-are-accidentally-exposing-data/12215).
6. **Register, gate, repeat:** move finds into the sanctioned tenant with the team defaults set (Vercel "All Deployments" team default — [Vercel changelog](https://vercel.com/changelog/set-team-wide-defaults-for-deployment-protection); Replit "Require" — [Replit privacy and deployment settings](https://docs.replit.com/teams/privacy-and-deployment-settings); Lovable website access "Workspace" — [Lovable privacy & security settings](https://docs.lovable.dev/features/privacy-and-security-settings); Base44 Apps SSO — [Base44](https://docs.base44.com/Enterprise/Enterprise-SSO-and-app-visibility)); put custom-domain apps behind an IdP gate with origin validation — [Cloudflare self-hosted app](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-public-app/).

**Cost anchors (USD list, verified dates above):** Cloudflare Zero Trust free to 50 users then USD 7/user/month — [Cloudflare Zero Trust plans](https://www.cloudflare.com/plans/zero-trust-services); Vercel Authentication on All Deployments free on every plan, Password Protection USD 20/project/month on Pro — [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection); Netlify Pro USD 20/month with unlimited members, Enterprise custom for SSO/SCIM — [Netlify pricing](https://www.netlify.com/pricing/); Lovable Business about USD 50/month (third-party, July 2026) — [Layer3 Labs](https://www.layer3labs.io/guides/lovable-pricing); Replit Core USD 20, Pro USD 100, Enterprise USD 10k–200k annual commitment — [Replit pricing](https://replit.com/pricing); [Replit Enterprise](https://docs.replit.com/billing/plans/replit-enterprise); Retool Business USD 50/builder + USD 15/internal user — [Jet Admin](https://www.jetadmin.io/blog/retool-pricing-2026-plans-user-costs-add-ons); Power Apps Premium USD 20/user/month — [Superblocks PowerApps pricing](https://www.superblocks.com/blog/powerapps-pricing). crt.sh, Common Crawl and search operators are free; Nudge/Torii/Zylo/Productiv and Censys/Shodan commercial pricing were not verified.

### Inferences
- For an EU company, step 5 should stay strictly read-only and be limited to assets the company can show it owns or is authorised to test; both research teams that ran write/delete probes acknowledged they could not fully explain how those were non-destructive, which is not a defensible position for a corporate security team. (This is my inference, not legal advice.)
- The highest-yield cheap steps are 1–3; outside-in enumeration is expensive in analyst time because attribution of a `random-name.lovable.app` host to the company depends on content matching, not on infrastructure ownership.

### Gaps
- No published, independently evaluated accuracy figures exist for any dedicated vibe-app scanner.
- No source gives a worked cost for a full outside-in programme at mid-size scale; the figures above are per-component list prices only.
- EUR conversions are not sourced; the approximate 1 USD ≈ 0.90 EUR used in the preamble is an assumption to be replaced with a dated rate.
