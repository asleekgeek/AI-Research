# Controls for the AI coding-agent execution plane: sandboxes, permissions, MCP exposure, credential scoping, dev/prod separation, destructive-action prevention, backups and recovery (as of 9 October 2026)

Scope note for the report writer: these notes were researched after reading the original report (`Vibe_coding_data_leakage_controls.md`) and the independent audit. Where the primary sources contradict or refine a statement in the original report, the discrepancy is called out explicitly under the relevant question (search for "**Correction to original**"). All vendor-documentation claims carry the date the page was fetched or its stated last-modified date, because several of these products changed defaults between October 2025 and October 2026.

---

## Key Question 1: Which agent-plane controls are enforced outside the model (OS sandbox, network proxy, IAM) vs inside (system prompt, permission prompt), and what documented bypasses exist for each?

### Takeaway
Across Claude Code, Copilot coding agent, Cursor, Codex, Windsurf/Devin Desktop and Replit, the only controls enforced by something other than the model are (a) OS-level sandboxes around *shell commands* (bubblewrap/seatbelt/Landlock-style), (b) a network proxy allowlist in front of those sandboxed commands, (c) cloud-side isolation (ephemeral VM/Actions runner, branch and token restrictions), and (d) IAM/OAuth scope on the credentials the agent holds. Every vendor documents that these have seams: file tools, MCP servers, hooks and helper processes run on the host outside the sandbox; sandboxes fail open by default when unavailable; agents can request an unsandboxed retry; classifier-based "auto" modes are explicitly "not a security boundary"; and allowlisted domains (github.com, package registries) remain exfiltration and supply-chain channels. The audit's warning that "deterministic" must not be read as "cannot be bypassed" is confirmed in the vendors' own wording.

### Cited Findings

#### 1a. Claude Code sandbox (code.claude.com docs, fetched 8–9 Oct 2026; docs reference versions up to v2.1.285)

**What is enforced by the OS/proxy, and defaults**
- "The Bash sandbox is a boundary that the operating system enforces around the shell commands Claude runs on your machine ... the limits apply to Bash, PowerShell, and Monitor commands and the processes they start." — [Claude Code: Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing)
- "The sandbox is off by default. To turn it on, run `/sandbox` in a session ... or set `sandbox.enabled` to `true`." — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Default access table: Writes = "The working directory, a per-user temp directory, and directories you've added"; Reads = "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`"; Network = "No direct route out. Connections go through a proxy on your machine that checks each host against your allowed domains, which start empty"; Environment variables = "Inherited from Claude Code, including any secrets in its environment". — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Platform: "The sandbox runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed." Built on the open-source `@anthropic-ai/sandbox-runtime` package. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Mechanisms: Linux bubblewrap and macOS seatbelt; network via a Unix domain socket to a proxy outside the sandbox. Anthropic reports sandboxing "safely reduces permission prompts by 84%" (internal usage; no methodology given). Blog published 20 Oct 2025. — [Anthropic engineering: Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)
- The sandbox proxy refuses hostnames that resolve only to local addresses: "loopback addresses such as `127.0.0.1`, link-local addresses such as the `169.254.169.254` cloud metadata endpoint, and addresses assigned to your own machine" (an allowed intranet hostname resolving to 10.0.0.0/8 still connects). — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- `autoAllowBashIfSandboxed` "still defaults to `true`, so sandboxed commands keep running without prompts." — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)

**Documented seams (vendor's own wording)**
- "The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it." Specifically: "Built-in file and web tools: tools such as Read, Edit, Write, WebFetch, and WebSearch follow permission rules instead. A `denyRead` entry doesn't stop the Read tool, and `allowedDomains` doesn't limit WebFetch". "Other processes Claude Code starts: command hooks, local MCP servers, plugin monitors, LSP servers, and helper commands such as your status line command and `apiKeyHelper` run with your full access". — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Commands the user types at the `!` prompt run unsandboxed in most sessions; `excludedCommands` run unsandboxed; and "Unsandboxed retries: Claude can ask to run a command unsandboxed, usually after it fails in the sandbox". The doc's own remedy: "To put the tools, processes, and commands in this section behind one boundary, run the Claude Code process itself in a container, virtual machine, or the sandbox runtime." — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Unsandboxed retry mechanics: "Claude analyzes the failure and may retry the command with the `dangerouslyDisableSandbox` parameter." Approval depends on mode: `bypassPermissions` = runs without prompt; Manual/`acceptEdits` = prompt titled "Bash command (unsandboxed)"; Auto mode = classifier evaluates; `dontAsk` = denied. "A matching allow rule: if an allow rule such as `Bash(curl *)` matches the command, it also approves the retry, so the command runs outside the sandbox with no prompt". Disable with `"allowUnsandboxedCommands": false` ("Strict sandbox mode"). — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Fail-open default: "By default, if the sandbox can't start because a dependency is missing or the platform is unsupported, Claude Code runs commands without sandboxing. To make Claude Code exit at startup instead, set `sandbox.failIfUnavailable` to `true`." — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- In `bypassPermissions` mode, hosts outside the allowlist are "Allowed without a prompt" unless `strictAllowlist` or `allowManagedDomainsOnly` is on; in Auto mode they are "Refused unless the command listed the host and the classifier approved the list"; in `dontAsk` refused. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Credentials: "There is no built-in credential deny list, so only the files and variables you list are restricted." `sandbox.credentials` (`mode: deny` or `mask`) affects sandboxed Bash only; `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials from all subprocesses. Masking with `injectHosts` substitutes the real value only on requests to listed hosts (e.g. `GH_TOKEN` only on `api.github.com`), which is a local credential-brokering pattern. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Disabling filesystem isolation is warned against because a command could write to "shell startup files, executables on `$PATH`, or `~/.claude/settings.json`, and use them to widen its own access on the next run"; `allowManagedDomainsOnly` "applies only to commands running inside the sandbox". — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Precedence fix: "A `false` in your user settings, `--settings`, or managed settings holds even when a project's settings set `true` ... Before v2.1.285, a project's `true` overrode a `false` in your user settings." — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Practitioner verification (Claude Code Camp, published 9 Apr 2026, modified 1 Oct 2026; headless `stream-json` traces, mostly macOS): confirmed "`sandbox.denyRead` does not stop Claude's Read tool"; default reads reached `/etc/passwd`, a fake SSH key and `~/.zshrc`; the retry escape hatch is on by default and the injected system prompt tells the model to retry "(don't ask, just do it)"; MCP servers and hooks run on the host; allowlisting `github.com` "allow[s] exfiltration through gists and issue comments"; a pattern-based refusal to read a file named `credentials` was defeated by renaming it `data.txt`. — [Claude Code Camp: how the sandbox works and what it doesn't protect](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect)
- **Correction to original (line 254):** the original says the agent can retry unsandboxed "unless `allowUnsandboxedCommands: false` is set" — confirmed, and the docs add that any matching `Bash(...)` allow rule also silently approves the retry. The original (line 252) says "The built-in Read tool ignores `sandbox.denyRead`" — confirmed by vendor docs.

**Permissions layer (model-mediated, with documented limits)**
- Bash deny/ask rules match command text only: "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." Examples: `Bash(curl *)` stops `curl https://example.com` but not `/usr/bin/curl ...` or `sh -c 'curl ...'`; `Bash(rm *)` not `/bin/rm`; `Bash(git push *)` not `git -C . push`. "For filesystem and network enforcement that doesn't depend on the command text, use sandboxing." — [Claude Code: Configure permissions](https://code.claude.com/docs/en/permissions)
- `Read(./.env)` deny "stops the file tools and commands that name the file, such as `cat .env`, but not `grep -r` run over the directory; the `sandbox` block ... closes that gap, because the sandbox adds your `Read` deny paths to what every sandboxed command can't read." — [Claude Code: Example settings files](https://code.claude.com/docs/en/settings-example)
- Trust gating: "Allow rules and `extraKnownMarketplaces` entries take effect after each person trusts this folder itself ... deny and ask rules apply in every session, trusted or not." — [Claude Code: Example settings files](https://code.claude.com/docs/en/settings-example)
- `bypassPermissions` "Skips permission prompts, except for the actions no mode auto-approves" and skips protected-path checks for `.git` and `.claude`; "Only use this mode in isolated environments like container[s]". `defaultMode` values `auto` and `bypassPermissions` "don't take effect from project or local settings ... Before v2.1.257, `bypassPermissions` took effect from any file." — [Claude Code permissions](https://code.claude.com/docs/en/permissions); [Claude Code settings](https://code.claude.com/docs/en/settings)
- Built-in read-only Bash commands (`ls`, `cat`, `grep`, `find` ...) run without prompt in every mode; the set is not configurable except by adding deny/ask rules; `permissions.blockReadsOutsideWorkingDirectories` (v2.1.257+) changes this for paths outside working directories and is honoured as `true` from any scope. — [Claude Code permissions](https://code.claude.com/docs/en/permissions); [Claude Code settings](https://code.claude.com/docs/en/settings)

- CVE-2026-21852: "A repository settings file could set `ANTHROPIC_BASE_URL` to an attacker-controlled endpoint, causing API requests before the trust prompt appeared", leaking Anthropic API keys. CWE-522/CWE-200. CVSS 4.0 5.3 (GitHub); CVSS 3.1 7.5 (NIST). Affected `< 2.0.65`, fixed 2.0.65. Published 20–21 Jan 2026. — [NVD CVE-2026-21852](https://nvd.nist.gov/vuln/detail/CVE-2026-21852); [GHSA-jh7p-qr78-84p7](https://github.com/anthropics/claude-code/security/advisories/GHSA-jh7p-qr78-84p7)

Recommendations: keep Claude Code updated; "Inspect configuration directories such as `.claude/` and `.vscode/` before opening projects"; review configuration changes "with the same rigor as source code". — [Check Point Research: RCE and API token exfiltration through Claude Code project files](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files/)
- Independent write-up (27 Feb 2026) maps the hooks issue to fix version 1.0.87, the MCP consent bypass to CVE-2025-59536/1.0.111 and the API-key issue to CVE-2026-21852/2.0.65, and concludes "configuration files effectively become part of the execution layer" and the trust prompt "is not a reliable boundary: two of the three issues bypassed it." — [urandom.io: The Claude Code Vulnerability Trilogy](https://urandom.io/blog/2026-02-27-git-clone-and-youre-pwned-claude-code-vulns)
- **Correction to original (line 259):** "CVE-2025-59536 allowed RCE through hooks and MCP settings" conflates two issues. Per Check Point's timeline, the hooks RCE was GHSA-ph6w-f82w-28w6 (no CVE, fixed Aug 2025) and CVE-2025-59536 was the MCP consent bypass (fixed Sep/Oct 2025). The NVD text for CVE-2025-59536 is generic ("execute code contained in a project before the user accepted the startup trust dialog") and does not name the mechanism, so the mapping relies on Check Point's and urandom.io's accounts.

#### 1b. GitHub Copilot coding agent (docs.github.com, fetched 9 Oct 2026)
- Firewall is on by default and "a recommended allowlist is also enabled by default so the agent can download dependencies." Recommended allowlist covers "Common OS package repositories", "Common container registries", "Package registries for languages including C#, Dart, Go, Haskell, Java, JavaScript, Perl, PHP, Python, Ruby, Rust, and Swift", CAs and Playwright browser hosts. — [GitHub Docs: Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- Limits in GitHub's words: "The firewall applies only to processes the agent starts through its Bash tool. It does not directly apply to MCP server processes or processes started in configured setup steps"; "Sophisticated attacks may bypass it"; the firewall "should not be considered a comprehensive security solution." Blocked requests produce a warning in the PR body/comment with the blocked address and command. — [GitHub Docs: Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- Org controls: "Enable firewall" and "recommended allowlist" each have Enabled / Disabled / "Let repositories decide" (default); org-level allowlist entries "can't be removed at the repo level"; owners can block repos from adding custom rules ("Allow repository custom rules"). The page does not address enterprise-level policy. — [GitHub Docs: Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- Platform-enforced guardrails: "Copilot cannot push directly to your default branch"; pushes only to a single `copilot/` branch; "Actions workflows triggered by pull requests raised by the agent require approval from a user with write access"; "By default, the cloud agent has a firewall enabled to prevent exfiltration of code or other sensitive data"; "The agent filters hidden characters that might allow users to hide harmful instructions in comments or issue contents"; only responds to users with write access; "has no access to Actions organization or repository secrets. Only secrets added to the `copilot` environment are passed to it." — [GitHub Docs: Responsible use of Copilot coding agent](https://docs.github.com/en/copilot/responsible-use/copilot-coding-agent)
- Session cap "59 minutes", cannot be extended; repo rulesets incompatible with the agent block it; one branch and one PR per task. — [GitHub Docs: About Copilot coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- MCP: default GitHub MCP server "connects to GitHub with a specially scoped token that only has read-only access to the current repository"; "Once an MCP server is configured, Copilot can use its tools autonomously without asking for approval" so GitHub "strongly recommends allowlisting specific read-only tools rather than using `"*"`"; secrets reach MCP config only via `COPILOT_MCP_`-prefixed Agents secrets; remote OAuth MCP servers not supported; code review may only use tools with `annotations.readOnlyHint: true`. — [GitHub Docs: Extend coding agent with MCP](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/extend-coding-agent-with-mcp)
- **Note vs original (line 267):** "Copilot's default allowlist permits public registries, which leaves [slopsquatting] open" is confirmed by the recommended-allowlist contents.

#### 1c. Cursor (cursor.com docs and official forum posts)
- Sandbox launched 29 Oct 2025 with Cursor 2.0: macOS only, Seatbelt-based; inside the sandbox commands cannot access the network unless "Auto-run network access" is enabled; a model can request to run outside the sandbox, requiring approval; limited to Pro/Pro+/Ultra at launch (Team/Enterprise "not updated at the time"). — [Cursor forum: Agent Sandboxing available in Cursor 2.0](https://forum.cursor.com/t/agent-sandboxing-available-in-cursor-2-0/139449)
- Cursor 2.5 (17 Feb 2026) added sandbox network access controls: per-project `sandbox.json` allowlist, allowlist + Cursor defaults, or unrestricted; enterprise admins can set allow/deny lists applying to all agent sandbox sessions, and a custom admin allowlist "replaces the defaults rather than merging". — [Cursor forum: Cursor 2.5 Sandbox Network Access Controls](https://forum.cursor.com/t/cursor-2-5-sandbox-network-access-controls/152126)
- `sandbox.json` reference: `type` default `"workspace_readwrite"`; `"insecure_none"` disables the sandbox; `readBoundary: "system"` is the default (reads not restricted to workspace) and `"workspace"` (Cursor 3.23+) prompts for reads outside; `networkPolicy.default` is `"deny"`; "Private RFC 1918, loopback, and cloud metadata addresses are blocked by default"; deny beats allow; matching is by domain/IP only ("URL paths are ignored"); always write-protected paths include `.cursor/*.json`, `.vscode/**`, `.git/hooks/**`, `.git/config`, `.cursorignore`; team-admin policies "can't be weakened by user or repo files". Under workspace read mode "only `~/.ssh/known_hosts` is readable from `~/.ssh`." — [Cursor docs: sandbox.json reference](https://cursor.com/docs/reference/sandbox)
- Run modes: Auto-review (recommended default as of Cursor 3.6; "the safest useful setup for most people"), Allowlist, Run Everything ("Every tool call runs automatically", no sandbox, no classifier); "Ask Every Time" deprecated in Cursor 3.5. "Auto-review is not a security boundary" and the classifier "can make mistakes". "If a sandboxed command fails on a sandbox restriction ... the agent can rerun it outside the sandbox. The classifier reviews that rerun." Team settings "take precedence over individual and project configuration"; blocking the Claude 4.5 Haiku classifier model disables Auto-review. — [Cursor docs: Run modes](https://cursor.com/docs/agent/security/run-modes)
- General security page: Run Modes are "best-effort guardrails rather than a hard security boundary"; `.cursorignore` blocks agent file access; all MCP connections and each tool call need approval unless allowlisted; workspace trust is disabled by default and can be enforced via MDM. — [Cursor docs: Agent security](https://cursor.com/docs/agent/security)

#### 1d. OpenAI Codex (docs now served from learn.chatgpt.com, fetched 9 Oct 2026)
- macOS sandbox "works out of the box using the built-in Seatbelt framework"; Windows native PowerShell runs use "the Windows sandbox"; Linux/WSL2 requires `bubblewrap` with a fallback helper needing unprivileged user namespaces. Modes: `read-only`, `workspace-write` ("the default low-friction mode for local work"), `danger-full-access` ("should be used only when you want the agent to act with full access"). Approval policies: `on-request` (asks "when it needs to go beyond that boundary") and `never`; "Codex and ChatGPT Work no longer support `untrusted` as a selectable approval policy." The sandbox "applies to spawned commands, not just to built-in file operations." — [Codex docs: Sandboxing](https://learn.chatgpt.com/docs/sandboxing)
- Network controls are experimental and off by default: `features.network_proxy.enabled` "Defaults to `false`; permission-profile domain rules are not enforced while the proxy is off"; `features.network_proxy.domains` "Unset by default, which means no external destinations are allowed until you add `allow` rules"; `allow_local_binding` defaults false; "App and connector traffic is not controlled by the sandboxed-command network proxy or its domain allowlist." Built-in permission profiles `:read-only`, `:workspace`, `:danger-full-access`. — [Codex docs: Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)

#### 1e. Windsurf (now "Devin Desktop"; docs.windsurf.com redirects to docs.devin.ai)
- Four auto-execution levels: Disabled, Allowlist Only, Auto, Turbo ("All commands are auto-executed immediately, except those in your deny list"). Allow/deny lists are prefix-matched command strings; "The denylist takes precedence over the allowlist." Admins set a maximum auto-execution level and team-wide lists in the Admin Portal. The page documents no OS-level sandbox, filesystem or network restriction — only a separate agent terminal (`zsh`/`bash`). — [Devin Desktop docs: Terminal](https://docs.devin.ai/desktop/terminal)

#### 1f. Devin (cloud agent)
- "Every Devin session requires a new VM"; VPC deployment runs the DevBox in the customer's VPC with the Brain in Cognition's Azure tenant; secrets are "decrypted at session start, loaded as environment variables, and then re-encrypted" and redacted in the UI; no egress allowlist is documented; Linux only. — [Devin docs: Enterprise VPC overview](https://docs.devin.ai/enterprise/vpc/overview)
- Secrets scopes: organization, personal, repo-specific, session-specific; Devin "supplies each value only to the tools that need it", binding it as an environment variable "when needed"; the docs do not state whether the model can see plaintext. — [Devin docs: Secrets](https://docs.devin.ai/product-guides/secrets)

#### 1g. Replit Agent
- "Agent is not able to modify the production database." Agent can edit the development database including deleting tables/columns; structural changes are applied to production at publish time; Helium databases offer checkpoint rollback, legacy Neon databases PITR; database removal "is irreversible after a retention period of 7 days." Development DBs moved to Replit's Helium infrastructure for new databases from 4 Dec 2025; shared legacy databases shut down 8 Jun 2026. — [Replit docs: Development and production databases](https://docs.replit.com/features/data-and-storage/development-and-production)
- Agent "creates checkpoints as it works, so you can roll back to any previous state"; Plan mode produces an approved task list before changes. — [Replit docs: Agent](https://docs.replit.com/replitai/agent)

#### 1h. MCP exposure (the host-side channel every sandbox leaves open)
- Lethal trifecta (16 Jun 2025): private data + untrusted content + external communication; "LLMs are unable to *reliably distinguish* the importance of instructions based on where they came from"; MCP "encourages users to mix and match tools from different sources"; the only safe approach is to "avoid that lethal trifecta combination entirely." — [Simon Willison: The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- General Analysis Supabase MCP attack (8 Jul 2025): Cursor + Supabase MCP running under `service_role` read a support ticket (submitted via the `anon` role) containing instructions addressed to "CLAUDE within cursor"; the agent read `integration_tokens` and posted them back into the ticket. Mitigations: `project_ref`, `read_only=true`, `features`; read-only "blocks the write-back step but still permits reads"; prompt-injection filters are supplementary and "cannot grant or restrict database permissions". — [General Analysis: Supabase MCP leak](https://www.generalanalysis.com/blog/supabase-mcp-blog)
- Supabase's current MCP guidance (page dated 8 Oct 2026): "Connect to a production project only when the task requires production evidence"; before connecting production enable `read_only=true` ("Execute all queries as a read-only Postgres user"), scope with `project_ref=<id>` (also disables account tools), restrict `features` (storage disabled by default); "Most MCP clients ask you to accept each tool call before it runs" — keep enabled; Supabase MCP "wraps SQL results with additional instructions to discourage LLMs from following" embedded commands, which "is not foolproof"; elicitations are "a guardrail, not a guarantee of human review or approval"; branching is experimental and paid. — [Supabase docs: MCP](https://supabase.com/docs/guides/getting-started/mcp)
- **Nuance vs original (line 261):** the original says Supabase "strongly discourages connecting its MCP to production". The current page's wording is conditional ("only when the task requires production evidence") plus read-only/scoped prerequisites; it does not contain the phrase "strongly discourage".
- MCP authorization spec (revision 2025-06-18): "Authorization is **OPTIONAL** for MCP implementations"; HTTP transports SHOULD conform; STDIO transports SHOULD NOT and "instead retrieve credentials from the environment"; OAuth 2.1 based; clients MUST send RFC 8707 `resource` indicators; servers MUST validate audience; "MCP servers **MUST NOT** accept or transit any other tokens" (token passthrough forbidden); confused-deputy warning for MCP proxies; authorization servers SHOULD issue short-lived tokens. Supabase's page links a newer revision dated 2026-07-28. — [MCP spec 2025-06-18: Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization); [Supabase docs: MCP](https://supabase.com/docs/guides/getting-started/mcp)
- Tool poisoning (Invariant Labs, 1 Apr 2025): hidden instructions in tool descriptions visible to the model but not the user (Cursor showed only a summarised tool name); demo exfiltrated `~/.cursor/mcp.json` and SSH keys via an injected `add` tool; "rug pull" (description changes after approval) and cross-server shadowing (a malicious server's description redirected a trusted `send_email` tool). Mitigations: show full descriptions, pin tool descriptions by hash, enforce dataflow boundaries between servers. — [Invariant Labs: MCP tool poisoning](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- Enterprise MCP gateways/registries:
  - Cloudflare MCP server portals (page updated 8 Oct 2026): one HTTP endpoint for up to 80 remote MCP servers behind Cloudflare Access/IdP; per-server Access policies; admins can disable individual tools/prompts or use an allowlist ("everything is hidden by default"); per-tool request logging with Logpush export (Enterprise); optional Gateway DLP; caveat: "blocked users can bypass this by using a server's direct URL"; only remote HTTP servers supported. — [Cloudflare One: MCP server portals](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/mcp-servers/mcp-portals/)
  - Docker MCP Gateway (page dated 25 Sep 2026): MCP servers run in containers with "restricted privileges, network access, and resource usage"; gateway injects credentials before forwarding; built-in logging and call tracing; `--profile` scoping; "MCP Gateway as part of Docker AI Governance is invite-only." — [Docker docs: MCP Gateway](https://docs.docker.com/ai/mcp-catalog-and-toolkit/mcp-gateway/)
  - Azure API Management (page dated 11 Sep 2026): expose REST APIs or external MCP servers as MCP tools; policies for rate limits, auth (Entra ID JWT, OAuth), IP filtering; Azure API Center "provides a private, enterprise MCP registry"; only MCP tools supported (not resources/prompts); GA/preview status not stated on page. — [Microsoft Learn: MCP servers in Azure API Management](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)

#### 1i. Rules-file / prompt-injection vectors
- Pillar Security "Rules File Backdoor" (18 Mar 2025): invisible Unicode (zero-width joiners, bidirectional markers) in `.cursor/rules` and Copilot instruction files; model inserted an attacker-sourced script tag and omitted it from chat; hidden characters stayed invisible in GitHub PR review. Vendor responses: Cursor (6 and 8 Mar 2025) said the risk "falls under users' responsibility" and "it is not a vulnerability on their side"; GitHub (12 Mar 2025) said "users are responsible for reviewing and accepting suggestions"; on 1 May 2025 GitHub added a warning "when a file's contents include hidden Unicode text on github.com." — [Pillar Security: Rules File Backdoor](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)
- Copilot coding agent now "filters hidden characters that might allow users to hide harmful instructions in comments or issue contents." — [GitHub Docs: Responsible use of Copilot coding agent](https://docs.github.com/en/copilot/responsible-use/copilot-coding-agent)
- Repository trust in Claude Code: project allow rules and marketplaces wait for folder trust; deny/ask rules apply regardless; hooks/MCP/`ANTHROPIC_BASE_URL` from repo settings were the three pre-trust execution paths fixed Aug 2025–Dec 2025 (see 1a). — [Claude Code: Example settings files](https://code.claude.com/docs/en/settings-example); [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files/)

#### 1j. OWASP Top 10 for Agentic Applications
- Published 9 Dec 2025 as "a globally peer-reviewed framework". — [OWASP GenAI Security Project: Agentic Top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)
- List: ASI01 Agent Goal Hijack; ASI02 Tool Misuse and Exploitation; ASI03 Identity and Privilege Abuse; ASI04 Agentic Supply Chain Vulnerabilities; ASI05 Unexpected Code Execution (RCE); ASI06 Memory & Context Poisoning; ASI07 Insecure Inter-Agent Communication; ASI08 Cascading Failures; ASI09 Human-Agent Trust Exploitation; ASI10 Rogue Agents. ASI03: agents "inherit credentials such as user sessions, API keys, and OAuth tokens, and traditional IAM doesn't separate what the user authorized from what the agent decides on its own"; mitigation "Issue short-lived, narrowly scoped tokens per task and cap permission boundaries using per-agent identities." ASI05: "When an agent can run shell commands, every prompt represents a potential path to compromise"; many agents by default "have the same permissions as the developer, with no isolation from sensitive resources or production databases"; mitigation "Require human approval for elevated runs; enforce role and action-based controls." — [Descope: OWASP Agentic Top 10 and identity](https://www.descope.com/blog/post/owasp-agentic-top-10-identity) (secondary summary of the OWASP document; the OWASP page itself did not render the list)

### Inferences
- Mapping to the audit's "control type" table: OS sandbox + proxy = runtime prevention for *shell commands only*; permission prompts, Bash deny rules, Cursor Auto-review classifier and Claude Code Auto mode = model-adjacent guidance/detection, each described by its vendor as not a security boundary; MCP servers, hooks and file tools sit outside both unless the whole agent process is containerised.
- PocketOS maps to ASI03 (inherited over-scoped credential readable from the filesystem) and SaaStr to ASI05/ASI03 (shell+DB access with developer-equivalent permissions). The General Analysis and Sentry cases map to ASI01 goal hijack via untrusted content delivered through an MCP tool.
- Every documented "allowlist" (Copilot recommended allowlist, Claude Code `allowedDomains` with `github.com`, Cursor defaults) necessarily includes hosts that accept uploads (registries, GitHub). A network allowlist therefore bounds *where* exfiltration can go, not *whether* it can happen; closing that requires either a push/upload-blocking proxy, read-only credentials on those hosts, or data minimisation on the host.

### Gaps
- Codex `workspace-write` network default: the fetched sandboxing page did not state whether network is disabled by default in that mode; the config reference confirms the domain-enforcing proxy is off by default. Not confirmed from primary source.
- Cursor: no primary page confirmed the current default on/off state of the sandbox across plans or Linux/Windows availability; forum posts cover macOS at launch (Oct 2025).
- Windsurf/Devin Desktop: no OS-level sandbox documented; absence in docs is not proof of absence in product.
- Devin: whether the model can read secret plaintext from the DevBox environment is not stated; no egress allowlist documented.
- OWASP ASI03/ASI05 text was taken from a vendor summary (Descope); the OWASP PDF itself was not parsed.

## Key Question 3: What is a minimal secure managed-settings baseline for Claude Code and Copilot in an enterprise (concrete keys/values)?

### Takeaway
For Claude Code, the vendor documents a managed-settings file (deployed at `/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`, or `C:\Program Files\ClaudeCode\managed-settings.json`, or via MDM/registry/claude.ai console) that can: force the sandbox on and fail-closed, remove the unsandboxed retry, lock the domain allowlist, deny reads of secret files, remove bypass mode, make managed permission rules and MCP allowlists the only ones that apply, pin plugin marketplaces, and pin login method/org. For Copilot coding agent, the controls are org-level toggles (firewall Enabled, recommended allowlist decision, custom allowlist, "Allow repository custom rules" off), MCP tool allowlists restricted to read-only tools, and secrets only via the `copilot` environment with `COPILOT_MCP_` prefixes. Anthropic explicitly says its example is "not a recommended policy", so the baseline below is assembled from documented keys, not a vendor recommendation.

### Cited Findings

**Claude Code: delivery mechanisms**
- File paths: macOS `/Library/Application Support/ClaudeCode/managed-settings.json`; Linux and WSL `/etc/claude-code/managed-settings.json`; Windows `C:\Program Files\ClaudeCode\managed-settings.json` ("Claude Code doesn't read the legacy Windows path `C:\ProgramData\ClaudeCode\managed-settings.json`"). Optional `managed-settings.d/` directory merged alphabetically; `managed-mcp.json` for managed MCP servers. — [Claude Code: Deploy managed settings](https://code.claude.com/docs/en/managed-settings)
- MDM: macOS configuration profile under the `com.anthropic.claudecode` managed preferences domain; Windows `HKLM\SOFTWARE\Policies\ClaudeCode` value `Settings` (`REG_SZ`/`REG_EXPAND_SZ`), re-checked every 30 minutes; HKCU variant; server-managed settings from the claude.ai console ("Only server-managed settings reach the cloud session"; console "can't target a group yet"). Verify with `/status` → "Enterprise managed settings (file)". — [Claude Code: Deploy managed settings](https://code.claude.com/docs/en/managed-settings); [Claude Code settings](https://code.claude.com/docs/en/settings)
- Precedence: managed > command line > project local > shared project > user; a few restrictive keys are honoured as stricter from any scope (`blockReadsOutsideWorkingDirectories: true`, `disableClaudeAiConnectors: true`). — [Claude Code settings](https://code.claude.com/docs/en/settings)

**Claude Code: documented lock semantics**
- "When managed settings set a Boolean key such as `enabled` or `failIfUnavailable`, Claude Code uses the managed value and ignores anything a developer sets locally. For array keys such as `allowRead`, Claude Code merges entries ... so a developer can append entries that widen the policy unless a lock covers that key." Locks: `allowManagedReadPathsOnly`, `allowManagedDomainsOnly`. Weakening keys to set `false` in managed settings: `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `network.allowAllUnixSockets`, `network.allowLocalBinding`, `allowAppleEvents`. Setting `allowUnsandboxedCommands: false` in managed settings makes the sandbox "admin-required", so repository settings that loosen it (including `excludedCommands`) are ignored. When managed settings configure `sandbox.filesystem` or a `credentials.files` deny entry, "only managed settings can set `filesystem.disabled`". — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Key kinds in managed sources: Lists (merged: `permissions.allow`, `hooks`, `sandbox.network.allowedDomains`, `deniedMcpServers`); Locks (strictest wins: `allowManagedHooksOnly`, `permissions.disableBypassPermissionsMode`); Restriction allowlists (taken whole from highest source: `availableModels`, `allowedMcpServers`, `strictKnownMarketplaces`). `allowManagedMcpServersOnly: true` in any admin source turns the MCP allowlist lock on (requires v2.1.273+). — [Claude Code: Deploy managed settings](https://code.claude.com/docs/en/managed-settings)
- The docs' quick-start managed example: `permissions.deny: ["Read(./.env)", "Read(./secrets/**)"]`, `permissions.disableBypassPermissionsMode: "disable"`, `allowManagedPermissionRulesOnly: true` ("makes Claude Code ignore permission rules from user, project, and local files and from `--allowedTools`"). — [Claude Code: Deploy managed settings](https://code.claude.com/docs/en/managed-settings)
- Fuller vendor example (explicitly "It isn't a recommended policy"): `forceLoginMethod: "claudeai"`, `forceLoginOrgUUID: [...]`, `availableModels` + `enforceAvailableModels: true`, `permissions.deny: ["Bash(curl *)", "Read(./.env)", "Read(./secrets/**)"]`, `disableBypassPermissionsMode: "disable"`, `allowManagedPermissionRulesOnly: true`, `allowedMcpServers: [{"serverUrl": "https://api.githubcopilot.com/*"}]` (matched by URL "since a user can name any server 'github'"; "every stdio server" is excluded when the list has only URL entries), `allowManagedMcpServersOnly: true`, `strictKnownMarketplaces: [{"source":"github","repo":"acme-corp/approved-plugins"}]`, `sandbox: {enabled: true, failIfUnavailable: true, allowUnsandboxedCommands: false, network: {allowedDomains: ["registry.npmjs.org","github.com"], allowManagedDomainsOnly: true}}`, `requiredMinimumVersion: "2.1.150"`, `cleanupPeriodDays: 7`. — [Claude Code: Example settings files](https://code.claude.com/docs/en/settings-example)
- Identity: `forceLoginMethod` and `forceLoginOrgUUID` restrict claude.ai logins to an org (Claude Code "exits at startup if the claude.ai credential in use belongs to an organization that isn't listed"); `allowedProviders` (v2.1.285+) restricts which inference providers a machine may use; `apiKeyHelper` supports short-lived tokens "fetched from a vault"; credentials stored in macOS Keychain or `~/.claude/.credentials.json` mode 0600. — [Claude Code: Authentication](https://code.claude.com/docs/en/iam)
- Credential protection keys: `sandbox.credentials.files` / `envVars` with `mode: "deny"` or `"mask"` (+ `injectHosts`); `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` for all subprocesses. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)

**Copilot coding agent: org-level controls**
- Org settings → Copilot → "Internet access": "Enable firewall" = Enabled; "recommended allowlist" = Enabled/Disabled/Let repositories decide; org custom allowlist entries cannot be removed by repos; "Allow repository custom rules" can be turned off. — [GitHub Docs: Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- MCP: configure `tools` allowlists per server (avoid `"*"`; prefer read-only tools); secrets only via `COPILOT_MCP_*` Agents secrets; default GitHub MCP token is read-only to the current repo. — [GitHub Docs: Extend coding agent with MCP](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/extend-coding-agent-with-mcp)
- Platform defaults that cannot be loosened by the agent: `copilot/` branches only, no default-branch push, Actions on agent PRs require write-user approval, secrets only from the `copilot` environment, 59-minute sessions. — [GitHub Docs: Responsible use](https://docs.github.com/en/copilot/responsible-use/copilot-coding-agent); [GitHub Docs: About coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- CI-side hardening recommended after the `claude-code-action` bypass (CVE-2025-66032): pin third-party actions to commit SHAs; limit `id-token: write` and `contents: write`; "Run AI agents in workflows without write credentials"; environment protection rules for human approval; egress filtering on runners. — [CSA: AI Agent Prompt Injection, the new CI/CD supply chain threat](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)

### Inferences
- A minimal Claude Code baseline assembled from documented keys (my synthesis; every key is documented above but the combination is not a vendor recommendation):
  - `sandbox.enabled: true`, `sandbox.failIfUnavailable: true`, `sandbox.allowUnsandboxedCommands: false` (admin-required sandbox), `sandbox.network.allowedDomains: [<internal registry proxy>, <git host>]`, `sandbox.network.allowManagedDomainsOnly: true`, `sandbox.allowManagedReadPathsOnly: true`, `sandbox.enableWeakerNestedSandbox: false`, `sandbox.enableWeakerNetworkIsolation: false`, `sandbox.network.allowAllUnixSockets: false`, `sandbox.network.allowLocalBinding: false`, `sandbox.credentials.files: [~/.ssh, ~/.aws, ~/.config/gh, ~/.netrc, ~/.docker, ~/.gnupg] mode deny`, `sandbox.credentials.envVars` deny/mask for cloud and registry tokens.
  - `permissions.deny: ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Read(~/.ssh/**)", "Read(~/.aws/**)", "WebFetch(domain:*)"]` (mirror every `denyRead` path as a `Read(...)` deny because the Read tool ignores the sandbox), `permissions.disableBypassPermissionsMode: "disable"`, `permissions.blockReadsOutsideWorkingDirectories: true`, `allowManagedPermissionRulesOnly: true`, `permissions.ask: ["Bash(dangerouslyDisableSandbox:true)"]` is moot once retries are disabled but documents intent.
  - `allowedMcpServers` by `serverUrl`, `allowManagedMcpServersOnly: true`, `deniedMcpServers` for known-risky servers, `allowManagedHooksOnly: true`, `strictKnownMarketplaces`, `forceLoginMethod`, `forceLoginOrgUUID`, `allowedProviders`, `requiredMinimumVersion` ≥ 2.1.285 (so strict-mode precedence and MCP lock apply; and far above the CVE fix versions 1.0.111 / 2.0.65), `cleanupPeriodDays` per retention policy, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` in managed `env`.
  - Residual: MCP servers, hooks and `apiKeyHelper` still run with full host access; the vendor's own guidance for unattended or high-risk use is to run the whole process in a container/VM/sandbox-runtime.
- Copilot baseline (my synthesis from documented toggles): firewall Enabled (locked at org), recommended allowlist Disabled with an org custom allowlist pointing to an internal registry proxy and required GitHub hosts, "Allow repository custom rules" off, MCP servers limited to read-only `tools` allowlists, no `COPILOT_MCP_` secrets with write scopes, environment protection rules on `copilot` environment, SHA-pinned actions.

### Gaps
- Anthropic publishes no "recommended baseline"; the example file is explicitly not one. The composed baseline above is inference.
- Copilot docs do not describe enterprise-level (above org) firewall policy; whether an enterprise can lock all orgs was not confirmed.
- Whether `WebFetch(domain:*)` as a deny rule is honoured exactly as written was asserted by the Claude Code Camp post, not confirmed in vendor docs.

## Key Question 4: What backup architecture would have survived PocketOS, and what does it cost in rough terms?

### Takeaway
PocketOS lost production and its co-located backups to one over-scoped token in a single provider account; it recovered only because Railway held separate disaster backups. An architecture that survives that class of event needs (1) a copy outside the identity domain the agent's credentials can reach, (2) storage-enforced immutability that no credential in the primary account can shorten (AWS logically air-gapped vault with always-on compliance Vault Lock; Azure immutable vault "Enabled and locked" plus enforced soft delete; GCP backup vault enforced retention; object-lock compliance mode on B2/S3-compatible targets), (3) optional but valuable cross-account/cross-org restore paths (AWS RAM sharing, optional MPA; Azure Resource Guard in a different tenant), and (4) tested restores with measured RPO/RTO. Costs are dominated by storage at roughly USD 0.05–0.06 per GB-month on AWS Backup (LAG vault ~USD 0.0575/GB-month in eu-west-1), plus restore and cross-region transfer per GB; MPA itself has no additional charge.

### Cited Findings

**AWS Backup**
- Logically air-gapped vault: "stores its backups in an AWS Backup service owned account"; "each vault is equipped with AWS Backup Vault Lock's compliance mode" / "Is always locked with a vault lock in compliance mode"; minimum retention "The minimum value allowed is `7` days"; encrypted with AWS-owned key by default (recommended) or a customer-managed KMS key chosen at creation only; "Can optionally be shared across accounts using AWS RAM" with individual account IDs only ("cannot be shared with an entire organization or with organizational units"); recipients can view or restore "but not to create a copy"; unencrypted Aurora/DocumentDB/Neptune unsupported; not-fully-managed resources must be encrypted with a customer-managed key; all charges billed under "AWS Backup". — [AWS Backup: Logically air-gapped vaults](https://docs.aws.amazon.com/aws-backup/latest/devguide/logicallyairgappedvault.html)
- MPA is optional: "You can integrate your logically air-gapped vaults with Multi-party approval (MPA) to enable recovery of backups in the vaults even if the vault-owning account is inaccessible." Requires two AWS Organizations (primary + recovery), IAM Identity Center in the recovery org, an approval team shared via RAM, an SCP on the primary org, and the team policy `arn:aws:mpa::aws:policy/backup.amazonaws.com/CreateRestoreAccessVault`; a "restore access backup vault" mirrors contents and "cannot change or delete them"; approval-team resources exist only in us-east-1; "no additional MPA cost, but storage and cross-Region transfer charges apply." — [AWS Backup: Multi-party approval](https://docs.aws.amazon.com/aws-backup/latest/devguide/multipartyapproval.html)
- **Correction to original (lines 326–330), confirming audit A7:** MPA is an optional, separately configured integration (two organisations, Identity Center, approval team); it is not required for every restore from a logically air-gapped vault. The original's "Multi-party approval for restore, even if the owning account is compromised" should read "optional MPA integration enables restore by a separate recovery account even if the owning account is inaccessible."
- Vault Lock: governance mode removable by IAM-privileged users; compliance mode requires a grace period of at least 3 days (`ChangeableForDays` 3–36,500) after which "the vault and its lock are immutable and cannot be changed or deleted by any user or by AWS"; deletion of recovery points by "any user (including the root user)" is denied; `MinRetentionDays`/`MaxRetentionDays` apply to new jobs only; on account closure AWS suspends for 90 days then deletes vault contents "even if a vault lock was in place"; deny `ec2:DisableImage` to prevent AMI-disable blocking restores. — [AWS Backup: Vault Lock](https://docs.aws.amazon.com/aws-backup/latest/devguide/vault-lock.html)
- Pricing (from worked examples on the pricing page): warm backup storage USD 0.05/GB-month (EFS and EBS, us-east-1); logically air-gapped vault storage USD 0.0575/GB-month (eu-west-1 example; no us-east-1 figure shown); restore USD 0.02/GB (EFS warm) and USD 0.03/GB (EBS file-level); cross-Region transfer USD 0.02/GB (EBS) and USD 0.04/GB (EFS) from us-east-1; restore testing USD 1.50 per recovery point evaluated. — [AWS Backup pricing](https://aws.amazon.com/backup/pricing/)

**Azure Backup**
- Immutable vault states: Disabled; Enabled (reversible); "Enabled and locked: WORM storage is enabled, and the setting can't be disabled. Locking is irreversible." Blocks stop-protection-with-delete, policy changes that reduce retention, and switching to lower-retention policies; immutability can follow policy retention or a fixed duration; supported on Recovery Services vaults and Backup vaults; page dated 9–10 Sep 2026. — [Microsoft Learn: Immutable vault concept](https://learn.microsoft.com/en-us/azure/backup/backup-azure-immutable-vault-concept)
- Secure by default soft delete: enforced and "eliminates the need to disable soft delete under any circumstances"; default 14 days at no extra cost, configurable 14–180 days; GA for Recovery Services vaults in all public regions and national clouds, GA for Backup vaults in three regions and preview elsewhere (page last updated 14 Aug 2026; the page itself contains inconsistent preview/GA statements). — [Microsoft Learn: Secure by default with soft delete](https://learn.microsoft.com/en-us/azure/backup/secure-by-default)
- Multi-user authorisation (Resource Guard) is explicitly configured by the backup admin (not default); mandatory protected operations include "Disable soft delete or security features" and "Remove MUA protection"; optional ones include "Delete protection" and "Modify policy" to reduce retention; Resource Guard placement "Different tenants" gives "Maximum" isolation; the backup admin must not hold Contributor/Backup MUA Admin/Operator on Resource Guard. — [Microsoft Learn: Multi-user authorization concept](https://learn.microsoft.com/en-us/azure/backup/multi-user-authorization-concept)

**Google Cloud Backup and DR**
- Backup vault is "a Google-managed regional resource that provides isolated, immutable, and indelible storage for backups"; minimum enforced retention "between 1 day and 99 years"; "No backup can be deleted before this time passes"; before the effective date the minimum can be adjusted up or down; "After the effective date, no one (not even a Project Owner) can decrease the retention period"; backups "cannot be manually deleted by you, any other user, or Google until your specified duration has passed"; supports Compute Engine, Filestore, Cloud SQL, AlloyDB (console) and VMware Engine/Oracle/SQL Server (appliance); access restriction setting is permanent; "Starting November 1, 2026, Backup and DR will automatically apply a project-level lien to any project containing a backup vault" with enforced-retention backups. — [Google Cloud: Backup vault concepts](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-vault)

**Object lock on commodity storage**
- Backblaze B2 Object Lock: governance retention "can be modified or overridden by clients with appropriate app key capabilities"; compliance retention "cannot be removed by any user" (dates can only be extended); legal hold independent; "Once Object Lock is enabled on a bucket, it cannot be disabled"; no extra charge beyond normal storage. — [Backblaze docs: Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock)
- pgBackRest supports S3-, Azure-, GCS-compatible and SFTP repositories; it has no immutability of its own and recommends enabling storage versioning and says "it may be useful to enable object locking for S3 and soft delete for GCS or Azure"; its sample S3 policy grants `s3:DeleteObject`, so expiry needs delete permission. — [pgBackRest User Guide](https://pgbackrest.org/user-guide.html)

**Dev/prod separation and database versioning (prevent the destructive write reaching production in the first place)**
- Replit: "Agent is not able to modify the production database." — [Replit docs](https://docs.replit.com/features/data-and-storage/development-and-production)
- Neon: take snapshots at "Start of each agent session" and "Before database schema changes"; restore with `finalize_restore: true` preserves "the original, stable connection string" though "the branch ID changes"; "Snapshot storage is billed at $0.09/GB-month"; Free plan 1 manual snapshot, paid plans 100 (scheduled snapshots don't count). — [Neon docs: AI database versioning](https://neon.com/docs/ai/ai-database-versioning)
- Neon anonymized branches (Beta): new branch with parent schema and data, masked statically via PostgreSQL Anonymizer; "The parent branch data remains unchanged"; cannot reset/restore the anonymized branch; console branches auto-delete after 1 day by default. — [Neon docs: Data anonymization](https://neon.com/docs/workflows/data-anonymization)
- Supabase branching: branches are "data-less by default" (no production data or storage objects), with seed files or "Include data" opt-in; preview branches auto-deleted on PR close; persistent branches for staging; no data masking documented; branching experimental and paid. — [Supabase docs: Branching](https://supabase.com/docs/guides/deployment/branching); [Supabase docs: MCP](https://supabase.com/docs/guides/getting-started/mcp)
- PlanetScale Postgres: development branches on `PS-DEV` instances from USD 5/month; "Branches page" creates empty branches, "Backup restore" creates a branch with schema and data from a backup; "The docs recommend against using production data in development environments"; "Only Organization Administrators and Database Administrators can delete production branches"; no deploy requests and "no automated way to merge schema changes between branches" for Postgres. — [PlanetScale docs: Postgres branching](https://planetscale.com/docs/postgres/branching)

**Credential brokering (keeps the destructive credential out of the agent's reach)**
- Vercel OIDC Federation "available on all plans"; build token in `VERCEL_OIDC_TOKEN`; function token in `x-vercel-oidc-token` header, reused up to 90 minutes with a 2-hour TTL; team issuer mode recommended (`https://oidc.vercel.com/acme`); cloud roles can be scoped per project/environment; page last updated 4 Aug 2026. — [Vercel docs: OIDC Federation](https://vercel.com/docs/oidc)
- GitHub Actions OIDC: each job gets a token "only valid for a single job"; claims include `sub` (e.g. `repo:octo-org/octo-repo:environment:prod`), `repository`, `ref`, `environment`, `job_workflow_ref`; repositories created after 15 Jul 2026 use an immutable subject format with owner/repo IDs. — [GitHub Docs: OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect)
- Cloudflare Outbound Workers (Workers for Platforms; page updated 21 Apr 2026): intercept every `fetch()` from user Workers; use cases include "Allow and block lists for hostnames" and "Adding authentication to your APIs so end developers don't need credentials"; when enabled, user Workers cannot use `connect()` for raw TCP; Durable Object fetches and mTLS bindings are not intercepted. — [Cloudflare docs: Outbound Workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)
- Claude Code's `sandbox.credentials` `mask` + `injectHosts` substitutes the real secret only on allowed hosts (e.g. `GH_TOKEN` on `api.github.com`), so the model and shell see a placeholder. — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)

### Inferences
- Architecture that would have survived PocketOS (my synthesis): production data on a platform where the agent's credential is environment-scoped (or absent); a daily logical backup (pgBackRest/WAL-G or provider snapshot export) pushed by a *separate* identity to an immutable target in a *separate* account/tenant/org (AWS LAG vault + optional RAM share to a recovery account, or Azure Backup vault locked + Resource Guard in another tenant, or GCP backup vault with enforced retention, or B2/S3 compliance-mode object lock); enforced minimum retention ≥ 7 days (AWS LAG minimum) and ideally 30+; a quarterly restore drill with `restore testing` (AWS charges USD 1.50 per recovery point tested) producing measured RPO/RTO. PocketOS's own newest backup was months old (per original report, line 50), which means the restore-drill gap, not just the storage layout, was a root cause.
- Rough cost (my arithmetic from the pricing figures above): for a 200 GB database with 30 daily incremental-aware recovery points averaging 400 GB stored in an AWS LAG vault at USD 0.0575/GB-month ≈ USD 23/month, plus one full cross-region copy of 200 GB/month at USD 0.02/GB ≈ USD 4, plus monthly restore testing of one recovery point USD 1.50 and USD 0.02–0.03/GB restored ≈ USD 4–6. Order of magnitude USD 30–40/month for an air-gapped, compliance-locked copy of a PocketOS-sized dataset; MPA adds nothing but organisational setup. Neon snapshots at USD 0.09/GB-month are roughly 1.5–2× AWS Backup warm storage but are in-platform and do not leave Neon's identity domain.
- Provider-internal "grace period" soft deletes (Railway two days; Replit DB 7 days; Azure soft delete 14 days) protect against a single destructive call but not against a credential that can also purge or wait out the window; only locked immutability with retention does.

### Gaps
- No us-east-1 price for the logically air-gapped vault was shown on the pricing page text fetched; the USD 0.0575 figure is the eu-west-1 example.
- Wasabi object-lock documentation fetch failed; Wasabi semantics are not cited.
- WAL-G documentation was not fetched; immutability semantics assumed equivalent to pgBackRest (storage-layer).
- "Database guardrail proxies" (SQL-aware proxies that block destructive statements) were not researched in this pass.
- PocketOS's RPO/RTO and the age of its own last backup were not in the Register article fetched (the original report cites "three months old"; not re-verified here).

## Key Question 5: Are there 2026 incidents of agents exfiltrating secrets via MCP or prompt injection in the wild?

### Takeaway
As of 9 October 2026 I found no primary-source confirmation of an in-the-wild incident in which a coding agent exfiltrated secrets via MCP. The 2026 record consists of (a) high-fidelity researcher demonstrations with disclosed vendor responses — Sentry MCP "agentjacking" (Tenet Security, June 2026; Sentry declined a root-cause fix) and the `claude-code-action` permission bypass CVE-2025-66032 (disclosed 1 Jun 2026, fixed within four days) — (b) one related CI case the CSA describes as exploited in the wild (Clinejection), and (c) non-agent supply-chain worms (Shai-Hulud) and one confirmed malicious slopsquat package (`unused-imports`) that are relevant because agents install packages autonomously.

### Cited Findings
- Sentry MCP agentjacking (CSA note 12 Jun 2026; Tenet Security disclosed to Sentry 3 Jun 2026): attacker needs only a public write-only Sentry DSN; injected error events were read by Claude Code, Cursor and Codex via the Sentry MCP, which "did not distinguish them from legitimate errors"; "85% exploitation success rate"; payload recovered environment variables, AWS credentials, GitHub/GitLab OAuth tokens, npm and Docker credentials, Kubernetes and CI/CD secrets; "at least 2,388 organizations had injectable Sentry DSNs"; attack evaded EDR/WAF/IAM/VPN because it used the developer's legitimate credentials. Status: "proof-of-concept research and controlled testing, not confirmed active exploitation at scale". Sentry "declined a root-cause fix, calling the issue 'technically not defensible' at the platform level" and added a content filter for the specific payload string. — [CSA: Agentjacking — MCP injection hijacks AI coding agents](https://labs.cloudsecurityalliance.org/research/csa-research-note-agentjacking-mcp-sentry-injection-20260612/)
- `claude-code-action` bypass CVE-2025-66032 / GHSA-xq4m-mc3c-vvg3 (CVSS 4.0 7.8): `checkWritePermissions` trusted any actor name ending in "[bot]", so a malicious GitHub App could inject prompts via issues; the chain could read environment variables including OIDC token request values exchangeable for a write-capable installation token. Reported 12 Jan 2026 by RyotaK (GMO Flatt Security), publicly disclosed 1 Jun 2026; Anthropic fixed "within four days" (human-actor check, workflow run summary disabled by default, `gh` wrapper, env-var scrubbing); fixed in `claude-code-action` v1.0.94 and `@anthropic-ai/claude-code` v1.0.93; USD 3,800 + 1,000 bounty. Presented as a demonstration, not in-the-wild. The related "Clinejection" incident "was exploited in the wild" and "Comment and Control" research stole `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, write-enabled `GITHUB_TOKEN` and Copilot tokens across Claude Code, Gemini CLI and Copilot agent. — [CSA: AI Agent Prompt Injection, the new CI/CD supply chain threat](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)
- Supabase MCP demonstration (2025) and its 6 Sep 2026 re-check: "the demonstration was not rerun" and no Supabase response is recorded. — [General Analysis](https://www.generalanalysis.com/blog/supabase-mcp-blog)
- Shai-Hulud npm worm: first wave September 2025 "Over 180 packages"; second wave ("Sha1-Hulud: The Second Coming", 24 Nov 2025) "525+ packages, with about 132 million monthly downloads" including `@zapier/*`, `@posthog/*`, `@postman/*` (including an MCP server package), `@asyncapi/*`; `preinstall` runs `node setup_bun.js`; TruffleHog plus filesystem/env scanning harvests AWS/GCP/Azure keys, npm and GitHub tokens; self-propagates by republishing the maintainer's packages; exfiltrates to public GitHub repos (~27,400 repos); if the GitHub token has `workflows` scope it installs a self-hosted Actions runner and a `discussion.yaml` workflow for persistent RCE. — [Semgrep: Sha1-Hulud, the second coming](https://semgrep.dev/blog/2025/digging-for-secrets-sha1-hulud-the-second-coming-of-the-npm-worm)
- Slopsquatting evidence (hallucination numbers vs exploitation):
  - Spracklen et al., USENIX Security 2025 (Distinguished Paper): 576,000 code samples, 16 models, two languages; commercial models average "at least 5.2%" hallucinated packages, open-source "at least 21.7%"; 205,474 unique hallucinated names. — [USENIX Security '25: We Have a Package for You!](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen)
  - CSA research note (19 Apr 2026) adds the 19.7% any-hallucination rate (440,445 of 2.23M samples), 43% of names recurring on every rerun, taxonomy (conflations 38%, typo variants 13%, pure fabrications 51%). — [CSA: Slopsquatting research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419-csa/)
  - 2026 re-evaluation (Churilov, arXiv 2605.17062, v3 9 Aug 2026): rates across Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro, DeepSeek V3.2 range 4.62%–6.10% on 199,845 paired prompts; 127 names hallucinated identically by all five models, 53 still registrable (41 PyPI, 12 npm) and disclosed to PyPI and Socket; "None reported" for in-the-wild attacks. — [arXiv 2605.17062](https://arxiv.org/abs/2605.17062)
  - In-the-wild cases (Aikido, 20 Feb 2026; CSA): `unused-imports` (npm) — "a real malicious package and 'potentially an intentional slopsquatting attack'", security-held by npm, ~233 weekly downloads as of early Feb 2026 (attacker intent unproven); `react-codeshift` (npm) — unclaimed hallucinated name spread via LLM-generated agent skills to 237 repositories, claimed defensively by Aikido in Jan 2026; `huggingface-cli` (PyPI, 2024) — benign PoC with 30,000+ downloads after Alibaba copied the install command into a README. — [Aikido: Slopsquatting](https://www.aikido.dev/blog/slopsquatting-ai-package-hallucination-attacks); [CSA: Slopsquatting research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419-csa/)
  - **Correction to original (line 65):** "as of July 2026, no in-the-wild attack had been reported" is contradicted by Aikido/CSA's `unused-imports` case (malicious, security-held, Feb 2026), though intent is unproven. Keep hallucination rates and exploitation counts separate as the audit (C7) asks.
- Socket Firewall (30 Sep 2025): free `sfw` wrapper for npm/yarn/pnpm, pip/uv, cargo; blocks known malicious packages including transitive ones via an ephemeral proxy; "possible AI-detected malware only triggers a warning"; unknown/unscanned packages are not blocked in Free; Enterprise adds policy, custom registries, allowlists. — [Socket: Introducing Socket Firewall](https://socket.dev/blog/introducing-socket-firewall)
- Controls recommended by CSA for agent-driven installs: restrict agents "with package-install capability to an allowlist, routing other installs to human review"; "Pin lockfiles and verify hashes in all CI/CD pipelines"; flag packages registered in the last 30–90 days; SBOMs for AI-generated code. — [CSA: Slopsquatting research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419-csa/)

### Inferences
- The absence of a confirmed in-the-wild MCP exfiltration incident is consistent with low detectability rather than low exposure: the Sentry case shows the attack uses legitimate developer credentials and evades perimeter tooling, so a successful exploitation would look like normal developer activity. The audit's caution (C7) that absence of reports is weak evidence of absence applies here with force.
- Shai-Hulud is the in-the-wild counterpart of the agent threat model: a `preinstall` script that harvests whatever credentials the installing process can read. An agent that runs `npm install` inside a sandbox whose reads cover `~/.aws`, `~/.npmrc` and the environment (the Claude Code default) hands such a worm the same material a developer shell would.

### Gaps
- No incident was found in which a *coding agent* was the confirmed vector for secret exfiltration in production; all 2026 agent cases are disclosed research or near-miss CI misconfigurations.
- The CSA's statement that Clinejection "was exploited in the wild" was not traced to its primary source (Adnan Khan) in this pass.
- Internal registry proxies (Artifactory/JFrog Curation, Nexus, Verdaccio) were not confirmed from primary docs (the JFrog fetch failed); their role as the enforcement point for an agent egress allowlist is inference supported by CSA's "allowlist" recommendation and Socket Firewall's documented limits.
