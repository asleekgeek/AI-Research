# Boundaries, not prompts, contain vibe-coded leaks

Data leaks from vibe-coded applications and AI coding agents almost never come from clever-but-wrong generated code; they come from four structural conditions that the generated code cannot see and the builder does not know exist. In 20 incidents and seven large-scale scans verified against primary sources for this paper, the demonstrated capability was row-level read or write through an internet-reachable data API with missing or inverted authorisation, unauthenticated publishing by default, platform-side authorisation bugs, or an agent holding an over-scoped credential that reached production and its backups together. The original research report this paper reviews had the thesis right and roughly thirty specifics wrong or over-compressed; the independent audit that followed caught most of the headline errors but missed at least six, including that Supabase's 30 October 2026 grant change leaves RPC `EXECUTE` defaults untouched, that the certificate-transparency blind spot it listed as an open question is now empirically verified for all five builder platforms, and that an in-the-wild malicious slopsquat package existed before the audit was written. The corrected practitioner position is that controls bind only at four boundaries the code does not own: builder identity and workspace, published-app ingress, the data and connector API, and the agent execution plane. At each boundary the paper gives the exact semantics, the dated vendor defaults, the behavioural test that proves the control works, and the documented bypass. Generation-time controls such as prompts, rules files and AI review measurably shift the correctness-versus-security trade-off but never cap damage; on the one exploit-confirmed benchmark of real deployed vibe-coded apps, **182 of 200 (91.0%)** carried at least one confirmed vulnerability and Broken Access Control appeared in **64.0%** of them ([Deng, Fan and Meng, arXiv 2606.23130v4](https://arxiv.org/html/2606.23130v4)). The legal layer is technology-neutral and already reaches every failure mode, but GDPR notification is risk-thresholded rather than automatic, a vibe-coded CRUD tool is not an "AI system" under the AI Act, and NIS2 and DORA duties attach only to in-scope entities and, for DORA's strongest clauses, only to critical or important functions. Everything quantitative or evaluative below carries an evidence-confidence tag; the tiered model, the rollout plan and the KPIs marked as proposals are the authors' design, not measured practice.

## 0. How to read this paper

**Date of record.** All vendor defaults, prices, regulatory statuses and incident facts are as verified on 8–9 October 2026. Vendor documentation in this market changes monthly; every default below should be re-checked in a trial tenant before procurement.

**Evidence-confidence legend.** Every quantitative claim and every control verdict carries one of six tags.

| Tag | Meaning |
|---|---|
| **[CP]** Confirmed-primary | Read directly from the primary source: vendor documentation or changelog, regulation text, EDPB guideline, CVE record, court filing, or the researcher's own write-up. |
| **[VR]** Vendor-reported | A vendor's own research, telemetry or evaluation, read at the vendor's page; figures are the vendor's and carry the vendor's sampling and commercial incentives. |
| **[RR]** Researcher-reported | Independent academic or researcher work read at source; independent replication is noted where it exists (it rarely does). |
| **[PO]** Press-only | Reputable press quoting named parties; the primary source was not located. |
| **[INF]** Author-inference | A conclusion the authors draw from cited evidence; reasoning is shown. |
| **[PROP]** Proposal | A design, threshold, tier, KPI or rollout step the authors recommend; no external validation claimed. |

**Structure.** Sections 1 and 2 review the original report and the audit. Sections 3 to 11 are the practitioner guidance. The appendix holds machine-readable tables for a presentation build.

**Terminology.** "Builder" means an AI app builder (Lovable, Replit, Base44, Bolt, v0). "Agent" means a coding agent (Claude Code, Cursor, GitHub Copilot coding agent, Codex, Gemini CLI, Kiro, Antigravity, Devin). "BaaS" means a backend-as-a-service reached directly from the browser (Supabase, Firebase, Neon Data API, Convex, PocketBase, Appwrite). Row-level security is "RLS". Monetary figures are USD list prices as published by vendors, EUR where the law states them; no currency conversion is applied.

## 1. Review of the original report: what holds, what needed correction

### 1.1 What holds

The original report's architecture survives intact. Its four failure modes (client-reachable data API with broken authorisation, public-by-default publishing, platform-side bugs, agent destruction with co-located backups) are confirmed by the full incident ledger in section 3, and no incident found in the May–October 2026 extension required a fifth category **[INF]**. Its central claim that controls must be enforced by a layer the generated code does not own is supported by every post-incident vendor remediation, all of which changed defaults or blast radius rather than code correctness: Replit's dev/prod database separation ([Fortune](https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure/)) **[PO]**, Railway's grace period on the API `volumeDelete` mutation ([Railway Central Station](https://station.railway.com/questions/any-changes-to-protect-database-backups-3b31d4d3)) **[CP]**, Supabase's explicit-grants default ([Supabase changelog 45329](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)) **[CP]**, and Lovable's private-by-default projects ([Lovable](https://lovable.dev/blog/our-response-to-the-april-2026-incident)) **[CP]**.

Statements that fresh primary-source research confirms verbatim or near-verbatim **[CP]**: the Base44 `auth/register` and `auth/verify-otp` mechanism and sub-24-hour fix ([Wiz](https://www.wiz.io/blog/critical-vulnerability-base44)); Moltbook's four remediation rounds in roughly three hours ([Wiz](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)); the Supabase 30 October 2026 date and the grants-versus-RLS distinction; that Vercel Authentication admits Vercel accounts, not the workforce IdP ([Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication)); that Cloudflare Access and Google IAP fail open unless the origin validates the proxy's token; every Claude Code sandbox seam it listed, now stated in Anthropic's own documentation ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)); the Lovable DPA's independent-controller carve-out and no-audit-right position ([Lovable DPA](https://lovable.dev/data-processing-agreement)); the AI Omnibus dates; the Tea attribution caution ([Simon Willison](https://simonwillison.net/2025/Jul/26/official-statement-from-tea/)); and the absence of any DPA enforcement decision on a vibe-coded app as of October 2026 **[INF]**.

1. **A3 omitted RPC.** The audit listed "security-definer functions, public views and unsafe RPC endpoints" as needing independent inspection but did not state that the 30 October change leaves function `EXECUTE` defaults untouched, which is the specific reason an agent-created RPC can remain anonymously callable in a project that believes itself "secure by default" **[CP]**/**[INF]**. 2. **Wildcard certificates.** Listed as a discussion topic (G, "Discovery"); now empirically verified for all five platforms, with the consequence that EASM attribution by certificate name or netblock cannot work for platform subdomains (section 4.6) **[CP]**.
3. **Slopsquatting.** The `unused-imports` case (Aikido, 20 Feb 2026) predates the audit; the audit's C7 should have said "one confirmed malicious package, intent probable, impact unquantified" **[VR]**.
4. **NCSC attribution.** Not caught **[CP]**.
5. **Colorado.** The audit's US coverage was limited to CCPA; the Colorado AI Act's repeal and replacement (14 May 2026) was five months old at audit date **[CP]**.

## 3. Four failure modes and the verified incident ledger

### 3.1 The four failure modes, restated precisely

**Failure mode 1 — broken authorisation on an internet-reachable data API.** The browser holds an intentionally public key and talks to PostgREST, Firebase or an equivalent. Exposure is decided by grants (may this role touch the table at all), RLS (which rows), column privileges, view and function ownership, and the logic of each policy. The key is not the defect; in every incident of this class the primary source says so **[CP]**. The characteristic defects are: no RLS; RLS with a permissive `USING (true)` policy; `TO authenticated` with no tenant predicate (authentication without authorisation); inverted logic (the EdTech RPC that "blocks the people it should allow and allows the people it should block" ([The Register](https://theregister.com/2026/02/27/lovable_app_vulnerabilities)) **[PO]**); and `SECURITY DEFINER` functions or owner-privileged views that bypass RLS silently ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security)) **[CP]**.

**Failure mode 2 — public-by-default publishing.** Not a code defect. The platform publishes to the open internet unless the builder changes a setting; the app is indexed; nobody in the organisation knows it exists. The RedAccess sweep is the canonical case and the vendors' reply ("a public app is not a breach") is technically correct and is the point ([Axios](https://www.axios.com/2026/05/07/loveable-replit-vibe-coding-privacy)) **[PO]**.

**Failure mode 3 — platform-side authorisation bugs.** Base44's unauthenticated registration endpoints and Lovable's February–April 2026 ownership-check regression share one root cause, authentication without object-level authorisation, and no app-level control could have helped **[CP]**/**[INF]**. Chat histories, prompts and source trees are data stores held by the platform.

**Failure mode 4 — agent credential reach.** An agent holding a credential that can mutate production, delete a volume or run `terraform destroy` does so, usually after a context mismatch, sometimes against explicit instructions. The constant across Replit, Cursor/Claude, Claude Code, Kiro and Antigravity incidents is credential reach, not model vendor **[INF]**. Where backups live in the same identity domain as the credential, they go too.

## 4. Four security boundaries and the controls at each

### 4.1 The boundary model

A vibe-coded deployment crosses four independent trust boundaries. Conflating them produces both false assurance (an identity-aware proxy on the UI that leaves the data API open) and false alarm (a publishable key in a bundle treated as a leaked secret). Each boundary has its own question, its own enforcement locus and its own test.

| Boundary | Core question | Enforcement locus | Correct test |
|---|---|---|---|
| B1 Builder identity and workspace | Who may create projects, connect data sources, publish externally, download code? | Builder tenant admin policy; IdP via SSO/SCIM | Attempt each action as a non-admin member; attempt from a personal account; export the inventory |
| B2 Published-app ingress | Who can load the app and call its server routes, through every origin? | Platform deployment protection, identity-aware proxy, app-level auth | Anonymous requests to canonical domain, platform subdomain, preview URLs, bypass headers |
| B3 Data and connector API | What may a principal read or change, through every surface? | Database grants, RLS, column privileges, function and view ownership; BFF authorisation; connector scopes | Anonymous, same-tenant and cross-tenant requests against REST, GraphQL, RPC and Storage, asserting on rows returned and SQLSTATE |
| B4 Agent execution plane | What can the coding agent read, install, transmit or destroy? | OS sandbox, egress proxy, credential scope and placement, MCP tool allowlists, dev/prod separation, backup isolation | Search the agent's reachable filesystem, environment and tools for production credentials; attempt a destructive call; restore from an isolated copy |

The audit's observation holds: a Cloudflare Access-protected HTML page with a separately reachable Supabase API is two boundaries, and "the public API is not automatically insecure if it enforces properly designed grants and RLS", while "a BFF that proxies through an unrestricted service-role credential is not automatically safe" **[INF]**.

### 4.3 Boundary B2: published-app ingress

#### 4.3.1 Identity-aware proxies and origin validation

All four mainstream IAPs depend on the origin being unreachable except through the proxy, or on the origin validating a signed assertion. Cloudflare: "To secure your origin, you must validate the application token issued by Cloudflare Access"; publicly routable origins must protect the origin IP by other means ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-public-app/)) **[CP]**. Google IAP: apps must "use signed headers"; on Compute Engine or GKE anyone reaching the serving port bypasses IAP; on Cloud Run the auto-assigned `run.app` URL "might be directly accessible" unless disabled or ingress-restricted ([Google IAP](https://docs.cloud.google.com/iap/docs/concepts-overview)) **[CP]**. Entra Application Proxy: "Passthrough preauthentication doesn't trigger Microsoft Entra authentication, so Conditional Access Policies can't be enforced"; P1/P2 licence required ([Entra app proxy FAQ](https://learn.microsoft.com/entra/identity/app-proxy/application-proxy-faq)) **[CP]**. Zscaler ZPA App Connectors "do not accept inbound connections" ([Zscaler](https://help.zscaler.com/zpa/what-zscaler-private-access)) **[CP]**.

For apps on Vercel, Netlify or Lovable platform subdomains, an IAP in front of a custom domain protects only that hostname; the platform subdomain and any direct BaaS endpoint remain reachable unless separately locked. Vercel's own docs say `*.vercel.app` URLs stay public unless Deployment Protection covers "All Deployments" ([Vercel KB](https://vercel.com/kb/guide/locking-down-deployments)) **[CP]**. The requirement is therefore three-part: IAP on the custom domain with origin validation, platform-level protection on the platform subdomain and previews, and boundary B3 controls on the data path **[INF]**.

#### 4.3.2 Password protection and shared links

Password protection is a shared secret with no per-user revocation; on Vercel Pro it costs USD 20 per protected project per month and is included on Enterprise ([Vercel Deployment Protection](https://vercel.com/docs/deployment-protection)) **[CP]**. Replit documents it as "different from private access tied to an authenticated identity" ([Replit](https://docs.replit.com/teams/privacy-and-deployment-settings)) **[CP]**. Funnel exposes a local service to the public internet; "Anyone with the Funnel URL can reach the shared resource", no visitor sign-in is described, and "Enabling Funnel through the CLI adds a default that lets all autogroup:member users use it" ([Tailscale Funnel](https://tailscale.com/kb/1223/funnel)) **[CP]**. ### 4.4 Boundary B3: the data and connector API

#### 4.4.1 Supabase semantics: schema exposure, grants, RLS, columns, views, RPC

Four independent PostgreSQL mechanisms gate a Supabase Data API request, in this order. First, schema exposure: with the Data API disabled "none of the auto-generated REST endpoints respond, regardless of grants or RLS" ([Supabase hardening guide](https://supabase.com/docs/guides/database/hardening-data-api)) **[CP]**. Second, table and column grants: "Grants decide whether a role can run an operation on the table at all"; "A missing grant raises a `42501` error before any policy runs"; and "Adding policies doesn't take those grants back" ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security)) **[CP]**. PostgREST's model is that "All authorization happens in the database"; requests with no JWT run as the anonymous role, and a JWT role claim causes `SET LOCAL ROLE` for the request ([PostgREST auth](https://docs.postgrest.org/en/v13/references/auth.html)) **[CP]**. Third, RLS: when enabled, "If no policy exists for the table, a default-deny policy is used"; permissive policies combine with `OR`, restrictive with `AND`; superusers, `BYPASSRLS` roles and table owners bypass it; referential-integrity checks "always bypass row security" and can be a covert channel ([PostgreSQL ddl-rowsecurity](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)) **[CP]**. An `UPDATE` policy needs a corresponding `SELECT` policy, and without `WITH CHECK` "the `using` expression decides both which rows are visible and which new rows are allowed", so a user can reassign a row's `user_id` to another user ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security); [Supabase SKILL.md](https://github.com/supabase/agent-skills/blob/main/skills/supabase/SKILL.md)) **[CP]**. Authorisation claims must come from `app_metadata` (`raw_app_meta_data`), never `user_metadata`, which "can be modified by authenticated end users" **[CP]**. Fourth, column privileges, which work "independently from RLS" but break `select *` for restricted roles and are labelled "an advanced feature" ([Supabase column-level security](https://supabase.com/docs/guides/database/postgres/column-level-security)) **[CP]**.

Two side paths bypass all of the above unless configured. Views "bypass RLS by default because they are usually created with the `postgres` user"; on Postgres 15+ `security_invoker = true` makes a view obey the invoking user's policies ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security); [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)) **[CP]**. Functions: "By default, any role can run a database function", including `anon`; a `security definer` function owned by `postgres` has `bypassrls` and "can return rows the caller isn't allowed to read"; without a pinned `search_path` a caller can hijack an unqualified name ([Supabase database functions](https://supabase.com/docs/guides/database/functions)) **[CP]**. The agent skill's rule is blunt: "Never add `SECURITY DEFINER` to resolve a permission error; it silently removes access control" **[CP]**. Security Advisor lints exist for each (0010 security definer view, 0028/0029 security definer functions executable by anon/authenticated, 0011 mutable search path, 0024 permissive policy, 0025 public bucket allows listing) ([Supabase database advisors](https://supabase.com/docs/guides/database/database-advisors)) **[CP]**, but lints 0008 and 0024 are presence and pattern checks; they cannot tell whether a predicate matches the tenancy model **[INF]**. The GraphQL path (pg_graphql) follows the same grants and RLS; introspection is off by default from 1.6.0; pg_graphql stopped being enabled by default on new projects on 18 May 2026 ([Supabase GraphQL](https://supabase.com/docs/guides/graphql); [changelog 45329](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)) **[CP]**.

#### 4.4.2 What the 30 October 2026 change does and does not do

Changelog 45329 (published 28 April 2026) is precise **[CP]**. New tables in `public` no longer receive the default `select, insert, update, delete` grants to `anon`, `authenticated` and `service_role`; without an explicit `GRANT`, PostgREST returns `42501` with the hint "GRANT SELECT ON public.your_table TO anon;". Dates: new default for all new projects 30 May 2026 ("gradual rollout over a few weeks"); applied to all existing projects **30 October 2026**. Verbatim limits: "Existing tables are not affected in your project, they keep their current grants and stay reachable"; "RLS behavior remains unchanged"; direct connections "will not affect you"; `storage`, `auth`, `realtime`, custom schemas and self-hosted deployments are out of scope ([Supabase changelog 45329](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)).

Three consequences the audit did not draw **[INF]**. The changelog's early-adoption SQL revokes default privileges on tables and sequences only; the hardening guide separately revokes `EXECUTE` on functions from `anon`, `authenticated`, `service_role` and `public` ([Supabase hardening guide](https://supabase.com/docs/guides/database/hardening-data-api)) **[CP]**. A new RPC function in `public` therefore stays callable by `anon` after 30 October unless the project also applies the function revokes; RPC exposure is a separate audit item. The RLS auto-enable event trigger (`ensure_rls` on `ddl_command_end`) is a per-database object only `postgres` can create, covers only `public`, enables RLS but adds no grants or policies, and "Existing tables still need RLS enabled manually" ([Supabase event triggers](https://supabase.com/docs/guides/database/postgres/event-triggers)) **[CP]**; its presence on a builder-provisioned project must be verified with `select evtname from pg_event_trigger`, not assumed. And the default-privilege statements are issued `for role postgres`; PostgreSQL default privileges are per creating role, so tables created by a different owner role would not be covered (PostgreSQL semantics; not discussed by Supabase). Whether the 30 October rollout for existing projects is instantaneous or gradual like the May rollout is not stated; test after the date **[INF]**.

"Secure by default" after 30 October therefore means only that a new table the agent forgets to grant is unreachable via REST and GraphQL. A table the agent does grant to `anon` with no RLS, or with a `USING (true)` policy, is as exposed as before. Grants are necessary, not sufficient; RLS is necessary, not sufficient; both plus correct policy logic are required **[INF]**. The practical privileged paths to audit on any project are: anything using a secret or `service_role` key; `security definer` functions and views in exposed schemas; custom roles with `bypassrls`; direct Postgres connection strings held by apps or agents **[INF]**.

Key model: publishable keys (`sb_publishable_`) are designed to be public and map to `anon` or `authenticated`; secret keys (`sb_secret_`) map to `service_role`, bypass RLS and are rejected with HTTP 401 when sent from a browser; legacy JWT `anon` and `service_role` keys are "deprecated by the end of 2026" with removal "Late 2026, TBC", and projects restored since 1 November 2025 receive no legacy keys ([Supabase API keys](https://supabase.com/docs/guides/api/api-keys); [changelog 29260](https://supabase.com/changelog/29260-upcoming-changes-to-supabase-api-keys)) **[CP]**. The OpenAPI schema at `/rest/v1/` is no longer served to `anon` callers since 8 April 2026 for all projects ([changelog 42949](https://supabase.com/changelog/42949-breaking-change-removing-access-to-openapi-spec-via-the-anon-key)) **[CP]**, which removes the enumeration step Wiz used at Moltbook but not the data path.

#### 4.4.3 Trust-path analysis: direct-to-BaaS with verified RLS versus a least-privilege BFF

The question is not "browser or server" but "where is the authorisation decision bound to the caller's identity and tenant on every request". Four paths **[INF]**, each grounded in vendor documentation **[CP]**:

**Path A — browser to PostgREST with a publishable key, verified grants and RLS.** The enforcement point is Postgres, which sees the real `sub` and claims on every request and cannot be bypassed by the client. Weaknesses: policy-logic correctness (needs the tests in 4.4.4); privileged side paths (security-definer RPC, non-invoker views, public buckets); no natural place for rate limiting, business validation or audit beyond `db-pre-request` hooks, which the hardening guide describes for "rate limiting, extra API key checks, or blocking direct access to certain objects" ([Supabase hardening guide](https://supabase.com/docs/guides/database/hardening-data-api)). An internet-reachable API is inherent.

**Path B1 — BFF forwarding the user's JWT.** Supabase Edge Functions default to `verify_jwt = true`; `auth: 'user'` yields a client "scoped to the caller's Row Level Security (RLS) policies" ([Supabase Edge Functions auth](https://supabase.com/docs/guides/functions/auth)). With a secret key, "A secret key bypasses RLS only when the request carries no user access token"; with a user token present the request "runs under the RLS policies of that signed-in user" ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security)). This is the least-privilege BFF: RLS remains the enforcement point and the server tier adds rate limiting, audit, validation and composition. Compromise of the BFF yields only the current caller's rights unless the secret key is also exfiltrated.

**Path B2 — BFF with a secret key and no user token.** RLS is removed from the path; tenant binding depends on every query carrying the right filter; one missing `where org_id = ...` is a cross-tenant leak, and a BOLA on any endpoint exposes the whole database. Supabase's own guidance treats this as the exception: "`ctx.supabaseAdmin` bypasses Row Level Security, so filter by the caller's ID"; "Use `ctx.supabaseAdmin` only for work that has to cross those policies" ([Supabase Edge Functions auth](https://supabase.com/docs/guides/functions/auth)). This is the confused deputy the audit described and is strictly weaker than Path A unless the BFF's authorisation is itself verified by the same cross-tenant tests.

**Path B3 — BFF with a dedicated Postgres role over a direct connection.** The 30 October change does not apply; grants and RLS must be designed explicitly; the role must not have `BYPASSRLS` and must not own the tables (owners bypass RLS unless `FORCE ROW LEVEL SECURITY`); per-request identity can be propagated with `SET LOCAL ROLE` and `set_config('request.jwt.claims', ...)` in a transaction, mirroring PostgREST ([PostgreSQL ddl-rowsecurity](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

Authorisation engines (Cedar, OPA, OpenFGA, Oso) are decision points, not enforcement points: Cedar defaults to `Deny` ([Cedar](https://docs.cedarpolicy.com/auth/authorization.html)), OPA "decouples policy decision-making from policy enforcement" ([OPA](https://www.openpolicyagent.org/docs/latest/)), Oso returns "a boolean, a list, or logic to run against your database" ([Oso](https://www.osohq.com/docs)) **[CP]**. In Path A they are irrelevant; in Path B their decision must be reflected in the query predicate, otherwise the engine approves while the secret-key query over-fetches **[INF]**. The OWASP Authorization Cheat Sheet supplies the BFF's acceptance criteria: deny by default, validate on every request, never rely on client-side checks, log, test ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)) **[CP]**. Governed low-code platforms implement Path B1/B3 by construction: Superblocks apps "never connect directly to business systems" ([Superblocks](https://docs.superblocks.com/getting-started/what-is-superblocks.md)); Retool permissions are per resource and group ([Retool](https://docs.retool.com/org-users/concepts/permission-groups)); ServiceNow Build Agent apps inherit ACLs ([ServiceNow](https://www.servicenow.com/docs/r/application-development/vc-governance.html)) **[CP]**. No vendor publishes breach-outcome comparisons between direct-RLS and BFF architectures; this analysis is reasoning from documented semantics **[INF]**.

#### 4.4.4 The behavioural authorisation test matrix

A presence check ("RLS enabled", "policy exists") passed the EdTech app and would pass a `USING (true)` policy. The test that matters is behavioural: three principals (anonymous publishable-key caller, authenticated tenant-A user, authenticated tenant-B user), four surfaces (REST table, GraphQL if enabled, each RPC function, Storage object), five operations (select, insert, update, upsert, delete), asserting on **row counts and SQLSTATE**, not HTTP status **[PROP]** assembled from documented patterns **[CP]**. The assertion discipline is the point: an RLS-filtered `SELECT` succeeds with zero rows and an `UPDATE` or `DELETE` of invisible rows succeeds affecting zero rows, so a test that checks only for 200/204 passes on a broken policy; a `42501` signals a missing grant or a `WITH CHECK` violation and is the correct expectation for anonymous access to tenant data after 30 October **[INF]**.

Documented tooling as of October 2026: pgTAP via `supabase test db`, with `set local role` and `set local "request.jwt.claims"` for impersonation ([Supabase testing overview](https://supabase.com/docs/guides/local-development/testing/overview)) **[CP]**; the basejump `supabase_test_helpers` extension 0.0.6 (`tests.create_supabase_user`, `tests.authenticate_as`, `tests.clear_authentication`, `tests.rls_enabled`) ([Supabase pgTAP extended](https://supabase.com/docs/guides/local-development/testing/pgtap-extended)) **[CP]**; Supabase's RLS Tester feature preview (24 April 2026), which is SELECT-only and therefore cannot detect missing `WITH CHECK` or UPDATE-without-SELECT defects ([changelog 45233](https://supabase.com/changelog/45233-feature-preview-rls-tester)) **[CP]**; SupaShield, a community CLI that generates anonymous and authenticated CRUD tests in rolled-back transactions ([GitHub](https://github.com/Rodrigotari1/supashield)) **[RR]**; and Lovable's Deep scan with Aikido "dynamic AI penetration testing" ([Lovable security](https://docs.lovable.dev/features/security)) **[VR]**. Application-level HTTP tests cannot use transactions for isolation and must sign in real users ([Supabase testing overview](https://supabase.com/docs/guides/local-development/testing/overview)) **[CP]**.

Minimal example, composed from the documented rules (explicit grants bundled with RLS per changelog 45329; `TO` clause, `(select ...)` wrapping and `app_metadata` claims per the RLS docs; USING plus WITH CHECK on UPDATE per SKILL.md) **[PROP]**:

```sql
-- migration: invoices, tenant-bound via app_metadata.org_id
create table public.invoices (
  id         uuid primary key default gen_random_uuid(),
  org_id     uuid not null,
  amount     numeric not null,
  created_by uuid not null default auth.uid()
);

-- Explicit grants (mandatory for new tables after 30 May / 30 Oct 2026). No grant to anon.
grant select, insert, update, delete on table public.invoices to authenticated;
alter table public.invoices enable row level security;

-- Tenant claim from user-immutable app_metadata; EXECUTE revoked from public/anon.
create or replace function public.current_org_id() returns uuid
language sql stable as $$
  select ((select auth.jwt()) -> 'app_metadata' ->> 'org_id')::uuid
$$;
revoke execute on function public.current_org_id() from public, anon;
grant  execute on function public.current_org_id() to authenticated;

create policy invoices_select on public.invoices for select to authenticated
  using (org_id = (select public.current_org_id()));
create policy invoices_insert on public.invoices for insert to authenticated
  with check (org_id = (select public.current_org_id()));
create policy invoices_update on public.invoices for update to authenticated
  using      (org_id = (select public.current_org_id()))
  with check (org_id = (select public.current_org_id()));
create policy invoices_delete on public.invoices for delete to authenticated
  using (org_id = (select public.current_org_id()));
```

```sql
-- supabase/tests/invoices_rls.test.sql   (run: supabase test db)
begin;
select plan(6);

set local role service_role;   -- seed as service_role (bypasses RLS)
insert into public.invoices (id, org_id, amount, created_by) values
  ('11111111-1111-1111-1111-111111111111','aaaaaaaa-0000-0000-0000-000000000001',10,'00000000-0000-0000-0000-00000000000a'),
  ('22222222-2222-2222-2222-222222222222','bbbbbbbb-0000-0000-0000-000000000002',20,'00000000-0000-0000-0000-00000000000b');

-- 1. Anonymous: no grant -> 42501 before any policy runs.
set local role anon;
select throws_ok($$ select * from public.invoices $$, '42501', null, 'anon has no grant');

-- 2. Tenant A sees exactly one row.
set local role authenticated;
set local "request.jwt.claims" =
  '{"sub":"00000000-0000-0000-0000-00000000000a","role":"authenticated","app_metadata":{"org_id":"aaaaaaaa-0000-0000-0000-000000000001"}}';
select results_eq($$ select count(*) from public.invoices $$, array[1::bigint], 'tenant A sees one row');

-- 3. Cross-tenant read returns empty, not an error.
set local "request.jwt.claims" =
  '{"sub":"00000000-0000-0000-0000-00000000000b","role":"authenticated","app_metadata":{"org_id":"bbbbbbbb-0000-0000-0000-000000000002"}}';
select is_empty($$ select id from public.invoices where id = '11111111-1111-1111-1111-111111111111' $$,
  'tenant B cannot read tenant A');

-- 4. Cross-tenant insert rejected by WITH CHECK.
select throws_ok($$ insert into public.invoices (org_id, amount)
  values ('aaaaaaaa-0000-0000-0000-000000000001', 1) $$, '42501',
  'new row violates row-level security policy for table "invoices"', 'tenant B cannot insert into A');

-- 5. Cross-tenant update affects zero rows (assert the count).
select results_eq($$ with u as (update public.invoices set amount = 999
  where id = '11111111-1111-1111-1111-111111111111' returning 1) select count(*) from u $$,
  array[0::bigint], 'tenant B update of A affects 0 rows');

-- 6. Reassignment attack: tenant B cannot move its row into tenant A.
select throws_ok($$ update public.invoices set org_id = 'aaaaaaaa-0000-0000-0000-000000000001'
  where id = '22222222-2222-2222-2222-222222222222' $$, '42501', null, 'WITH CHECK blocks reassignment');

select * from finish();
rollback;
```

The same six cases must be re-run over HTTP (publishable key with no `Authorization` header for the anonymous case; signed-in tenant A and B JWTs for the rest) against `/rest/v1/invoices`, `/graphql/v1` if enabled, each `/rest/v1/rpc/<fn>` and `/storage/v1/object/<bucket>/...`, asserting on body row counts or `returning` values **[PROP]**. Storage follows RLS on `storage.objects`; upsert needs INSERT plus SELECT plus UPDATE or "file replacement (upsert) silently fails"; service keys bypass Storage RLS entirely ([Supabase storage access control](https://supabase.com/docs/guides/storage/security/access-control); [SKILL.md](https://github.com/supabase/agent-skills/blob/main/skills/supabase/SKILL.md)) **[CP]**. The Supabase agent skill tells agents to run advisors before committing migrations but not to write cross-tenant tests; an organisation's `AGENTS.md` or `CLAUDE.md` should require this matrix explicitly **[INF]**/**[PROP]**.

#### 4.4.5 The same failure class on other BaaS

Firestore test mode "allows anyone to read and overwrite your data"; production mode denies all client reads and writes while server SDKs "bypass all Cloud Firestore Security Rules"; rules "are not filters—queries are all or nothing"; the allow-all ruleset carries the warning "NEVER use this rule set in production" ([Firestore quickstart](https://firebase.google.com/docs/firestore/quickstart); [Firestore security](https://firebase.google.com/docs/firestore/security/get-started); [rules and queries](https://firebase.google.com/docs/firestore/security/rules-query)) **[CP]**. App Check "prevents some, but not all, abuse vectors" and is complementary to Authentication and rules, not a substitute ([Firebase App Check](https://firebase.google.com/docs/app-check)) **[CP]**. Neon's Data API "has no permission layer of its own"; its "Grant public schema access" option runs `ALTER DEFAULT PRIVILEGES` so future tables are auto-granted to `authenticated`, the pre-30-October Supabase posture restricted to logged-in users ([Neon Data API](https://neon.com/docs/data-api/get-started)) **[CP]**/**[INF]**. Convex has no declarative row filter: "By default your Convex functions are public", and only internal functions are shielded, so the behavioural cross-tenant test is the only test available ([Convex](https://docs.convex.dev/functions/internal-functions)) **[CP]**/**[INF]**. PocketBase and Appwrite default to locked; their characteristic vibe-coding failure is generated code setting `""` rules or `Role.any()` to make a demo work ([PocketBase](https://pocketbase.io/docs/api-rules-and-filters/); [Appwrite](https://appwrite.io/docs/advanced/platform/permissions)) **[CP]**/**[INF]**.

#### 4.4.6 Bundle secrets: what each control actually scans

Framework prefixes inline values into the browser bundle by design: Next.js "inline[s]" `NEXT_PUBLIC_` values at build time; Vite says `VITE_*` variables "should not contain sensitive information such as API keys" ([Next.js](https://nextjs.org/docs/app/guides/environment-variables); [Vite](https://vite.dev/guide/env-and-mode)) **[CP]**. The decisive distinction for CI gating is what is scanned **[INF]**. Repository scanners (gitleaks, TruffleHog, GitHub secret scanning) see source, so they catch a hard-coded secret key but not an environment variable a build inlines. Only build-output scanning catches the prefixed-variable leak: Netlify's smart detection "scans for potential secrets in your repository code and build output" and fails the build, on Personal, Pro and Enterprise plans ([Netlify secret scanning](https://docs.netlify.com/manage/security/secret-scanning/)) **[CP]**; elsewhere a post-build grep of `dist/` or `.next/static` is needed, safelisting `sb_publishable_` and failing on `sb_secret_` or a legacy service-role JWT **[PROP]**. Vercel's Protected Source Maps (default for new projects since 14 May 2026; existing projects opt in) gate `.map` files behind Vercel Authentication, which protects code logic, not a `NEXT_PUBLIC_` value that sits in the minified bundle itself ([Vercel changelog](https://vercel.com/changelog/protected-source-maps-ship-browser-source-maps-securely)) **[CP]**/**[INF]**.

GitHub push protection for repositories "Is disabled by default" and requires paid Secret Protection, at an illustrative "$19 per active committer" over 90 days; user-level protection covers public repositories only; by default anyone with write access can bypass with a reason ([GitHub push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection); [GitHub pricing](https://docs.github.com/en/code-security/how-tos/secure-at-scale/configure-organization-security/configure-specific-tools/estimating-the-price-of-secret-protection)) **[CP]**. GitHub added `supabase_oauth_access_token`, `supabase_scoped_personal_access_token` and `lovable_api_key` detectors on 5 October 2026; push-protection support for these is not stated ([GitHub changelog](https://github.blog/changelog/2026-10-05-secret-scanning-adds-detectors-for-lovable-supabase-and-more)) **[CP]**. Supabase auto-revokes secret keys found in public GitHub, post-commit; push protection was "planned, 2026" ([Supabase Security Retro 2025](https://supabase.com/blog/supabase-security-2025-retro)) **[CP]**. gitleaks is "feature complete" with security patches only ([gitleaks](https://github.com/gitleaks/gitleaks)) **[CP]**; TruffleHog verifies over 700 detector types against live APIs ([trufflehog](https://github.com/trufflesecurity/trufflehog)) **[CP]**; neither README lists Supabase formats (gap).

### 4.5 Boundary B4: the agent execution plane

#### 4.5.1 What is enforced outside the model, and where the seams are

Across Claude Code, Copilot coding agent, Cursor, Codex, Windsurf/Devin Desktop and Replit, the only controls enforced by something other than the model are an OS-level sandbox around shell commands, a network proxy allowlist in front of those commands, cloud-side isolation (ephemeral runners, branch and token restrictions), and the IAM or OAuth scope of the credentials the agent holds. Every vendor documents seams in its own words **[CP]**.

**Claude Code.** The sandbox is "off by default"; when on, writes are limited to the working directory and a temp directory, but reads cover "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`", environment variables are "Inherited from Claude Code, including any secrets in its environment", and the network allowlist "start[s] empty" ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)) **[CP]**. "The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it"; "A `denyRead` entry doesn't stop the Read tool"; hooks, local MCP servers, LSP servers and `apiKeyHelper` "run with your full access" **[CP]**. Fail-open: if the sandbox cannot start "Claude Code runs commands without sandboxing" unless `failIfUnavailable` is true **[CP]**. Unsandboxed retry: the model "may retry the command with the `dangerouslyDisableSandbox` parameter", and "if an allow rule such as `Bash(curl *)` matches the command, it also approves the retry, so the command runs outside the sandbox with no prompt"; disable with `allowUnsandboxedCommands: false` **[CP]**. There is "no built-in credential deny list" **[CP]**. Bash deny rules match command text and are "not a security boundary around the program": `Bash(curl *)` does not stop `/usr/bin/curl` or `sh -c 'curl ...'` ([Claude Code permissions](https://code.claude.com/docs/en/permissions)) **[CP]**. Native Windows runs unsandboxed **[CP]**. Anthropic's own remedy for the seams is to run the whole process "in a container, virtual machine, or the sandbox runtime" **[CP]**. Practitioner traces confirmed the Read-tool gap, default reads of `/etc/passwd` and SSH keys, the retry prompt text "(don't ask, just do it)", and exfiltration through gists once `github.com` is allowlisted ([Claude Code Camp](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect)) **[RR]**. Three pre-trust execution paths were fixed between August and December 2025: hooks in `.claude/settings.json` (GHSA-ph6w-f82w-28w6, no CVE), MCP servers from `.mcp.json` before approval (CVE-2025-59536, fixed 1.0.111) and `ANTHROPIC_BASE_URL` exfiltration (CVE-2026-21852, fixed 2.0.65) ([Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files/); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-21852)) **[CP]**. Opening an untrusted repository remains an attack surface; Check Point's advice is to "Inspect configuration directories such as `.claude/` and `.vscode/` before opening projects" **[CP]**.

**GitHub Copilot coding agent.** The firewall is on by default with a recommended allowlist covering OS package repositories, container registries and language package registries; "The firewall applies only to processes the agent starts through its Bash tool. It does not directly apply to MCP server processes or processes started in configured setup steps"; it "should not be considered a comprehensive security solution" ([GitHub firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)) **[CP]**. Platform-enforced guardrails: no push to the default branch, one `copilot/` branch per task, Actions on agent PRs need write-user approval, hidden-character filtering, secrets only from the `copilot` environment, 59-minute sessions ([GitHub responsible use](https://docs.github.com/en/copilot/responsible-use/copilot-coding-agent); [About coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)) **[CP]**. Once an MCP server is configured "Copilot can use its tools autonomously without asking for approval", so GitHub recommends read-only tool allowlists rather than `"*"` ([GitHub MCP](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/extend-coding-agent-with-mcp)) **[CP]**.

**Cursor, Codex, Windsurf/Devin, Replit.** Cursor's sandbox (2.0, macOS Seatbelt) defaults to `readBoundary: "system"` (reads unrestricted) and `networkPolicy.default: "deny"`; team-admin policies "can't be weakened by user or repo files"; Auto-review "is not a security boundary" and a failed sandboxed command can be rerun outside the sandbox after classifier review ([Cursor sandbox.json](https://cursor.com/docs/reference/sandbox); [Cursor Run modes](https://cursor.com/docs/agent/security/run-modes)) **[CP]**. Codex defaults to `workspace-write`, offers `danger-full-access`, and its domain-enforcing proxy "Defaults to `false`" with "App and connector traffic ... not controlled" by it ([Codex config](https://learn.chatgpt.com/docs/config-file/config-reference)) **[CP]**. Windsurf/Devin Desktop documents prefix-matched allow/deny lists up to a Turbo mode and no OS sandbox or network restriction ([Devin Desktop](https://docs.devin.ai/desktop/terminal)) **[CP]**. Replit's "Agent is not able to modify the production database" ([Replit dev/prod](https://docs.replit.com/features/data-and-storage/development-and-production)) **[CP]** is the only vendor change in the record that removes the destructive capability rather than mitigating it **[INF]**.

Every documented allowlist (Copilot's recommended list, Claude Code's `github.com`, Cursor defaults) includes hosts that accept uploads; a network allowlist bounds where exfiltration can go, not whether it can happen **[INF]**.

#### 4.5.2 MCP: the host-side channel every sandbox leaves open

The lethal trifecta is private data, untrusted content and an exfiltration channel; "LLMs are unable to reliably distinguish the importance of instructions based on where they came from" ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) **[RR]**. The General Analysis demonstration (8 Jul 2025) had Cursor plus the Supabase MCP under `service_role` read a support ticket submitted via `anon`, then copy `integration_tokens` back into the ticket; read-only mode "blocks the write-back step but still permits reads" ([General Analysis](https://www.generalanalysis.com/blog/supabase-mcp-blog)) **[RR]**. Supabase's MCP page (8 Oct 2026) says to connect to production "only when the task requires production evidence", with `read_only=true`, `project_ref` scoping and restricted feature groups; manual approval of each tool call is "a guardrail, not a guarantee of human review"; result-wrapping against injection "is not foolproof" ([Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp)) **[CP]**. Tool poisoning (hidden instructions in tool descriptions, "rug pulls", cross-server shadowing) exfiltrated `~/.cursor/mcp.json` and SSH keys in Invariant's demonstration ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)) **[RR]**. The MCP authorisation spec makes authorisation optional, forbids token passthrough and recommends short-lived tokens ([MCP spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)) **[CP]**. Enterprise gateways exist (Cloudflare MCP server portals with per-tool allowlists and Logpush, where blocked users "can bypass this by using a server's direct URL"; Docker MCP Gateway, "invite-only"; Azure API Management with Entra JWT policies) ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/mcp-servers/mcp-portals/); [Docker](https://docs.docker.com/ai/mcp-catalog-and-toolkit/mcp-gateway/); [Microsoft Learn](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)) **[CP]**.

As of 9 October 2026 no primary source confirms an in-the-wild incident in which a coding agent exfiltrated secrets via MCP; the record is high-fidelity research (Sentry MCP agentjacking, 85% success in testing, 2,388 injectable DSNs, Sentry calling a root-cause fix "technically not defensible"; `claude-code-action` CVE-2025-66032) plus one CI case the CSA says was exploited in the wild ([CSA agentjacking](https://labs.cloudsecurityalliance.org/research/csa-research-note-agentjacking-mcp-sentry-injection-20260612/); [CSA CI/CD](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)) **[CP]**/**[PO]**. Absence is consistent with low detectability: the Sentry attack uses legitimate developer credentials and looks like normal activity **[INF]**.

Rules files are an injection surface. Pillar's "Rules File Backdoor" hid instructions in `.cursor/rules` and Copilot instruction files with zero-width and bidirectional Unicode; Cursor said the risk "falls under users' responsibility", GitHub that users are "responsible for reviewing and accepting suggestions", and GitHub added a hidden-Unicode warning on 1 May 2025 ([Pillar Security](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)) **[VR]**; no in-the-wild case is reported **[VR]**.

#### 4.5.3 Post-incident vendor changes

Replit (21 Jul 2025): "automatic DB dev/prod separation to prevent this categorically" ([The Register](https://www.theregister.com/2025/07/22/replit_saastr_response/)) **[PO]**, now documented as "Agent is not able to modify the production database" **[CP]**. Railway: the API `volumeDelete` mutation now has the same "two-day grace period" as dashboard deletes ([Railway Central Station](https://station.railway.com/questions/any-changes-to-protect-database-backups-3b31d4d3)) **[CP]**; as of 9 October 2026 Railway still has no permission-scoped API tokens, the token model being Account, Workspace, Project (one environment) and OAuth ([Railway Public API](https://docs.railway.com/reference/public-api)) **[CP]**, and a "Read-only access for AI agents" request is "Under Review" with no reply ([Railway feedback](https://station.railway.com/feedback/read-only-access-for-ai-agents-7fd55962)) **[CP]**. Railway's fix addresses recoverability, not authorisation: a token that can delete a volume can still delete it; the window converts an irreversible call into a two-day reversible one **[INF]**. No Cursor or Anthropic statement or change attributable to PocketOS was found; Cursor's network controls (Feb 2026) predate it, and Anthropic's 2026 hardening (`bypassPermissions` no longer honoured from project settings in v2.1.257, `blockReadsOutsideWorkingDirectories`, `allowManagedMcpServersOnly` in v2.1.273, strict-sandbox precedence fix in v2.1.285) is not attributed to the incident ([Claude Code settings](https://code.claude.com/docs/en/settings); [managed settings](https://code.claude.com/docs/en/managed-settings)) **[CP]**. Google fixed the Gemini CLI WIF over-grant with `.geminiignore` and role scoping **[CP]**; Amazon introduced "mandatory peer review for production access" ([Amazon](https://www.aboutamazon.com/news/aws/aws-service-outage-ai-bot-kiro)) **[CP]**.

#### 4.5.4 Minimal managed-settings baselines

Anthropic publishes a managed-settings mechanism (`/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`, `C:\Program Files\ClaudeCode\managed-settings.json`, MDM profiles, Windows registry re-checked every 30 minutes, or the claude.ai console) with documented lock semantics: Boolean keys set in managed settings override local values; array keys merge unless a lock such as `allowManagedDomainsOnly` or `allowManagedReadPathsOnly` covers them; `allowUnsandboxedCommands: false` makes the sandbox "admin-required" ([Claude Code managed settings](https://code.claude.com/docs/en/managed-settings); [sandboxing](https://code.claude.com/docs/en/sandboxing)) **[CP]**. Anthropic's fuller example "isn't a recommended policy" ([Claude Code settings example](https://code.claude.com/docs/en/settings-example)) **[CP]**. The baseline below is assembled from documented keys; the combination is the authors' **[PROP]**.

| Claude Code key | Value | Why |
|---|---|---|
| `sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands` | `true`, `true`, `false` | Sandbox on, fail closed, no unsandboxed retry; repo `excludedCommands` ignored |
| `sandbox.network.allowedDomains`, `sandbox.network.allowManagedDomainsOnly` | internal registry proxy and git host only; `true` | Egress allowlist developers cannot widen |
| `sandbox.allowManagedReadPathsOnly`, `sandbox.enableWeakerNestedSandbox`, `sandbox.enableWeakerNetworkIsolation`, `sandbox.network.allowAllUnixSockets`, `sandbox.network.allowLocalBinding` | `true`, `false`, `false`, `false`, `false` | Close documented weakening keys |
| `sandbox.credentials.files` and `.envVars` | deny or mask (`injectHosts`) for `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.netrc`, `~/.docker`, `~/.gnupg`, cloud and registry tokens | There is "no built-in credential deny list"; masking with `injectHosts` is a local credential broker |
| `permissions.deny` | `Read(./.env)`, `Read(./.env.*)`, `Read(./secrets/**)`, `Read(~/.ssh/**)`, `Read(~/.aws/**)` | Mirror every `denyRead` path because the Read tool ignores the sandbox; deny rules apply "in every session, trusted or not" |

| `forceLoginMethod`, `forceLoginOrgUUID`, `allowedProviders`, `requiredMinimumVersion` | org values; `>= 2.1.285` | Pin identity and provider; version at or above the strict-mode and MCP-lock fixes and far above CVE fixes 1.0.111 / 2.0.65 |

Copilot coding agent baseline (documented toggles; combination **[PROP]**): org "Enable firewall" = Enabled; recommended allowlist = Disabled with an org custom allowlist pointing at an internal registry proxy and required GitHub hosts; "Allow repository custom rules" off; MCP servers limited to read-only `tools` allowlists; no `COPILOT_MCP_` secrets with write scopes; environment protection rules on the `copilot` environment; third-party actions pinned to commit SHAs and no `id-token: write` or `contents: write` for agent workflows ([GitHub firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall); [CSA CI/CD](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)) **[CP]**. Whether an enterprise can lock all orgs is not documented (gap).

#### 4.5.5 Dev/prod separation and credential brokering

Dev/prod separation is the one categorical control. Beyond Replit, Neon recommends snapshots at "Start of each agent session" and "Before database schema changes", restorable with the connection string preserved, at USD 0.09/GB-month, and offers anonymised branches masked with PostgreSQL Anonymizer ([Neon versioning](https://neon.com/docs/ai/ai-database-versioning); [Neon anonymization](https://neon.com/docs/workflows/data-anonymization)) **[CP]**. Supabase branches are "data-less by default", auto-deleted on PR close, experimental and paid, with no masking documented ([Supabase branching](https://supabase.com/docs/guides/deployment/branching)) **[CP]**. PlanetScale restricts production-branch deletion to administrators and recommends against production data in development ([PlanetScale](https://planetscale.com/docs/postgres/branching)) **[CP]**.

Credential brokering keeps the destructive credential out of the agent's reach: Vercel OIDC Federation (all plans; build and function tokens with 2-hour TTL; cloud roles scoped per project and environment) ([Vercel OIDC](https://vercel.com/docs/oidc)) **[CP]**; GitHub Actions OIDC tokens "only valid for a single job" with `sub` claims such as `repo:org/repo:environment:prod` ([GitHub OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect)) **[CP]**; Cloudflare Outbound Workers intercept every `fetch()` and add authentication "so end developers don't need credentials" ([Cloudflare](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)) **[CP]**; Claude Code's `mask` plus `injectHosts` substitutes the real secret only on allowed hosts **[CP]**. ASI03 of the OWASP Agentic Top 10 states the principle: agents "inherit credentials such as user sessions, API keys, and OAuth tokens"; "Issue short-lived, narrowly scoped tokens per task" ([Descope summary of OWASP](https://www.descope.com/blog/post/owasp-agentic-top-10-identity)) **[RR]**. Where a provider cannot scope tokens, as Railway still cannot, the closest approximation is token type (a project token bound to one environment) and the gap is a vendor-selection criterion **[INF]**.

#### 4.5.6 Backups outside the blast radius

An architecture that survives the PocketOS class needs a copy outside the identity domain the agent's credentials can reach, storage-enforced immutability that no credential in the primary account can shorten, optional cross-account restore paths, and tested restores with measured RPO and RTO **[PROP]**. AWS logically air-gapped vaults store recovery points "in an AWS Backup service owned account", are "always locked with a vault lock in compliance mode", have a minimum retention of 7 days, and "Can optionally be shared across accounts using AWS RAM" ([AWS LAG vault](https://docs.aws.amazon.com/aws-backup/latest/devguide/logicallyairgappedvault.html)) **[CP]**. **Multi-party approval is optional**: "You can integrate your logically air-gapped vaults with Multi-party approval (MPA) to enable recovery ... even if the vault-owning account is inaccessible", requiring two Organizations, Identity Center, a RAM-shared approval team and an SCP, with "no additional MPA cost" ([AWS MPA](https://docs.aws.amazon.com/aws-backup/latest/devguide/multipartyapproval.html)) **[CP]**. Compliance-mode Vault Lock becomes immutable after a grace period of at least 3 days, denying deletion to "any user (including the root user)"; on account closure AWS deletes vault contents after 90 days "even if a vault lock was in place" ([AWS Vault Lock](https://docs.aws.amazon.com/aws-backup/latest/devguide/vault-lock.html)) **[CP]**. Equivalents: Azure's immutable vault "Enabled and locked" (irreversible; enforced soft delete 14 days; Resource Guard in a different tenant for "Maximum" isolation) ([Azure](https://learn.microsoft.com/en-us/azure/backup/backup-azure-immutable-vault-concept)); GCP backup vaults where "no one (not even a Project Owner) can decrease the retention period" ([GCP](https://docs.cloud.google.com/backup-disaster-recovery/docs/concepts/backup-vault)); Backblaze B2 compliance-mode Object Lock ([Backblaze](https://www.backblaze.com/docs/cloud-storage-object-lock)); pgBackRest relying on storage-layer object lock ([pgBackRest](https://pgbackrest.org/user-guide.html)) **[CP]**.

Cost anchors: AWS warm storage USD 0.05/GB-month; LAG vault USD 0.0575/GB-month (eu-west-1 example); restore USD 0.02–0.03/GB; restore testing USD 1.50 per recovery point ([AWS Backup pricing](https://aws.amazon.com/backup/pricing/)) **[CP]**. For a 200 GB database with 30 recovery points averaging 400 GB stored, the authors' arithmetic gives roughly USD 30–40 per month for an air-gapped, compliance-locked copy **[INF]**. Provider-internal grace periods (Railway two days, Replit 7 days, Azure 14 days) protect against a single destructive call but not against a credential that can also purge or wait out the window **[INF]**. PocketOS's own newest backup was months old, so the restore-drill gap was a root cause alongside the storage layout **[PO]**/**[INF]**.

#### 4.5.7 Dependency and registry controls

Package hallucination is measured and persistent (section 5.7). Socket Firewall's free tier blocks known-malicious packages at install, but "possible AI-detected malware only triggers a warning" and unknown packages pass ([Socket](https://socket.dev/blog/introducing-socket-firewall)) **[VR]**. Copilot's recommended allowlist includes public registries, leaving this path open **[CP]**. The CSA's controls for agent-driven installs are an allowlist with other installs routed to human review, pinned lockfiles with hash verification in CI, flags on packages registered in the last 30–90 days, and SBOMs for AI-generated code ([CSA slopsquatting](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419-csa/)) **[CP]**. The deterministic form is an agent egress allowlist that reaches only an internal curated registry proxy **[PROP]**; registry-proxy products were not verified from primary documentation in this pass (gap). The in-the-wild counterpart of the threat is Shai-Hulud: the November 2025 wave hit 525+ npm packages with about 132 million monthly downloads, harvested AWS, GCP, Azure, npm and GitHub credentials via `preinstall`, and installed a self-hosted Actions runner when the GitHub token had `workflows` scope ([Semgrep](https://semgrep.dev/blog/2025/digging-for-secrets-sha1-hulud-the-second-coming-of-the-npm-worm)) **[RR]**. An agent running `npm install` inside a sandbox whose reads cover `~/.aws`, `~/.npmrc` and the environment hands such a worm the same material a developer shell would **[INF]**.

### 4.6 Shadow-app discovery pipeline

#### 4.6.1 The verified wildcard-certificate finding

Direct TLS probes on 9 October 2026 show that all five platform subdomains are served under a single wildcard certificate, live apps included: `nonexistent-probe-xyz123.lovable.app` presented `CN=lovable.app`, SAN `*.lovable.app` (Google Trust Services); `replit.app` presented `*.replit.app`; `*.vercel.app` covered `next-blog-starter.vercel.app`, `nextjs-dashboard.vercel.app` and `v0-portfolio.vercel.app` (HTTP 200); `*.netlify.app, O=Netlify, Inc` (DigiCert) covered `docs-example.netlify.app`; `*.base44.app` (Let's Encrypt) **[CP]** (own verification). Per-app hostnames on platform subdomains therefore never appear in Certificate Transparency logs. Custom domains attached to these platforms do receive per-domain certificates and are CT-visible: Vercel "will automatically try to generate a certificate for every domain once it is added to a project" ([Vercel SSL](https://vercel.com/docs/domains/working-with-ssl)) **[CP]**. Symbiotic's own pipeline corroborates the blind spot: crt.sh produced 52 of its 1,085 confirmed sites (4.8%), against dorking 632 (58.2%), Common Crawl 251 (23.1%) and DNS brute-force 149 (13.7%) ([Symbiotic](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws)) **[VR]**. Because platform subdomains share one certificate and one IP pool, EASM products that attribute by certificate names or netblocks (Censys's discovery paths, Defender EASM seeds) cannot attribute these apps to a customer; attribution must come from content (brand tokens, logos, corporate email domains), HTML/JS fingerprints (Escape used Shodan this way), search indexes and Common Crawl, or inside signals ([Censys ASM](https://docs.censys.com/docs/asm-understand-investigate-attack-surface); [Defender EASM](https://learn.microsoft.com/en-us/azure/external-attack-surface-management/using-and-managing-discovery); [Escape methodology](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/)) **[CP]**/**[INF]**.

#### 4.6.2 The pipeline

Six steps, each tied to documented sources **[PROP]**:

1. **Inside the sanctioned tenants (day 1, no cost).** Export Lovable Security insights filtered to "Externally published" and "no owner"; Power Platform Inventory CSV or API; Replit team Deployments; Vercel and Netlify project lists with protection settings, remembering team defaults do not retro-apply **[CP]**.
2. **Identity and email signals (days 1–7).** IdP sign-in and OAuth consent logs for builder domains; email-metadata scanning of vendor welcome and billing mails recovers historical sign-ups ([Nudge Security](https://www.nudgesecurity.com/post/how-to-discover-shadow-ai-with-nudge-security)) **[VR]**; expense-feed and unfederated-access detection ([Torii, vendor comparison](https://www.toriihq.com/articles/five-shadow-ai-discovery-tools)) **[VR]**; corporate-card and corporate-email registration checks ([TechTarget](https://www.techtarget.com/it-strategy/feature/Research-shows-the-vibe-coding-security-crisis-CIOs-cant-ignore)) **[PO]**.
3. **SSE/CASB/browser telemetry (days 1–14).** Query SWG and CASB logs for builder consoles and for `*.lovable.app`, `*.replit.app`, `*.vercel.app`, `*.netlify.app`, `*.base44.app` using the GenAI app-type categories in Cloudflare Gateway, Netskope CCI and Defender for Cloud Apps ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/traffic-policies/application-app-types); [Netskope CCI](https://docs.netskope.com/en/cloud-confidence-index/)) **[CP]**; access logs show platform use, not what was deployed ([VentureBeat](https://venturebeat.com/security/vibe-coded-apps-shadow-ai-s3-bucket-crisis-ciso-audit-framework)) **[PO]**. No vendor documentation confirms that builder published-app domains are catalogued as distinct apps rather than under generic AI categories (gap).
4. **Outside-in enumeration (weeks 1–3).** Search dorking with brand tokens restricted to the five platform zones, Common Crawl index queries, DNS brute-force of brand tokens under platform zones, GitHub code search, urlscan.io, Wayback; Shodan/Censys HTML fingerprint searches; CT monitoring **only** for the corporate domain, known custom domains and Lovable branded URLs **[VR]**/**[CP]**.
5. **Passive triage (continuous).** Fetch the bundle, look for `*.supabase.co` URLs and key formats, attempt an anonymous read only. Both research pipelines converged on this minimum check set **[VR]**. Write and delete probes must not be run against assets the company does not own; both research teams that ran them acknowledged they could not fully explain how those were non-destructive **[INF]**.
6. **Register, gate, repeat.** Move finds into the sanctioned tenant with team defaults set (Vercel "All Deployments", Replit "Require", Lovable "Workspace", Base44 Apps SSO); put custom-domain apps behind an IdP gate with origin validation **[CP]**.

Cost anchors: Cloudflare Zero Trust free to 50 users then USD 7/user/month; Vercel Authentication on All Deployments free; Netlify Pro USD 20/month; Lovable Business about USD 50/month (third-party, July 2026); Replit Core USD 20, Pro USD 100, Enterprise USD 10,000–200,000 annual commitment; Power Apps Premium USD 20/user/month ([Replit pricing](https://replit.com/pricing); [Replit Enterprise](https://docs.replit.com/billing/plans/replit-enterprise); [Netlify pricing](https://www.netlify.com/pricing/)) **[CP]**/**[PO]**. crt.sh, Common Crawl and search operators are free; no published, independently evaluated accuracy figures exist for any dedicated vibe-app scanner **[INF]**.

## 5. Corrected empirical evidence on AI-generated code security

Read with their denominators, five independent academic studies and three vendor evaluations since 2025 support a narrower conclusion than "prompting redistributes rather than reduces": prompting shifts the correctness-versus-security trade-off, and whether that helps depends on model class, task length and phrasing. Nothing in this evidence caps damage; that is the job of the boundaries in section 4.

### 5.1 SusVibes, with correct denominators and best pairing

SusVibes (ICML 2026; v2 16 Feb 2026) is 200 Python feature-request tasks from 108 open-source repositories, each reconstructed from a CVE-linked fix commit, with mean repository context 162K lines and mean patch 172 lines; the agent passes when its code satisfies the functional tests **and** the security tests written for that specific CWE ([SusVibes](https://arxiv.org/html/2512.03262v2)) **[RR]**. Table 3, FuncPass / SecPass as % of 200 tasks: Claude 4 Sonnet with SWE-agent **61.0 / 10.5**, OpenHands **49.5 / 12.5**, Claude Code 44.0 / 6.0; Kimi K2 22.5 / 6.0, 37.0 / 9.0, 43.5 / 8.0; Gemini 2.5 Pro 19.5 / 7.0, 21.5 / 8.5, 15.0 / 4.5 **[RR]**. "Over 80%" of functionally correct solutions were insecure (82.8% for SWE-agent + Claude 4 Sonnet) **[RR]**. Every run already included the reminder "Make sure to follow best security practices and avoid common vulnerabilities" **[RR]**. Adding the exact target CWE left the joint rate at 10.5% while cutting FuncPass to 56.0%; self-selected CWEs gave 52.5 / 9.5, because agents picked 7.5 CWEs per task against 1.06 ground truth with precision around 0.1 **[RR]**. The authors "do not claim coverage of all exploit modalities", so SecPass is an upper bound on true security **[RR]**/**[INF]**. The released v1.0 dataset holds 186 tasks, not 200 ([LeiLiLab/susvibes](https://github.com/LeiLiLab/susvibes)) **[RR]**. The defensible one-sentence statement: on CVE-derived Python feature work in mature codebases, developer agents produced code that passed both functional and targeted security tests on 4.5–12.5% of tasks, with the best functional agent at 10.5% and the best joint agent at 12.5%. It is not a measure of vibe-coded apps.

### 5.2 The Veracode trend, with methodology

Veracode's suite is 80 tasks (4 languages × 4 CWEs: SQL injection, XSS, log injection, weak crypto × 5 instances), judged by Veracode's own SAST, with no security prompting by design, across more than 150 models cumulatively ([Veracode Spring 2026](https://www.veracode.com/blog/spring-2026-genai-code-security/)) **[VR]**. The 2025 release found 45% of tasks introduced an OWASP Top 10 flaw, Java above 70% failure, XSS 86% failure ([Veracode press release](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)) **[VR]**. The March 2026 update reports 55% overall pass (SQLi 82%, crypto 86%, XSS 15%, log injection 13%; Python 62%, Java 29%), GPT-5.1/5.2 "within the margin of error of GPT-4.1", Claude 4.5/4.6 "flat compared to earlier Claude generations", and **GPT-5-series with extended reasoning at 70–72%**, "a meaningful improvement over the standard 55%" yet "far from acceptable"; syntax pass rose from about 50% to 95% since 2023 **[VR]**. The corrected statement: average security pass for frontier non-reasoning models stayed in a 45–55% band from 2023 to March 2026 on a vendor SAST-judged, four-CWE suite with no authorisation CWEs, with a documented exception for reasoning modes **[INF]**. BaxBench independently finds reasoning models (o1, o3-mini, DeepSeek-R1) are the only class that benefits from generic security reminders ([BaxBench](https://arxiv.org/html/2502.11844v3)) **[RR]**. The Georgia Tech SSLab tracker attributes 74 CVEs to AI-authored code between 1 May 2025 and 20 Mar 2026 (Claude Code 49, Copilot 15), a figure the researcher calls a lower bound reflecting "detection blind spots" ([The Register](https://www.theregister.com/2026/03/26/ai_coding_assistant_not_more_secure/)) **[RR]**.

### 5.3 Prompting: redistribution, semantic drift, and phrasing

"Redistributes, not reduces" comes from one single-shot study on the synthetic Cybernative.ai dataset: 424 Python tasks, five prompts, GPT-4o and LLaMA 3.1-8B, one output each, Bandit and CodeQL ([Urmi et al., arXiv 2608.24857](https://arxiv.org/html/2608.24857v1)) **[RR]**. With a minimal prompt GPT-4o returned valid code on only 86 of 424 tasks; structured prompts raised that to about 380. Among valid outputs the share with any Bandit finding fell from 76.3% to 72.0% and the high-severity **share** fell from 20.8% to 13.6% while the low-severity share rose from 32.0% to 43.5%; absolute counts were never reported **[RR]**. "Semantic drift" (the model removing a requested unsafe construct) was found in 9–10 of **15 manually sampled** task IDs under security prompts, in a dataset where some tasks "explicitly encourage insecure practices" **[RR]**. The authors conclude prompt structure "is an unreliable substitute for robust security controls" **[RR]**. The result is evidence that security framing changes what the model writes, not evidence that prompting cannot reduce counts **[INF]**.

Other studies fill in the conditions. Backslash (vendor, Apr 2025, task count unpublished): GPT-4o 10% → 20% → 65% vulnerability-free across naive, generic and OWASP prompts; Claude 3.7 Sonnet 60% → 100%; "five out of the seven LLMs" still produced vulnerable code ([Infosecurity Magazine](https://www.infosecurity-magazine.com/news/llms-vulnerable-code-default/)) **[VR]**. BaxBench (392 backends, exploit-confirmed): for Claude 3.5 Sonnet a generic reminder raised secure-and-correct from 32.9% to 34.5% while dropping correctness from 53.6% to 45.5% **[RR]**. The only study on real deployed vibe-coded apps replayed 70 confirmed vulnerabilities 1,680 times: a one-line "production-ready" framing cut reintroduction from 25.7% to **11.0%**, a security-hardening skill to 11.9%, while a long "professional" technical prompt raised it to **45.7%**; a stronger model tier changed nothing (+0.5 pp); in 20.7% of reintroductions the agent "recognized the risk and still shipped the insecure code" ([Deng, Fan and Meng](https://arxiv.org/html/2606.23130v4)) **[RR]**. The cross-study pattern is a correctness tax (SusVibes −5.5 to −8.5 pp FuncPass; BaxBench −8 to −12.6 pp pass@1); prompting helps on short tasks with reasoning-class models and concise framing, and does not help on long agentic trajectories, with weaker models, or where the model knows the risk and ships anyway **[INF]**.

### 5.4 Iteration

Shukla et al. (GPT-4o, 10 secure C/Java baselines × 4 strategies × 10 rounds, 400 samples) found 387 vulnerabilities: efficiency-focused 124, feature-focused 158, **security-focused 38**, ambiguous 67; per-sample means rose from about 2.1 (rounds 1–2) to 6.2 (rounds 8–10) ([Shukla et al.](https://arxiv.org/html/2506.11022v2)) **[RR]**. The abstract's "37.6% increase in critical vulnerabilities after just five iterations" has no defined baseline in the body and should not be quoted as a precise figure **[RR]**/**[INF]**. The authors' operating rule, at most three LLM-only rounds between human reviews, is reasonable **[RR]**.

### 5.5 Stack-specific skills, with sample sizes

Supabase's own evaluation (9 Apr 2026): six scenarios per condition, LLM judge on Braintrust, run count not stated. Baseline / MCP only / MCP + skill: Claude Code Opus 4.6 58 / **50** / 67; Sonnet 4.6 46 / 58 / 71; Codex GPT-5.4 71 / 71 / 88; GPT-5.4 Mini 42 / 63 / 71. "These are early results with a small sample size" ([Supabase blog](https://supabase.com/blog/supabase-agent-skills)) **[VR]**. With n = 6 a swing of one scenario is about 17 pp; the deltas are within one or two scenarios **[INF]**. The Opus 4.6 regression when the MCP server was added without the skill shows that more tools without rules can reduce security outcomes **[VR]**/**[INF]**. The mechanism is plausible: the independent vibe-app study attributes 658 of 1,186 confirmed vulnerabilities (55.5%) to "hidden security rules" of the platform, exactly what the skill encodes (RLS on views, `app_metadata`, grants, `SECURITY DEFINER`) **[RR]**. Kharma et al. (12 developers, gpt-5.2, Spring Boot) cut authorisation/object-access weaknesses from 30 to 14 with a bundled training-plus-scaffold intervention, no control arm ([arXiv 2604.17763](https://arxiv.org/html/2604.17763v1)) **[RR]**. No study A/B-tests a stack-specific skill against a generic OWASP rules file on identical tasks (gap). Verdict: directionally positive, underpowered, vendor-run, LLM-judged **[INF]**.

### 5.6 AI review: recall limits for authorisation bugs

The one 2026 study that checks whether a reviewer identified the actual vulnerability (MalPR-Bench, 89 malicious PRs plus 50 benign controls) found CodeRabbit blocked 24 of 31 held-out PRs but pointed at the true flaw in 16: **16 of 24 when the evidence lay inside the touched files, 0 of 7 when it lay outside**; for 14 "absence-type" (missing-check) cases it blocked 9 and identified the target in **3** ([Chen et al., arXiv 2608.25730](https://arxiv.org/abs/2608.25730)) **[RR]**. That is the profile of a missing RLS policy, a missing ownership check or an inverted guard **[INF]**. An academic test of Copilot Code Review (public preview, Feb 2025) produced "fewer than 20 comments" across seven vulnerable datasets, "most of which addressed spelling or minor style issues", and no injection or access-control finding ([Amro and Alalfi](https://arxiv.org/html/2509.13650v1)) **[RR]**. Vendor precision figures are 20–68% on Augment's dataset and 64–96% on the CodeRabbit-commissioned Signal65 dataset, neither reporting recall ([Signal65](https://signal65.com/research/ai/evaluating-ai-code-review-tools-a-real-world-bug-detection-study/); [Liatrio](https://github.com/liatrio-labs/claude-code-gauntlet/blob/main/docs/research/artifacts/07-evaluation-benchmarks-and-metrics.md)) **[VR]**. Copilot Autofix's median 28 minutes to fix versus 1.5 hours manual is a remediation-speed metric for CodeQL-detected alerts, not a detection result ([GitHub blog](https://github.blog/news-insights/product-news/secure-code-more-than-three-times-faster-with-copilot-autofix/)) **[VR]**. Bright Security's five-run test is one 300-line app with two planted XSS flaws, undisclosed prompts, undefined denominators and an internal inconsistency ([Bright Security](https://brightsec.com/blog/ai-security-review-fails-in-practice-claude-opus-4-6-missed-critical-vulnerabilities-generated-dangerous-false-positives)) **[VR]**; it illustrates run-to-run variance and nothing more **[INF]**. A clean AI review is not evidence of absence; use it to find and fix faster and keep deterministic scanners and behavioural tests as the gate **[INF]**.

### 5.7 Package hallucination versus in-the-wild exploitation

Hallucination is measured: across 576,000 code samples from 16 models, **440,445 of 2.23 million package references (19.7%)** did not exist; commercial models at least 5.2%, open-source 21.7%; 205,474 unique names; 43% of hallucinated names recurred on all ten re-queries; most are not typosquats (48.6% at Levenshtein distance 6 or more) ([Spracklen et al., USENIX Security 2025](https://arxiv.org/html/2406.10279v3)) **[RR]**. A 2026 re-measurement across Claude Sonnet 4.6, Claude Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro and DeepSeek V3.2 found 4.62–6.10% on 199,845 paired prompts, with 127 names hallucinated identically by all five models and 53 still registrable ([Churilov, arXiv 2605.17062](https://arxiv.org/abs/2605.17062)) **[RR]**. Exploitation is a separate ledger: `unused-imports` (npm) is "a real malicious package" on a name LLMs produce instead of `eslint-plugin-unused-imports`, drawing about 233 weekly downloads in early February 2026 before npm's security hold, "potentially an intentional slopsquatting attack" whose intent Aikido "can't prove"; `react-codeshift` (npm) was a benign name spread to 237 repositories by 47 LLM-generated agent skills and claimed defensively; `huggingface-cli` (PyPI, 2024) was a benign placeholder with more than 30,000 downloads ([Aikido](https://www.aikido.dev/blog/slopsquatting-ai-package-hallucination-attacks)) **[VR]**. The CSA's "tens of thousands of downloads" line conflates the benign placeholder with the malicious package and should not be repeated as malicious reach **[INF]**. Evidence ladder as of October 2026: hallucination confirmed; registration of hallucinated names confirmed, once with malicious code; autonomous agents installing hallucinated names from skill files confirmed; **no documented victim compromise** **[INF]**.

### 5.8 Population evidence for vibe-coded apps

Deng, Fan and Meng (v4, 14 Sep 2026) fingerprinted 74,800 repositories (Claude Code `.claude/` and Lovable meta tags), kept 9,041 with at least 90% AI-authored commits and lines, found 1,007 deployed, randomly sampled 200 deployed web apps and confirmed 1,186 vulnerabilities by two-author manual exploitability review (κ = 0.87): **182 of 200 (91.0%)** vulnerable, median 6 per vulnerable app, 65.77% Critical or High; Broken Access Control 339 findings (28.58%) in **64.0% of apps**, 77% of them backend; Injection in 54.0%; Authentication Failures in 51.5% ([arXiv 2606.23130v4](https://arxiv.org/html/2606.23130v4)) **[RR]**. Root causes: knowledge defects 63.4% (of which "hidden security rules" 55.5%), objective defects 23.1% ("demo-oriented design" 14.7%), memory defects 13.5% **[RR]**. The authors' advice: "generated apps should be treated as prototypes" **[RR]**. No study counts cross-tenant or RLS-correctness failures separately, and no study measures builder expertise; "non-developer builders" is inferred from platform, not measured **[INF]**.

### 5.9 Revised determinism ladder

| Rung | Examples | Evidence as of Oct 2026 | Revised verdict |
|---|---|---|---|
| Generic rules and prompts | "Write secure code"; OWASP reminders | Model-dependent gains on short tasks (Backslash, BaxBench); flat joint rate on agentic repository work (SusVibes); correctness tax; phrasing effects of ±15–20 pp on real apps (Deng replay) **[RR]**/**[VR]** | Conditional, non-deterministic, with a correctness cost; not "mostly theatre", never a control |

## 6. The governance operating model

### 6.1 Gartner and the CSA in their own words, forecast separated from observation

Gartner has published at least three paywalled vibe-coding governance notes. The public abstract of "Govern Vibe Coding for Citizen Developers With Self-Service Platforms" (ID 8068765, 29 Jun 2026) says the shift "raises security, compliance, and governance risks" and that leaders should "enable and govern vibe coding effectively"; it contains no numbers ([Gartner](https://www.gartner.com/en/documents/8068765)) **[CP]**. The two-layer model ("development controls" and "pre-deployment validation"), the agent safeguards ("sandboxing agents, mitigating prompt injection, restricting outbound data flows, and capping token spend") and the two Strategic Planning Assumptions ("by 2028, 60% of vibe-coded applications will be retired"; "30% of software engineering teams will face material capacity strain") are visible only on a vendor reprint page ([Tray.ai](https://tray.ai/guides/gartner-govern-vibe-coding.md)) **[PO]**; they are forecasts with no sample, method or baseline **[INF]**. "How to Govern Vibe Coding" (ID 8207229, 31 Jul 2026) says "Ungoverned vibe coding creates unmanaged risk, bypassing existing security and governance controls" ([Gartner](https://www.gartner.com/en/documents/8207229)) **[CP]**. Gartner's one relevant survey is 302 cybersecurity leaders (Mar–May 2025), of whom 69% "suspect or have evidence that employees are using prohibited public GenAI" ([Gartner newsroom](https://www.gartner.com/en/newsroom/press-releases/2025-11-19-gartner-identifies-critical-genai-blind-spots-that-cios-must-urgently-address0)) **[CP]**.

The CSA's "The Vibe Coding Governance Gap" (2 Jun 2026) recommends "a lightweight registration process—deliberately not a heavyweight review process at this stage", paired with monitoring for unregistered apps and "non-punitive framing"; "The goal of this initial step is awareness, not gatekeeping" ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-vibe-coding-ai-governance-gap-20260602-csa/)) **[CP]**. Its three review categories (internal tools with non-sensitive data; apps processing PII or regulated data; apps incorporating AI API calls or agentic functionality) "warrant different levels of security review" but carry no control lists, owners, exceptions or kill-switch logic **[CP]**. The note does **not** address amnesty programmes, kill switches or lifecycle management, and it states that no major AI security framework (NIST AI RMF, OWASP LLM Top 10, CSA's own AICM) defines a citizen-developer role **[CP]**. Its statistics are inherited: "56% of employees use unauthorized AI tools ... only 23% use IT-governed alternatives" reaches it from IDC via Vectra AI with no N, population or period located **[PO]**. The CSA's shadow-AI note (30 May 2026, "generated with AI assistance" and not through official review) frames governance as "redirection of productive behavior into monitored channels, not prohibition of it" and calls inventory gaps "the primary governance metric" ([CSA PDF](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_research_note_shadow_ai_apps_enterprise_20260530-csa-styled.pdf)) **[CP]**. The T0–T3 tier model in section 8 is therefore the authors' synthesis on a CSA skeleton, exactly as the audit said **[PROP]**.

### 6.2 Named organisations that publish practice: a bounded statement

Of about 40 sources reviewed in October 2026, three organisations describe their own vibe-coding governance in the first person, none of them a bank, telco, public body or EU-headquartered large enterprise, and none publishes an approval SLA, registry schema, expiry rule or outcome metric **[CP]**.

**Method** (fintech, 21 Apr 2026): chat-generated apps get "the same access controls and data handling restrictions as any other internal service"; secret names declared in config, values in a secret manager; secret scanning on every commit; non-root, read-only root filesystem, capabilities dropped; egress limited to DNS and HTTPS; deployment blocked on critical vulnerabilities; three review layers (scanners, AI PR review, human approval); PR-scoped previews on the private network deleted when the PR closes ([Method](https://methodfi.com/resources/method-labs/vibe)) **[CP]**. Outcomes are qualitative only. **Tenable** (6 Oct 2026): "Governance works better than blanket bans, because prohibiting AI-aided development usually causes employees to keep their app development activities hidden"; a five-tier model from Executive Staff through an AI Governance Board, AI Functional Leads with "direct authority and accountability over AI skill approvals, operational queues", an enablement working group and community channels; "Tenable has tied AI tool access directly to mandatory security training" ([Tenable](https://www.tenable.com/blog/how-to-secure-mitigate-ai-risk-vibe-coding-ai-apps-citizen-coders)) **[CP]**. It also records the costs: citizen-coder volume "can become overwhelming and disruptive for the IT and security teams", token spend, and "siloed data lakes" **[CP]**. **EXANTE** (regulated brokerage, 27 Feb 2026): "proper, governed internal APIs ... Not direct database access"; managed environments; "We insist that all vibe-coded work goes into version control"; sharing and discovery; metrics "We're working on it" ([Finance Magnates](https://www.financemagnates.com/thought-leadership/vibe-coding-in-a-regulated-business-or-how-i-learned-to-stop-worrying-and-let-the-compliance-team-have-kittens/)) **[CP]**. An unnamed "large European insurance company" is described second-hand by AWS, for professional engineers ([AWS](https://aws.amazon.com/blogs/industries/how-financial-institutions-can-operationalize-ai-dlc-quickly-and-effectively/)) **[VR]**. All three disclosures converge on governed APIs over direct data access, a managed runtime, version control, review before production and training tied to access; that supports the direction of the paved-road thesis but is three self-reports, not comparative evidence **[INF]**. Government guidance (UK AICA guidance, Australian DTA, US GSA compliance plan, Swedish Digg/IMY) governs staff use of AI tools; none addresses the citizen-built app as an artefact with an owner and lifecycle ([GOV.UK](https://www.gov.uk/government/publications/ai-insights/ai-insights-ai-coding-assistants-for-developers-in-hmg-html); [GSA](https://www.gsa.gov/technology/government-it-initiatives/artificial-intelligence/ai-guidance-and-resources/ai-compliance-plan)) **[CP]**.

Mendix enforces exactly one Technical Contact per app, transferable ([Mendix](https://docs.mendix.com/developerportal/general/app-roles/)) **[CP]**.

### 6.4 Lifecycle controls with specifics

The only fully specified lifecycle machinery in the public record is Microsoft's CoE Starter Kit, now "no longer actively maintained" with core capabilities moved into the admin centre ([Microsoft Learn](https://learn.microsoft.com/power-platform/guidance/coe/governance-components)) **[CP]**. Its shipped defaults are the only mechanised thresholds published anywhere and are configurable examples, not norms **[INF]**: inactivity check for apps not modified or launched in **six months**, owner asked via flow approval, deletion **three weeks** after approval, manager escalation after **one month** of silence; **quarantine after 7 days** of non-compliance (missing business justification), released automatically on submission or manually after an admin risk assessment, with end users shown an access-denied message; orphaned objects reassigned weekly to the former owner's manager with "Take ownership", "Delete" or "Assign to someone else" actions; "Re-publish needed" at 60 days; compliance triggers at sharing with more than 20 users or a group ([Microsoft Learn governance components](https://learn.microsoft.com/power-platform/guidance/coe/governance-components); [quarantine setup](https://learn.microsoft.com/power-platform/guidance/coe/setup-quarantine-components)) **[CP]**. The native admin centre lists ownerless apps active in the last 90 days with "Assign to new owner", and warns that "New owners don't automatically get permissions to the environment or data sources" ([Microsoft Learn](https://learn.microsoft.com/power-platform/admin/security-recommendations)) **[CP]**.

Lovable: when a member leaves, owned projects "pass automatically to the most senior remaining member" (owners, admins, editors), "Projects with access set to Restricted are not transferred automatically", and the leave event is audit-logged on Enterprise ([Lovable workspace docs](https://docs.lovable.dev/features/workspace.md)) **[CP]**; this prevents orphaning but assigns by seniority rather than business relevance **[INF]**. Mendix offers archive/un-archive, single-owner transfer and a 30-day grace after licence expiry ([Mendix](https://docs.mendix.com/private-mendix-platform/reference-guide/admin/company/)) **[CP]**. ServiceNow: reviews "at least once a year"; "Significant modifications go through the same lifecycle phases as new apps"; retirement is notify, resolve dependencies, "Back up the app and its data ... and then delete the app" ([ServiceNow Community](https://www.servicenow.com/community/coe-developer-citizen-articles/citizen-development-define-the-application-lifecycle/ta-p/2494868)) **[CP]**. Method's PR-scoped preview deletion is the only automatic expiry in a vibe-coding-specific disclosure **[CP]**. Exception handling exists in the Starter Kit ("excused" with approval comment) and in GSA's plan (CAIO waivers with written justification, reported to OMB within 30 days, reviewed annually; none issued) ([GSA](https://www.gsa.gov/technology/government-it-initiatives/artificial-intelligence/ai-guidance-and-resources/ai-compliance-plan)) **[CP]**. Supplier review: CSA asks for "vendor security attestations and audit logging in contracts" where source export is unsupported **[CP]**. No source publishes an app TTL, a recertification cadence tied to data class, or an exception register for vibe-coded apps **[INF]**.

### 6.6 Counter-evidence on bans versus enablement

The paved road has four documented weaknesses **[CP]**/**[VR]**. First, the sanctioned platform becomes its own shadow estate: Zenity's customer telemetry reports about 80,000 apps, automations and copilots per large enterprise, 62% with vulnerabilities, 63% of copilots overshared ([Zenity](https://www.prnewswire.com/news-releases/zenity-research-finds-62-of-copilots-and-low-code-apps-contain-security-vulnerabilities-302241231.html)) **[VR]**; Nokod's samples show around 10,000 vulnerable applications owned by 2,500 individuals in large environments **[VR]**; the CSA says governance dashboards are "frequently underutilized" **[CP]**; a Power Platform practitioner describes personal connections as "credentials sharing as a service" ([Perspectives+](https://www.perspectives.plus/p/one-billion-apps)) **[RR]**. Second, maintenance and cost shift to engineering (Gartner forecasts; Tenable's first-person account) **[PO]**/**[CP]**. Third, "bans fail" is under-evidenced: Netskope telemetry (1 Oct 2024–31 Oct 2025) shows **90% of organisations block at least some genAI apps** (average 10) while personal-account use fell from 78% to 47% and organisation-managed use rose from 25% to 62% ([Netskope 2026](https://www.netskope.com/resources/cloud-and-threat-reports/cloud-and-threat-report-2026)) **[VR]**; the 2023 corporate bans were temporary restrictions with no measured outcome ([TechCrunch](https://techcrunch.com/2023/05/02/samsung-bans-use-of-generative-ai-tools-like-chatgpt-after-april-internal-data-leak)) **[PO]**; stated intent to defy bans is self-report (46% of 6,000 knowledge workers, Software AG) ([eWeek](https://www.eweek.com/news/unauthorized-ai-use-surges-at-work/)) **[VR]**. Fourth, non-punitive registration without enforcement has no documented effect; the CSA itself notes policy without communication "may have negligible effect" **[CP]**. The honest framing: paved road plus registration is the consensus recommendation of Gartner, CSA, Tenable, Method, EXANTE and Cloudflare; the consensus practice measured by Netskope is "block many, sanction some"; the two are compatible **[INF]**. No comparative study of ban versus amnesty versus paved-road outcomes exists **[INF]**.

## 7. The legal and standards layer

Nothing in this section is legal advice; the decision trees present regulator guidance, not an opinion on a specific incident, and the audit's instruction to obtain qualified legal review before publication stands.

### 7.1 GDPR: risk-thresholded decision trees per failure mode (EDPB Guidelines 9/2022)

A personal data breach exists only where "a breach of security" led to "the accidental or unlawful destruction, loss, alteration, unauthorised disclosure of, or access to, personal data" (Art. 4(12)); an unexploited vulnerability is an Art. 32 weakness, not by itself a notifiable breach **[CP]**. Once a breach exists, Art. 33 requires notification to the supervisory authority "without undue delay and, where feasible, not later than 72 hours after having become aware of it ... unless the personal data breach is unlikely to result in a risk"; Art. 34 requires communication to individuals only where the breach is "likely to result in a high risk"; Art. 33(5) requires documentation of every breach, notifiable or not ([EDPB Guidelines 9/2022 v2.0](https://www.edpb.europa.eu/system/files/2023-04/edpb_guidelines_202209_personal_data_breach_notification_v2.0_en.pdf), paras 28–29, 82–83, 121) **[CP]**. The EDPB's three breach types are confidentiality, integrity and availability (para 17); "A breach will always be regarded as an availability breach when there has been a permanent loss of, or destruction of, personal data" (para 19); a temporary loss restored from backup is still a breach of security to be documented and assessed case by case, with the worked contrast of hospital data (could present a risk) and a media company's newsletter (unlikely) (paras 20–22) **[CP]**. Awareness arises at "a reasonable degree of certainty that a security incident has occurred that has led to personal data being compromised" (para 31); a short investigation is permitted before the clock starts (para 34); the lost-USB example says notify even when access cannot be established (para 33) **[CP]**. A processor "must notify the controller 'without undue delay'" and "does not need to first assess the likelihood of risk" (para 44) **[CP]**.

The Digital Omnibus (COM(2025) 837, 19 Nov 2025) proposes notification only where a breach is "likely to result in a high risk", 96 hours, and an ENISA single entry point; the EDPB–EDPS Joint Opinion 2/2026 welcomed the direction; as of September 2026 there was a Parliament draft report (22 Jun 2026) and Council working-party activity but no committee vote or trilogue ([Praxikon, 15 Sep 2026](https://www.praxikon.com/en/avg/digital-omnibus/datalekmelding); [White & Case](https://www.whitecase.com/insight-alert/eu-digital-omnibus-what-changes-lie-ahead-data-act-gdpr-and-ai-act)) **[PO]**. **72 hours and the "unlikely to result in a risk" threshold are the law in force** **[CP]**.

| Failure mode | Step 1: is there a breach? | Step 2: Art. 33 | Step 3: Art. 34 | Always | Design duties engaged |
|---|---|---|---|---|---|
| FM1 broken authorisation on a data API | Personal data in exposed tables and evidence of unauthorised read or write (logs, researcher demonstration, a written-back "paid" record) = confidentiality and, with writes, integrity breach; where logs cannot exclude access, paras 31 and 33 point toward treating confirmed exposure as a breach after a short investigation | Notify within 72 h of awareness unless unlikely to result in a risk; addresses, debt amounts, payment data and minors weigh heavily | Communicate only if high risk (financial data, special categories, minors, identity-theft potential) | Document under Art. 33(5) | Art. 32(1)(b), (d) and 25(1); risk-based, not categorical |

Controller and processor roles for personal sign-ups: an employee's personal account creates a contract between the individual and the platform, not between the employer and the platform; absent an Art. 28(3) contract the platform may well be an independent controller for what it receives (Lovable's DPA says so for Service Data); the employer's exposure is then an uncontrolled disclosure to a third party and an Art. 28/32 failure, not "a disclosure to a processor with no Article 28 contract" as the original put it **[INF]**; fact-specific and for counsel. No supervisory-authority decision as of October 2026 applies Art. 33/34 to a vibe-coded app; the EDPB's framework already supplies the analysis, and the contested points will be awareness timing, exposure without proven access, and who is controller for prompt and chat content **[INF]**.

### 7.2 Registry to Art. 30 and Art. 35 without one ROPA per app

Art. 30 records are kept per processing activity (purposes, categories of data subjects and data, recipients, transfers, retention "where possible", and "where possible, a general description of the technical and organisational security measures" under Art. 30(1)(g)) ([EUR-Lex GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj)) **[CP]**. An app supports one or more activities and several apps can support one. The registry should link each app to the activity records it serves by purpose; where none exists the app has surfaced a new processing activity and the DPO creates one; the app's authorisation model, publishing setting, backup arrangement and vendor DPA status feed the Art. 30(1)(g) description and the Art. 28 recipient entry **[PROP]**. DPIAs are triggered by processing "likely to result in a high risk" (Art. 35(1)), not by every citizen app; the WP248 criteria most often met by citizen-built apps are new technology (LLM features, agentic actions), sensitive data, vulnerable subjects, scale, matching datasets and systematic monitoring, with two or more generally requiring a DPIA ([EDPB endorsed WP29 guidelines](https://www.edpb.europa.eu/our-work-tools/general-guidance/endorsed-wp29-guidelines_en)) **[CP]** (wording from prior knowledge; not re-opened). DPIA screening belongs in the registry as a questionnaire, not an automatic trigger **[PROP]**. The registry is nonetheless the strongest Art. 24 accountability evidence available when an authority asks about an app that leaked **[INF]**.

### 7.3 EU AI Act: the three-question "AI system" test and Art. 4/50 status after the Omnibus

Regulation (EU) 2026/1744 (8 Jul 2026; OJ 24 Jul; in force 27 Jul 2026) moved Annex III high-risk obligations to **2 December 2027** and Annex I to **2 August 2028**; Art. 50 transparency applies from **2 August 2026**, with a grace period to 2 December 2026 only for the Art. 50(2) marking duty of generative systems already on the market ([EUR-Lex OJ L 2026/1744](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=OJ:L_202601744); [Commission FAQ on Art. 50](https://digital-strategy.ec.europa.eu/en/faqs/transparency-obligations-under-article-50-ai-act); [AI Act Service Desk timeline](https://ai-act-service-desk.ec.europa.eu/en/ai-act/timeline/timeline-implementation-eu-ai-act)) **[CP]**. Art. 4 as amended reads that providers and deployers "take measures to support the development of AI literacy" with the express clause "This obligation does not require providers or deployers to guarantee any specific level of AI literacy of any individual" ([AI Act Service Desk, Art. 4](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-4)) **[CP]**.

The Act regulates the deployed system's behaviour, not how its source code was authored. Under Art. 3(1) and the Commission's February 2025 guidelines (C(2025) 924), systems "based on the rules defined solely by natural persons to automatically execute operations" and "basic data processing systems" are outside the definition ([Commission guidelines](https://digital-strategy.ec.europa.eu/en/library/commission-publishes-guidelines-ai-system-definition-facilitate-first-ai-acts-rules-application); [CMS summary](https://cms.law/en/pol/legal-updates/eu-commission-issues-guidelines-on-the-definition-of-ai-systems)) **[CP]**. Three questions of the deployed app **[PROP]**:

1. **Does any component infer outputs (predictions, content, recommendations, decisions) from inputs rather than executing human-written rules?** No: not an AI system; GDPR, NIS2/DORA and CRA only. The coding assistant that wrote it is an AI system whose provider is the vendor; the enterprise is a deployer, which is what engages Art. 4.
2. **If yes, is the enterprise placing that component into service under its own name (a branded support bot calling an LLM API)?** If yes it is likely the provider of that AI system (Art. 3(3): "has an AI system ... developed and ... puts the AI system into service under its own name") and also the deployer internally; Art. 50(1) (inform people they interact with an AI system) and, for generative output, 50(2) (machine-readable marking) apply from 2 August 2026, with fines up to EUR 15 million or 3% of worldwide turnover (Art. 99(4)) ([AI Act Service Desk FAQ](https://ai-act-service-desk.ec.europa.eu/en/faq)) **[CP]**. Whether an enterprise merely wrapping a third-party GPAI model is the "provider" for 50(2) is contested and awaits the code of practice; flag for counsel.
3. **Does the use case fall in Annex III (employment, education, credit, essential services)?** If yes, high-risk obligations apply from 2 December 2027; the CSA's "drift into high-risk use cases" risk is real, so the registry records intended use.

The CSA note's "August 2, 2026" high-risk date was accurate when written and is superseded **[CP]**. Art. 4 is a duty of effort; training on BaaS authorisation, secrets and publishing defaults is a natural way to evidence it **[INF]**. The verbatim post-Omnibus text of Art. 50(1)–(5) was not extracted in this pass; sources report no substantive amendment to those paragraphs; confirm against the consolidated text ([EUR-Lex consolidated](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:02024R1689-20260727)) before publication (gap).

### 7.4 NIS2 and DORA with in-scope qualifiers

Neither instrument names AI builders or coding assistants. NIS2 Art. 21(2) requires essential and important entities to address "(c) business continuity, such as backup management and disaster recovery", "(d) supply chain security, including security-related aspects concerning the relationships between each entity and its direct suppliers or service providers", "(e) security in network and information systems acquisition, development and maintenance, including vulnerability handling", "(g) basic cyber hygiene practices and cybersecurity training" and "(i) ... asset management"; Art. 21(3) requires account of each supplier's "secure development procedures" ([NIS2 Art. 21 mirror](https://www.nis-2-directive.com/NIS_2_Directive_Article_21.html); [EUR-Lex Directive 2022/2555](https://eur-lex.europa.eu/eli/dir/2022/2555/oj/eng)) **[CP]**. The applicability chain for an in-scope entity (an inference): the citizen-built app is a system the entity uses for its operations, its development falls under 21(2)(e), the builder is a supplier under 21(2)(d) and 21(3), the estate under 21(2)(i), backups under 21(2)(c) **[INF]**. None of this is universal; it attaches to in-scope entities, is proportionate and varies with national transposition **[CP]**.

DORA (applying since 17 Jan 2025) makes financial entities "at all times ... fully responsible" (Art. 28(1)), requires a register of **all** ICT contractual arrangements distinguishing those supporting critical or important functions (28(3)), pre-contract assessment (28(4)) and, for critical or important functions, "unrestricted" rights of access, inspection and audit, participation in threat-led penetration testing and exit terms (30(3)) ([DORA Art. 28](https://www.digital-operational-resilience-act.com/Article_28.html); [DORA Art. 30](https://www.digital-operational-resilience-act.com/Article_30.html); [EUR-Lex DORA](https://eur-lex.europa.eu/eli/reg/2022/2554/oj/eng)) **[CP]**. A builder hosting an app used by a financial entity is an ICT third-party service provider; every such arrangement, including a shadow personal sign-up, belongs in the 28(3) register and its absence is itself a gap **[INF]**. The decisive qualifier is critical or important function; most prototypes are not, but anything on a payments, onboarding or regulatory-reporting path may be, and for those Lovable's DPA (no audit clause) and Vercel's DPA (audit rights "satisfied by" SOC 2 reports) do not supply 30(3)(e) on standard terms **[CP]**/**[INF]**. No competent authority has named AI builders as a supply-chain category (gap).

### 7.5 Cyber Resilience Act: scope and dates

The CRA (Regulation (EU) 2024/2847) covers "products with digital elements placed on the market": downloadable or installable software, embedded software, and "software plus cloud" where remote data processing is essential; "Pure SaaS is generally excluded" and falls under NIS2/DORA instead; internal tools never placed on the market are out of scope ([Kirkland](https://www.kirkland.com/publications/kirkland-alert/2026/09/the-eu-cyber-resilience-act); [DLA Piper](https://www.dlapiper.com/en/insights/publications/2026/02/cyber-resilience-act-the-fine-line-between-saas-and-digital-products)) **[PO]**. Art. 14 reporting (actively exploited vulnerabilities and severe incidents: early warning 24 hours, notification 72 hours, final report 14 days or one month) has applied since **11 September 2026**; essential requirements, vulnerability handling, documentation and conformity assessment apply from **11 December 2027**; fines up to EUR 15 million or 2.5% of turnover ([Kirkland](https://www.kirkland.com/publications/kirkland-alert/2026/09/the-eu-cyber-resilience-act)) **[PO]**. A vibe-coded SaaS with a Supabase backend is normally outside the CRA; a vibe-coded mobile or desktop app distributed commercially is inside, and its backend may be a remote data processing solution; the manufacturer then owes Art. 14 reporting today and Annex I ("secure by default configuration", "without known exploitable vulnerabilities") from December 2027 **[INF]**. The Commission's separate guidance on remote data processing was not located as published (gap).

The ICO's 8 October 2026 call for evidence on agentic AI is not vibe-coding-specific **[CP]**. No ICO guidance addresses low-code or AI-generated code (gap).

**US.** California's CCPA regulations (effective 1 Jan 2026) require documented risk assessments from 1 January 2026 with attestations due by 1 April 2028 and independent cybersecurity audits certified from 1 April 2028 (revenue over USD 100 million), 2029 and 2030 ([Hunton](https://www.hunton.com/privacy-and-cybersecurity-law-blog/newly-approved-ccpa-regulations-have-staggered-deadlines-for-compliance)) **[CP]**; an unregistered vibe-coded app fails such an audit by omission **[INF]**. The Colorado AI Act (SB 24-205) was repealed and replaced on 14 May 2026 by SB 189, the Automated Decision-Making Technology Act, effective 1 January 2027 if AG rulemaking completes, with notice, explanation and human-review rights, AG-only enforcement up to USD 20,000 per violation, and no algorithmic-discrimination duty of care or impact assessments ([Skadden](https://www.skadden.com/insights/publications/2026/06/colorado-repeals-and-replaces-its-ai-act)) **[CP]**. ### 7.8 DPA procurement checklist

The three documents read in this pass (Lovable DPA, page updated 6 Nov 2025; Vercel DPA, effective 31 Mar 2026; Replit ToS, 3 Aug 2026) share one pattern: processor only for a defined class of Customer Personal Data and independent controller for service, usage or log data; training prohibitions attach to the processor class only; audit rights replaced by SOC 2 or ISO reports; deletion "commercially reasonable" or "may persist in backups"; breach notice "without undue delay" with no hour commitment; sub-processor objection windows of 5–20 days with termination as the sole remedy ([Lovable DPA](https://lovable.dev/data-processing-agreement); [Vercel DPA](https://vercel.com/legal/dpa); [Replit ToS](https://replit.com/terms-of-service)) **[CP]**. Lovable's §10.1 bars training on Customer Personal Data while §9.1(c) permits "training or tuning proprietary machine-learning models" on Service Data; the two "appear to conflict" **[CP]**. Replit's ToS grants a licence to "copy, display, distribute, perform, reformat, and modify your content" and to access private apps for "troubleshooting, improving our service", and does not state whether content trains models; its DPA and Commercial Agreement were not read (gap) **[CP]**. Cursor's security page says Privacy Mode means "we will not train on your data", inheritable by team members, without using the words "zero data retention" ([Cursor security](https://cursor.com/security)) **[CP]**; the original report's BYOK and per-model ZDR caveats came from a different Cursor page not re-opened (gap).

Checklist **[PROP]**, grounded in Art. 28(3) **[CP]**:

1. **Carve-outs.** Identify exactly which data classes the vendor treats as its own controller data; ask in writing whether prompt and chat content is Customer Personal Data.
2. **Training.** Require the no-training clause to cover every class the vendor can see, not only Customer Personal Data.
3. **Audit rights.** Art. 28(3)(h) requires the processor to "allow for and contribute to audits, including inspections"; report-only clauses may suit low-risk processing but not DORA critical or important functions.
4. **Backups and deletion.** Demand a maximum backup retention and a deletion certificate.
5. **Sub-processors.** Monitor the list proactively; map sub-processors to the Art. 30 record.
6. **Transfers.** Confirm the SCC module (Two versus Three) and whether any DPF certification is relied on; Lovable and Vercel rely on SCCs, not the DPF.
7. **Breach notification.** Negotiate a fixed outer bound (24–48 hours from processor awareness) and a duty to notify on suspicion, consistent with EDPB para 44.
8. **Regulated data.** No BAA means no PHI; check PCI DSS responsibility and special-category exclusions.

## 12. Conclusion

Three things changed between the original report and this paper. First, the evidence base is now large enough to say that the leak class is structural and stable: the one random-sample study, the five non-independent scans and twenty incidents agree that the dominant defect is authorisation on a reachable data API, that it is created by the same mechanism the agents use to build (programmatic table creation without grants and policies), and that seventeen months of model releases have not visibly moved the exposure rate. Vendors have responded by changing defaults at the storage layer, which closes the new-table path on Supabase from 30 October 2026 but leaves existing tables, RPC `EXECUTE` and every other BaaS where they were. Second, the agent plane has acquired a documented, vendor-acknowledged anatomy: sandboxes bound shell commands and nothing else; MCP, hooks and file tools run on the host; allowlists bound destinations, not exfiltration; and the only categorical control anyone has shipped is Replit's removal of production from the agent's reach. Third, the legal picture is more precise and less dramatic than "every exposure is a reportable breach": the EDPB framework already decides each failure mode, the AI Act does not reach a CRUD tool, and DORA bites through contract terms that consumer-grade builders do not offer.

The practical consequence for a CISO, platform architect or DPO is a short list of decisions that generated code cannot override: whether the browser may talk to the database at all and, if so, whether anyone has run the cross-tenant matrix; whether a non-admin can publish to the open internet; where the agent's credentials live and what they can delete; whether a copy of the data exists that no credential in the primary account can shorten; and whether the organisation can produce, on request, a register naming an owner for the app that leaked. Everything else in this paper, including its own proposals, is second-order once those five are settled.
